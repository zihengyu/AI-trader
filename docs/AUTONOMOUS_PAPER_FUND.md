# AI 自主组合管理：本地模拟交易

基于原生 LumiBot Agent、Strategy、Broker 和 BacktestingBroker 的纸面账户应用。

**Last Updated:** 2026-11-14

**Status:** 公开行情、本地虚拟账户及一次真实 DeepSeek 盘前研究已验证；量化风控、例外审批、授权资金分仓、盯盘、记分卡、Telegram 回复审批、实时推送报价与资讯监控已通过替身测试；Alpaca、真实推送和开盘交易待验证

**Audience:** 本地运行者和维护者

## Overview

本应用位于 `scripts/autonomous_fund/`，不修改 LumiBot 核心、原有 AI 示例、版本或发布流程。
Ubuntu 的 `.env` 模板、systemd 双服务、审批理由、自动日报和恢复验收步骤见
[服务器部署说明](AUTONOMOUS_FUND_UBUNTU.md)。该入口启动时保持 STOP，独立监控正常后由操作员恢复。
用到的每个数据源、局限和升级路线见[数据源与升级路线](AUTONOMOUS_FUND_DATA_SOURCES.md)。
`researcher` 研究行情、技术指标、基本面、新闻与持仓；`critic` 给出研究的反面论证；
`manager` 自主选择完整目标组合、现金比例和下次复核时间。
两者复用原生 `self.agents.create()` 和结构化 `output_schema`，均设置 `allow_trading=False`。
这是用户指定的混合策略：唯一的投资决策者输出目标，独立 Python 代码执行量化风控、风险准入与订单。
AI 的权重是上限：确定性量化风控只会把它们缩小（波动率目标、ES、历史危机情景、按波动率调整的单名上限、行业组上限、
财报前上限、回撤分档预算、单日亏损闸门和流动性），见[量化风控原则](#量化风控原则)。唯一的例外是有证据支持时
自动启用的风险预算构建：同样的证券和总仓位，按 AI 权重重新分配风险贡献，见[反方审查与组合构建 A/B](#反方审查与组合构建-ab)。
本应用不是对官方纯 AI 示例模式的修改。

没有固定买卖信号，也不要求每天交易。默认配置包含多只流动性较高的美股和普通 ETF；
操作员可审核并修改名单，AI 可在名单内自由选择。名单是操作员信任边界，不能让 AI 修改分类或把杠杆／反向基金伪装成普通 ETF。
每次交易前还检查最近 20 个已完成交易日的平均成交额至少 2,000 万美元。
这份当前名单不是历史成分股数据库；历史实验存在存活者偏差，严肃研究应提供当时可投资的名单。

## 安装和启动

在项目根目录执行。示例中不包含真实密钥；请通过当前进程环境或自己的秘密管理器注入凭证。
启动器不使用 LumiBot 的 `.env` 自动发现，只显式选用本仓库根目录的 `.env`（见[`.env`：运营者配置入口](#env运营者配置入口)）。

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt -r scripts/autonomous_fund/requirements.txt
```

应用依赖固定 `litellm==1.105.1`，与框架要求的 MCP 1.x 配合使用；不修改共享依赖或升级 MCP 主版本。
修改依赖前先停止正在运行的模拟盘。以后重新安装共享依赖后，也需重新应用本应用的依赖约束。

### 启动模式：由 `.env` 的 `FUND_MODE` 决定

在 `.env` 中设置 `FUND_MODE` 后，**不带命令**启动（或服务器服务重启）就按该模式运行；修改后重新启动即生效：

| `FUND_MODE` | 含义 | 需要 |
|---|---|---|
| `local`（默认） | 真实行情本地模拟盘：Yahoo 实时行情＋本地虚拟资金，本地保守撮合，不连接任何券商 | 模型 Key |
| `paper` | Alpaca 模拟账户：券商模拟撮合，不是真钱 | 模型 Key＋Alpaca Paper Key |

```powershell
.\scripts\run_autonomous_fund.ps1
```

Linux：`bash scripts/run_autonomous_fund.sh`。启动时第一行会打印模式、来源（`FUND_MODE`／命令行／默认）和账户目录。

- **没有实盘选项**：`FUND_MODE` 只接受 `local`、`paper`，写 `live`、`schwab` 或其他任何值都拒绝启动。
- **账户目录**：`FUND_RUN_DIR` 留空时为 `artifacts/fund-<模式>`，local 和 paper 的账本自动分开，切换模式不会混用账本；
  若以前不带 `-RunDir` 启动过，账本在旧默认目录 `artifacts/autonomous-fund`，系统会识别并继续使用它。
  `stop`、`resume`、`approvals`、`report`、`acceptance` 等命令不带 `--run-dir` 时，也作用于 `FUND_MODE` 对应的账户。
- **只读观察**：`FUND_OBSERVE_ONLY=true`（仅 local）不调用模型、不下单。
- **显式命令优先**：`-Mode local`／`-Mode paper`（Linux 为 `local`／`paper`）或 `-RunDir` 仍然有效，并覆盖 `.env`；
  mock、backtest 等历史实验从不写入账户目录。
- `stop` 即使 `.env` 有拼写错误或文件权限不对也会执行（并提示错误），仍会读出其中的 `FUND_MODE`／`FUND_RUN_DIR`；
  不带 `--run-dir` 时，除了 `FUND_MODE` 对应的账户，还会停止所有最近一小时内有心跳的账户（包括刚退出、可能马上被服务重启的），
  因此用 `-Mode paper` 等显式命令启动的账户也不会漏停；某个目录写入失败不影响其他账户，最后会列出失败的目录。
  指定的 `--run-dir` 不存在时直接报错并列出最近活动的账户，不会因为路径写错而误报“已停止”。紧急停止不会被配置问题挡住。
- `show-config` 会显示最终的启动模式、来源和账户目录。

无需密钥的完整机械检查：

```powershell
.\scripts\run_autonomous_fund.ps1 -Mode mock -RunDir artifacts/fund-mock
```

它运行真实 LumiBot 回测引擎与限价订单，但价格和两名 Agent 的回答都是合成测试数据。
输出会明确标识 `mode=mock`、`scripted_model=true`，不证明投资收益。
每次历史实验使用新的目录，防止混合账本。PowerShell 启动器对回测设置 1,200 秒上限。
Python 模块同样可跨平台运行：`python -m scripts.autonomous_fund.run --help`。

## `.env`：运营者配置入口

模型 Key、你给 AI 的约束和外部参数都可以写在仓库根目录的 `.env`（已被 Git 忽略；从
`scripts/autonomous_fund/.env.example` 复制）。优先级为 **进程环境变量 > `.env` > `config.json`**：
`config.json` 保存完整的、经审阅的默认策略，`.env` 只覆盖你要改的项；模板里的风控与参数值与默认值一致，留空表示不覆盖；
模板中的 `FUND_MODE=local` 决定不带命令启动时进入本地模拟盘。
每个覆盖都按与 `config.json` 相同的规则校验，记入启动审计（`startup.environment_overrides`），并且会使旧目标失效、由 AI 按新规则重新决策。
`.env` 中写错的 `FUND_*` 名称会直接拒绝启动并提示正确名称，避免约束被静默忽略。

| 类别 | 变量 | 作用 |
|---|---|---|
| 启动 | `FUND_MODE`、`FUND_RUN_DIR`、`FUND_OBSERVE_ONLY`、`FUND_AUTO_RESUME` | 启动模式 local／paper（没有实盘）、账户目录、只读观察（见[启动模式](#启动模式由-env-的-fund_mode-决定)）、重启后安全条件下自动恢复交易 |
| 模型 | `DEEPSEEK_API_KEY`（及可选 `OPENAI_API_KEY`、`ANTHROPIC_API_KEY`） | 模型 Key |
| 模型 | `FUND_RESEARCH_MODEL`、`FUND_DECISION_MODEL`、`FUND_REASONING_EFFORT` | 研究员／基金经理模型与推理强度（角色变量优先于 `AI_MODEL`） |
| 模型 | `FUND_MAX_AGENT_RUNS_PER_DAY`、`FUND_MIN_REVIEW_MINUTES`、`FUND_MODEL_PRICES_JSON`、`FUND_MAX_DAILY_COST_USD` | 每日调用上限、最短复核间隔、费用估算价格（含缓存命中价 `cached_input`）、每日模型费用上限 |
| 模型 | `FUND_SKIP_QUIET_REVIEWS`、`FUND_MAX_QUIET_MINUTES` | 到点复核时无任何变化就跳过模型调用、连续跳过的最长分钟数（见[模型调用预算](#模型调用预算与失败退避)） |
| 外部 | `FUND_DATA_DESK`、`FUND_DESK_INTRADAY_SECONDS` | 数据员（常驻服务，持续拉取整理资讯、盘中行情、宏观、财报）开关、盘中行情刷新间隔 |
| 约束 | `FUND_CAPITAL_USD`、`FUND_ALLOW_EXTERNAL_HOLDINGS`、`FUND_LOCAL_ACCOUNT_USD` | 授权资金（如账户 5 万只给 AI 1 万）、是否有你自己的持仓、本地虚拟账户资金 |
| 约束 | `FUND_MAX_POSITION`、`FUND_MAX_EXPOSURE`、`FUND_MAX_DRAWDOWN`、`FUND_DAILY_ORDERS` | 单只上限、总敞口、回撤硬锁、每日提交次数 |
| 约束 | `FUND_DAILY_LOSS_LIMIT`、`FUND_TARGET_VOL`、`FUND_MAX_ES` | 单日亏损闸门、波动率目标、尾部损失上限 |
| 约束 | `FUND_EXTRA_STOCKS`、`FUND_EXTRA_ETFS`、`FUND_EXCLUDE_SYMBOLS`、`FUND_INSTRUCTIONS` | 加入投资范围的股票和非杠杆 ETF（`代码:分组` 计入该行业上限）、禁止交易的代码（逗号分隔）、给 AI 的文字约束（`|` 分隔） |
| 外部 | `FUND_RESEARCH_SYMBOLS` | 只供因子研究、不交易的额外股票 |
| 审批 | `FUND_AUTOMATION_MODE`、`FUND_APPROVAL_MODEL`、`FUND_AUTO_DAILY_EXPOSURE_INCREASE`、`FUND_AUTO_DAILY_BUY_TURNOVER`、`FUND_STRESS_REQUIRES_APPROVAL`、`FUND_APPROVAL_VALID_MINUTES` | 自动／人工审批模式、独立审批模型、自动额度（设 0 则所有买入都审批）、压力下是否审批、有效期 |
| 通知 | `FUND_TELEGRAM_BOT_TOKEN`、`FUND_TELEGRAM_CHAT_ID`、`FUND_TELEGRAM_APPROVER_IDS`、`FUND_TELEGRAM_APPROVALS` | Telegram 通知与回复审批 |
| 外部 | `FUND_ITERATION_SECONDS`、`FUND_LIVE_STREAM`、`FUND_RESEARCH_RESOLVER` | 盯盘间隔、实时推送报价、研究网页解析（Fake-IP 用 `doh`） |
| 外部 | `FUND_NEWS_ENABLED`、`FUND_NEWS_POLL_SECONDS`、`FUND_NEWS_QUERIES`、`FUND_NEWS_RSS_FEEDS`、`FUND_SEC_USER_AGENT`、`FRED_API_KEY` | 实时资讯监控与数据源 |
| 外部 | `FUND_SHADOW_AB`、`FUND_FACTOR_LAB` | 影子 A/B 验证 AI 的复盘学习；因子实验室（AI 提出因子、代码客观检验） |
| Alpaca | `ALPACA_API_KEY`、`ALPACA_API_SECRET` | paper 必填 Paper 凭证；local 选填一整对，用于日线核对及备用行情 |
| 模拟标识 | `ALPACA_IS_PAPER` | 仅 paper 读取，默认 `true` |
| Schwab | `SCHWAB_ACCOUNT_NUMBER`、`SCHWAB_APP_KEY`、`SCHWAB_APP_SECRET`、`SCHWAB_BACKEND_CALLBACK_URL`、`SCHWAB_TOKEN`、`SCHWAB_TOKEN_PATH` | 仅用于只读体检 `schwab-check`（见“Schwab 实盘准备”） |

投资范围的新增、行业分组和其余细节参数仍在 `config.json` 中修改（新增证券需要审阅分类）。
查看最终生效的配置及每项来源（密钥只显示已设置／缺失）：

```powershell
.\scripts\run_autonomous_fund.ps1 -Mode show-config
```

Windows 和 Linux 启动器都会显式选用仓库根目录的 `.env`（解析而非执行，进程环境优先），也可用 `-EnvFile`／`--env-file` 指定其他文件。
LumiBot 自身的 `.env` 自动发现仍保持关闭。

## 无券商账户：真实行情本地模拟盘

`local` 模式读取 Yahoo 公开行情，将虚拟资金（`mandate.local_account_usd`，默认 10,000 美元，仅在新账本创建时生效）、持仓和订单保存在本地。
它使用原生 `Broker`、`Order`、`Position`、`Strategy` 和 `Trader` 生命周期，
不构造任何券商交易客户端，不需要 Alpaca／Schwab 账户或券商 Key。
它不是券商 Paper 账户，成交属于明确标记的本地虚拟成交。

先检查真实行情与所选模型的凭证是否存在，不调用模型：

```powershell
.\scripts\run_autonomous_fund.ps1 -Mode check -RunDir artifacts/fund-market-check
```

默认研究员使用 `deepseek/deepseek-flash`，基金经理使用 `deepseek/deepseek-v4-pro`，共用你自己的 `DEEPSEEK_API_KEY`。
可在当前 PowerShell 中安全输入，输入不会显示，也不会写进命令历史或仓库：

```powershell
$fundKey = Read-Host 'DeepSeek API Key' -AsSecureString
$env:DEEPSEEK_API_KEY = [System.Net.NetworkCredential]::new('', $fundKey).Password
Remove-Variable fundKey
.\scripts\run_autonomous_fund.ps1 -Mode local -RunDir artifacts/fund-local
```

密钥最终仍是进程环境中的字符串；本例没有把它保存到文件。关闭终端后需重新注入。
推荐把 Key 写进仓库根目录的 `.env`（从 `scripts/autonomous_fund/.env.example` 复制），启动器会自动选用它；
也可用 `-EnvFile <your-secret-file>` 指定其他文件。现有进程环境优先，启动器不搜索其他目录的 `.env`。不要把真实密钥发到聊天或提交 Git。

没有模型 Key 时，只读观察模式可先验证启动、资金记录和交易日历，完全不调用模型或提交订单：

```powershell
.\scripts\run_autonomous_fund.ps1 -Mode local -ObserveOnly -Once -RunDir artifacts/fund-local-check
```

去掉 `-Once` 可持续运行只读观察；有 Key 后去掉 `-ObserveOnly` 启动 AI 自主研究和虚拟交易。
正常重启继续使用同一目录；不要通过换目录重置风险锁。`local` 的账户与券商账户彼此独立。
进程需保持运行、电脑需联网且不休眠。NYSE 休市时等待下次开盘，日历包含节假日、夏令时与提前收盘。
休市不妨碍研究：正常模式启动时先完成一次只读研究，周末也可运行；
原生 `before_market_opens` 钩子会在正常开盘前一小时更新研究。
同一目标交易时段、同一研究阶段成功完成后持久化去重，正常重启会读取已有结论；不是全天循环收费调用模型。
若在开盘前一小时内启动，启动研究与盘前钩子属于同一阶段，不重复成功调用。
开盘后基金经理直接评估实时账户、行情和风险，参考已保存的盘前结论及其原始时间，
并使用自己的只读研究工具核查信息。缺失、无效或较早交易日的预研会明确标注，
不再同步重跑研究员或等待其成功。经理的结构化目标仍需独立验证，再重新读取账户、行情和风控。
盘前研究不会成为待开盘直接执行的订单。
独立执行入口和本地撮合器均要求正常交易时段；盘前陈旧收盘价只供研究，不能用于成交。
`-ObserveOnly` 和人工 STOP 标记会阻止自动研究；历史回测的研究时间规则不变。

盘前研究可通过运行中的 `report` 命令查看 `latest_premarket_research`，
也会导出为 `premarket_research.json`，含研究起止时间、目标开盘时间、研究结论与证据。
修改代码后，已有进程需要在原 PowerShell 中 Ctrl+C 结束，再用原命令和原运行目录重启；
账户与风控账本保留，不要并行启动第二个交易进程。
`status.json` 的 `heartbeat_at` 表示轮询活性；`runner_state=exited` 表示已退出，
`stopped` 另指人工 STOP 标记。强制终止后应结合心跳年龄判断，旧状态文件不能证明进程仍在运行。

行情与撮合的具体限制：

- Yahoo 提供完成的一分钟 OHLCV，不保证交易所实时性、服务可用性或盘口覆盖；可能延迟或限流。
  报价保留源时间，超过 60 秒时禁止成交，不会放宽阈值或用接收时间冒充新行情。
  当前日线不进入技术分析／流动性样本，未完成的分钟线也不进入研究或撮合。
- 买卖价是围绕最新完成分钟收盘价加减 10 基点总价差的代理值，明确标注为
  `completed_minute_close_with_spread_proxy`，不是交易所实际 bid/ask。
- 下单后必须等待开始时间晚于提交时刻的一根新分钟线完整结束。
  买单用该分钟最高价再加半价差和 5 基点滑点，卖单用最低价减去同等摩擦，向不利方向取整。
  价格超出限价则不成交；单分钟最多取观测成交量的 1%，可部分成交；买入、卖出各按成交额另扣 0.1% 模拟费用。
  费用在成交事务中直接扣除现金，因此已包含在净值和收益里；价差和滑点另体现在成交价中。
  这些是保守的透明假设，不重放真实排队或订单簿，也不代表可实现收益。
- 成交时重新核验持仓／总敞口、现金、回撤、STOP、有效期和所有持仓报价的新鲜度。
  到期订单撤销，停机期间已过时的分钟线不追补成交。成交、现金、持仓和审计事件同一事务提交，
  重启不会重复成交或重复扣费。本地已接受订单及意图 ID 同一事务保存，没有券商网络确认的不确定窗口。
- 持有期间拆股同步调整数量和成本；无法整股表示的拆并股、供应商修改已处理动作时暂停撮合并记录异常。
  Yahoo 在拆股后按拆股比例改写历史分红金额（如 0.40 变为 0.20），这种改写不算修改；真正的金额修改仍需人工核对。
- 卖出（降风险）成交不要求其他持仓的报价新鲜，只要求本证券的成交价不早于已应用的拆股；买入仍要求所有持仓都有新鲜估值。
  分红仅按除息事件计入不可花费的应收款，因为此来源没有可靠付款日，首版不自动转为可交易现金。
  分红数量从除息日前的成交账本重建，除息日新买入不参与；若迟报时相关持仓已清空或重开，可能漏计，需人工补核。
  拆股迟报且已发生除息日后的交易时暂停撮合。复杂公司行动、退市、并购、换股和税务尚未完整覆盖，
  本地报告不能视作完整的税后总收益账单。

Yahoo 公开数据的使用还须符合其条款；本模式用于个人研究与功能验证。
若正常交易时段行情长期超时或延迟，需要在后续阶段接入有权限的行情服务，届时再配置该服务的 Key。

`Getting historical prices ... 10000 bars` 可来自原生递归指标的预热请求，不代表 AI 主动要求逐条研究一万天。
本地适配器接受正整数长度并返回供应商实际可用的已完成 K 线；不足请求数量时不填充、不伪造历史。
已通过原生 `get_indicator` → Strategy → 本地数据源的 EMA 回归，而不是只测试行情函数本身。
模型出现 `first ADK event` 说明已有模型事件，不代表整轮研究完成；成功标志仍是 `Pre-market research saved`。
`Agent run exceeded 300s timeout` 指整轮研究超时，原生运行时会重试；切勿把重试日志当成完成。
超时或被终止的调用可能没有返回完整 usage，报告中的模型成本不能视为完整账单，应同时核对提供方记录。

若使用 OpenClash 等代理，排查是否有流媒体解锁任务不断切换行情所用的主代理组。
先稳定该代理组，再运行 `check` 验证真实行情；不要通过关闭 TLS 校验或放宽报价时效来掩盖网络故障。

## 独立风控与执行合同

默认风险参数集中在 `config.json`，加载成不可变策略对象；模型没有配置写入或交易修改工具。
本应用还锁定研究用 DuckDB 的文件／扩展访问，防止多语句 SQL 读写风险账本或本地凭证；
已加载的行情／文档表仍可分析。研究浏览器只接受 HTTP(S) 导航，不能直接打开本地文件或脚本 URL，
下载和上传保留在独立研究目录。浏览器为原生可选依赖，本次未做真实浏览器联网验证。
禁止融资、卖空、期权和期货；只提交整股、当日有效限价单。
硬上限：单证券 10%、总证券敞口 70%、每日提交上限 20 次（含改价重挂）、观测净值高点回撤 8% 锁定增仓。
提交上限按方向分开计算：买入计入当日**全部**提交（大量卖出不会腾出买入额度）；卖出只计卖出，另有同样大小的额度，保护性止损／止盈再多 5 次。这样买入和追价重挂用尽额度的当天（往往正是大跌日），回撤降仓和止损卖出仍能执行。
拒绝非有限数值、重复证券、超额目标、未来／过期决策、陈旧账户或报价、缺失流动性证据。
日限额按纽约交易日计算，买卖、失败和取消的提交均占用次数。
上涨使持仓超过上限、或回撤使预算下降时，执行中按约束自动减持（超过再平衡带时）；
到达 8% 硬锁后预算降到 25% 敞口并自动卖出超出部分。跳空和停牌造成的实际亏损不保证止于这些阈值。

每笔订单都走同一条确定性路径：AI 目标 → [量化构建](#量化风控原则)（只缩小权重）→ 自动额度／审批判断 →
按净值、现金、实际持仓和限价计算整股数量 → 预留并提交。规划和预留前各独立计算一次，结果不同即拒绝。
先执行减仓，每次最多提交一笔，再等待状态确认、重新读取资金和持仓，继续执行仍有效的目标。
目标在新鲜模型回答通过校验时持久化，后续每次迭代可继续调仓，不必等待下一次模型复核。
新回答仍须在五分钟内接受；已接受目标只保留到 `next_review_at`（不早于最短复核间隔）与 `expires_at` 较早者，
每一笔继续执行都重验账户、报价、流动性、回撤、订单次数和审批。重启恢复目标与复核时间，不重置账户。
AI 思考两三分钟后，先重读账户与行情，再按新价格计算股数和委托限价；不会把思考前的价格当成成交价。
有 `entry_limit` 时，当前 ask 超过该价位会等待；没有入场价时，首次下单依据新价执行，
不会自动套用“相对思考前涨幅过大就重审”的规则。追价上限针对首次提交后的重挂，并不覆盖首次提交前的价格变化；
原投资逻辑是否仍成立仍需经理结合最新证据判断，价格／账务校验不能代替该判断。
目标到期时尝试撤销本应用的未完成订单，并等待券商确认后再接受替代目标。
未成交卖单不能为买单提供资金；账户中任何未完成或未知订单都会阻止新的订单。

执行质量控制（`execution` 段）：

- **改价重挂**：限价单挂出超过 `reprice_after_seconds`（默认 180 秒）仍未完成，就请求撤单；
  券商确认撤单后，下一次迭代按新报价和全部风控重新计算，而不是让一张不成交的单冻结整个组合。
  撤单是异步的（券商会先显示“撤单中”）：同一订单只请求一次，确认前不会每次迭代重复请求；
  若 240 秒后券商仍显示该单在工作中（请求可能丢失），才再请求一次。
- **追价上限**：同一决策内同一证券的买入限价不能高于首次提交限价的 `max_buy_chase`（默认 0.75%）；
  超出即停止追买该证券并记录 `buy_chase_limit`。卖出（降风险）不设追价上限。
- **再平衡带**：小于 `max(min_trade_notional, rebalance_band × 净值)`（默认 max(100 美元, 0.5%)）的调整不交易，
  避免价格小幅波动造成来回买卖；目标为 0 的完全卖出始终执行。
- **流动性参与率**：单笔名义金额不超过最近 20 个已完成交易日平均成交额的 `max_adv_participation`（默认 1%）。

SQLite 在下单前原子保存意图和日限额，写入失败则不下单。账本使用 WAL 和按事件类型的索引，
监控读取不再阻塞交易写入；`events.jsonl` 增量追加（被改动则自动全量重建；每个 UTC 自然月压缩归档为
`events-YYYY-MM.jsonl.gz`，见“数据保留”），报告每 `report_interval_seconds`
（默认 300 秒）重建一次，收盘和退出时总会重建。
提交超时、响应丢失或程序崩溃后不自动重发。同目录进程锁和相同 API Key 的跨目录进程锁避免重复启动。
请只用一个专用 Paper 账户、一个凭证及本应用交易；不同机器、不同 Key、外部手动交易或其他程序不受本地锁控制。
Alpaca 模式只查询**未完成**订单（上限 500 条，达到即拒绝继续），本应用自己的订单逐笔按券商 ID 核对，
历史订单数量不再导致账户在约 100 笔后永久锁死。

本地模拟订单在实际接受事务中重新检查 STOP、撮合是否启用、市场时段、声明的订单有效期和必需的独立监控；
等待锁或核对账本期间跨过截止时间也会拒绝。`created_at` 使用检查完成后的接受时间，
不能拿等待期间已开始的分钟线当作提交后的执行证据。
如果意图身份匹配、且数据库确认没有对应本地订单，这类拒绝记为 `local_order_rejected`，
释放该意图的未决锁，同时保留尝试和日限额历史；不推断外部券商的未知提交结果。
接受、成交和取消的数据库提交与原生订单事件在同一订单状态锁下顺序发布，避免迟到的 NEW／部分成交回调覆盖最终状态。
该锁不覆盖行情 I/O；另一线程等待持仓行情时仍可取消订单，后续撮合会重新检查其持久状态。
STOP 和到期取消先于公司行动行情读取，因此行情故障不会挡住取消；有效且未到期的订单仍等待行情恢复。

正常重启继续使用同一 `--run-dir` 和凭证。账本与账户／模式绑定，不会把另一账户的高水位或订单借来使用。
已保存券商 ID 的订单逐笔向券商查询。完整成交可从券商累计数量和均价恢复，标记为
`broker_cumulative_observation`，时间是观察时间；不会虚构停机期间的逐笔执行时间。
部分成交通过原生回调记录；停机期间部分成交后又取消的明细可能缺失，需要券商成交记录补核。
账户状态重读仍用于风险校验，缺失费用不会按零费用包装。

若崩溃恰好发生在券商接受之后、ID 保存之前，系统保持锁定。
先在 Paper 券商界面确认确切订单，再停掉本应用进程，使用：

```powershell
.\.venv\Scripts\python.exe -m scripts.autonomous_fund.run attach-order --run-dir artifacts/fund-paper --intent-id <intent-id> --broker-order-id <broker-order-id>
```

恢复程序校验相同凭证／账户、证券、方向、完整数量、限价及创建时间窗口，只绑定已有订单，不发单。
若确认从未发出订单，保留证据并人工维护该预留；首版不提供一键“假装失败后重试”。

## 授权资金与约束

人的角色是设定约束、审批例外和阅读复盘。约束写在 `config.json` 的 `mandate` 段：

```json
"mandate": {
  "capital_usd": "10000",
  "allow_external_holdings": false,
  "local_account_usd": "10000",
  "instructions": ["只用授权资金 capital_usd 交易……", "不使用杠杆、融资、卖空……"]
}
```

- **授权资金 `capital_usd`**：账户有 5 万美元而只允许 AI 用 1 万时，设为 `"10000"`。首次启动时把超出部分记为
  **保留现金**（`mandate_reserve_cash`），AI 看到的账户、净值、仓位比例、回撤、单日亏损和全部量化约束都只按这 1 万的分仓计算；
  分仓现金永远不能低于 0，因此不可能动用保留现金，也不可能形成融资或杠杆。本地撮合器在成交瞬间也按分仓复核。
- **调整规模（申购／赎回）**：见下一节，推荐用脚本。也可以把 `capital_usd`（`.env` 的 `FUND_CAPITAL_USD`）改成你想要的
  **净投入本金**后重启。基金登记目标（`mandate_capital_change_requested`），轮到它时按已确认的本金重新计算差额。
  前面的请求被拒绝或取消时，差额也会随之更新。`.env` 的值保持原样时，用脚本申赎不会触发新的配置请求。
- **模拟盘余额变动**：在账户端调整后，可以用下一节的命令登记。`adjust-reserve --amount` 也可以手工修正保留现金。
- **外部持仓**：默认要求专用账户。`allow_external_holdings: true` 时，投资范围以外的股票视为你自己的持仓，
  不计入分仓、AI 不会交易；它们的数量在首次启动时冻结，之后若有变化（你手动买卖）则停止交易，
  核对后用 `adjust-reserve --rebaseline-external`（必要时同时 `--amount`）重新确认。投资范围以内的证券不能作为外部持仓。
- **文字约束 `instructions`**：最多 20 条，例如“财报前两个交易日不新建仓位”“单一行业不超过 20%”。
  研究员和基金经理每次都收到这些约束并被要求遵守；盘后复盘必须在 `mandate_compliance` 中逐条自评，日报展示。
  能写成数字的约束请优先放进 `limits`、`quant_risk` 或 `approval`，由代码强制执行；文字约束依赖 AI 遵守，需要你抽查日报。

### 申购与赎回（加钱、取钱）

做法和公募基金一样：份额（units）和单位净值（NAV per unit）。第一次申购或赎回之前，每 1 美元授权资金算 1 份，
所以单位净值就是基金成立以来的增长。申购 X 美元按当时的单位净值发行 X／净值 份；赎回 X 美元注销 X／净值 份。
申购赎回前后单位净值不变，所以这笔钱**不算收益也不算亏损**。实现见 `scripts/autonomous_fund/capital.py`。

```bash
bash scripts/fund-capital.sh                  # 查看：份额、单位净值、净投入本金、等待中的请求、最近的申购赎回
bash scripts/fund-capital.sh subscribe 10000  # 申购：加 10000 美元
bash scripts/fund-capital.sh redeem 5000      # 赎回：取 5000 美元
bash scripts/fund-capital.sh cancel <编号>     # 取消等待中的请求
```

本地虚拟账户和 Alpaca 模拟盘使用同一套命令，都可以在服务运行时登记。首次使用需要为该账户配置数值型
`FUND_CAPITAL_USD` 并启动一次。这个运行器支持 `local` 和 `paper` 两种模式。
已有数值型授权的账本需要保留数值配置，以维持原份额和保留现金的边界。

需要安全重试时，为 `subscribe`、`redeem`、`deposit` 或 `withdraw` 提供自选操作编号，例如
`bash scripts/fund-capital.sh subscribe 10000 --operation-id add-001`。在同一账本用相同编号和参数重试会返回原登记。
同一编号对应一笔操作。提交新操作时请换一个编号。

| 模式 | 申购的钱从哪来 | 赎回的钱到哪去 | 额外步骤 |
|---|---|---|---|
| 本地虚拟账户 | 存入虚拟现金 | 从虚拟账户取出 | 无 |
| 模拟盘（Alpaca paper） | 账户里没有交给 AI 的余额（保留现金，例如 10 万账户只授权 1 万时的 9 万） | 回到保留现金 | 无：模拟盘没有真实转账 |

对于 Alpaca 模拟盘，通常只需要 `subscribe` 和 `redeem`。如果操作员已在账户端单独完成余额调整，
可以在基金停止时用 `deposit`／`withdraw` 登记对应金额。命令只写账本，账户端的余额由操作员核对。
`deposit` 默认也登记申购，加 `--reserve-only` 则把这笔钱留在保留现金。
通过 `FUND_CAPITAL_USD` 增资时，如果模拟盘保留现金不足，请求会保留在队列中。
如果已单独调整模拟盘余额，停服务后用 `deposit --reserve-only` 登记差额，重新启动后原申购即可继续。
也可以修改目标本金并重启，最新配置会替换尚未完成的配置目标，保留用脚本明确登记的申赎。

- **脚本只登记请求，基金自己执行**：交易进程在下一个交易时段的估值点、本应用没有挂单时，按当时的单位净值确认，
  和下单、成交、风控检查不会同时发生；投资不中断。STOP 或只观察模式期间请求保持等待，恢复后再处理。确认后 Telegram 通知，并请基金经理按新的规模重新复核
  （目标是权重，规模变了照样有效）。
  申赎确认和筹资卖单使用当日有效的账户估值。状态命令也会显示近期被拒绝、取消和已达到的配置目标，便于按请求编号核对。
  拿到数据库写锁后、以及计算份额后开始写入前，重新检查 STOP、常规交易时段和估值新鲜度；
  等待期间若跨过收盘、切换交易日、时钟回退或估值过期，请求保留等待，现金、份额和风控基准均不修改。
  事务内只查询本地交易日历，券商状态查询仍在事务外，避免网络等待占用资金账本写锁。确认事件使用锁等待后的实际时钟。
- **钱从哪里来、到哪里去**：本地虚拟账户（local）申购就是存入虚拟现金、赎回就是取出（账本事件 `local_cash_flow`，
  账务校验会逐笔核对现金、份额和赎回前后的权益）。Alpaca 模拟盘从保留现金申购，赎回资金回到保留现金（见上表）。
- **份额精度**：保留 8 位小数。如果当前单位净值下，请求金额舍入后对应零份额，或份额价值与请求金额的差达到半美分，
  则拒绝该请求并说明精度原因，不划转现金；可用当前份额刻度能够表示的金额重新提交。正常单位净值下的 0.01 美元申赎仍支持。
- **赎回现金不够怎么办**（专业基金的流动性顺序）：
  1. 先检查能否用现金支付。股票仓位以赎回前的权重加 5 个百分点为目标，整股交易允许 1 个百分点的容差。`max_position` 和 `max_exposure` 始终是硬上限。
  2. 如需降低仓位，先计划将单只证券降到上限，剩余部分按比例从 AI 持仓计划整股卖出。持仓估值齐备时，暂缺可执行买价的标的留在计划内，其余有报价的计划卖单可以继续。
     跨交易日时用开盘后已对账的持仓重算剩余切片，避免拆股等公司行动让旧股数失效。
  3. 每次成交后用新估值复核。仓位达标后，如果仍缺现金，优先卖现金替代 ETF（如 SGOV），数量按预计扣费后的到账额计算。
  4. 实有现金足够才确认赎回。虚拟账本的应收股息计入净值，可用现金只计算已入账资金。
  卖单走普通的提交路径（STOP、监控、交易时段、同一时间一笔、每日卖出次数），过期决策不会撤掉它们，过时会改价。
  取消赎回会阻止新的筹资卖单，已挂卖单会请求撤单，已成交部分留在基金里。
  获取报价后、发送给券商前，会再次核对对应的赎回请求，以及 STOP、监控、交易时段和订单授权期限；
  已确认未发送的订单释放预留状态，同时保留本次尝试记录。Paper 订单已经发送后，撤单与成交以券商回报为准。
  本地模式还会在接受订单和每次成交的事务内核对：请求已取消的筹资卖单停止，赎回排队时旧买单和停泊买单停止，
  不等待公司行动行情恢复。已成交部分保留，重启后仍从账本核对同一个请求编号，另一笔赎回不会重新授权旧卖单。
  正常卖出和止损仍可执行，单纯排队的申购不会阻止买入。
  处理期间暂停 AI 买入和现金停泊；卖出、止损、研究和决策照常。卖出次数用完、拿不到报价等原因卡住时，
  每天每种原因发一次 Telegram 说明，不会悄悄停着。赎回（连同等待中的请求）不能超过基金最近估值的 95%，
  登记时就会拒绝；要清盘请先 STOP 再人工处理。
- **风控状态跟着基金走，不跟着这笔钱走**：回撤峰值和当日起始净值按同样比例缩放，所以赎回不会触发 8% 回撤锁或
  当日亏损暂停，申购也不会掩盖亏损。赎回卖出也不计入 AI 的换手。
- **收益都按单位净值算**：报告的累计收益、回撤和夏普，记分卡和净成本计分板的逐日收益，周报，复盘的当日收益，
  日度归因，以及决策后续表现，都已剔除申购和赎回；起止净值仍是美元，含这笔钱。
  基金经理在 `fund_capital` 里看到份额、单位净值、等待中的请求和最近的申购赎回，并被告知这些不是盈亏；
  `operator_mandate.capital_usd` 显示它现在实际管理的本金，而不是 `.env` 里的旧数字。
  配置变更时若请求队列已满，基金先处理队列中的请求，再登记目标。状态页会同时展示目标本金和预计划转金额。

## 分钟级盯盘与 AI 择时

AI 不需要每分钟被调用。基金经理在每次复核时为每个目标可选地给出执行价位，并可设置价格提醒：

| 字段 | 含义 | 执行者 |
|---|---|---|
| `entry_limit` | 只有卖价 ≤ 该价才买入（等回调） | 确定性代码，每分钟检查 |
| `stop_loss` | 买价 ≤ 该价时清掉该持仓 | 自动卖出，无需审批 |
| `take_profit` + `take_profit_weight` | 买价 ≥ 该价时减到指定权重（默认 0） | 自动卖出，无需审批 |
| `alerts`（`above`／`below`／`reason`） | 价格穿越时提前唤醒 AI 复核 | 只唤醒，不下单 |

盯盘循环每次策略迭代运行（本地／Paper 默认 30 秒，可配置），不调用模型：
- 止损／止盈触发后立即挂**可成交的**卖出限价单：限价为买价下方 `execution.protective_limit_buffer`（默认 0.5%，
  普通调仓只有 0.1%），并在 `execution.protective_reprice_seconds`（默认 60 秒，普通单 180 秒）后未成交就撤单，
  按新报价重挂，直到减到目标，不会“触发一次就忘”。保护性卖出优先保证离场，而不是争取价格。
  同一决策内被止损的证券不会被重新买回，等 AI 下一次复核再决定。
- 有挂单（例如一笔买单在等成交）时，止损／止盈照常检测；需要卖出时，先撤掉本应用的非保护性挂单，让止损优先。
- 止盈减仓的股数在触发时一次算定，价格继续上涨也不会一股一股地追着卖；减仓完成后，剩余股份的**止损继续有效**。
  减仓还没卖完时价格跌破止损，会改为全部卖出。
- 买价已经跌到 AI 自己给出的 `stop_loss` 或以下时，不会再新买入该证券（记录 `stop_breached_no_buy`），
  已挂出的该证券买单会立即撤销（记录 `buy_canceled_stop_breached`），不等待 180 秒改价周期。
- 价格提醒、持仓或目标证券相对本决策首次观测价的波动达到 `execution.review_on_move`（默认 3%）、
  市场进入压力状态时，会把下一次 AI 复核提前；提前复核仍遵守最短复核间隔、失败退避和每日模型预算。
  基金经理在 `watch_triggers` 中看到被唤醒的原因。
- 每次新的 AI 决策替换全部旧价位和提醒，**正在执行的止损／止盈卖出除外**：止损触发后提前唤醒的新决策不会中断它，
  卖出完成前不买入该证券；新决策为该证券设的价位在卖出完成后才生效。
  决策中的价位同样受校验：止损须低于入场价和止盈价，止盈须高于入场价（否则买入后立刻触发止盈，白付价差），
  `take_profit_weight` 须低于目标权重。

价格提醒是只读观察，可以跟踪交易名单外的指数或其他行情符号；行情源须提供带源时间的新鲜正价格，
不要求指数具有成交量或可交易盘口。提醒触发只唤醒 AI，不能让该符号成为合法目标或订单。
行情缺失、过时或时间在未来时记录 `price_alert_unavailable`，保留提醒等待重试。
同轮其他证券的读取使先取的报价过期时，提醒会重新取一次源报价并校验；仍不合格则不触发。
交易报价使用读取完成后的时钟校验，避免把请求期间新到的真实报价误判为未来。

本地模式另外复用原生每 5 秒的撮合轮询，开市时约每 30 秒独立重估授权资金组合；账本或成交发生变化时立即尝试刷新。
这条估值路径不调用模型，即使研究员或基金经理仍在运行，也会按现金、应收款与实际持仓市值更新 `account` 事件和报告。
保留资金、账户外持仓和现金等价物遵循原有分仓规则；报价期间账本变化时整次结果作废重试，避免混用成交前后的现金与持仓。
开市时必须满足源时间新鲜度。收盘时按交易日历（含节假日、夏令时和提前收盘）优先取最后一根完整常规时段分钟线，
若其缺失或分钟接口退避，则独立读取**同一交易日已完成的未复权日线收盘价**。只在该日实际收盘之后使用，
不能用昨日收盘、未完成日线、盘后成交或更早分钟线代替；日线来源不会成为模拟成交的分钟线。
现金和持股账户都只保存一次收盘估值，后续轮询、重启、复盘沿用它；下一次开市才恢复相对更新时间。
两种有效收盘来源均缺失时保留上次有效估值并披露缺失，不能把盘中旧价称为收盘价；
估值的逐标的报价记录 `price_kind`、源 K 线开始时间、所属收盘和实际取得时间，迟到行情仍按取得时刻入账。
已验证的收盘报价按证券和收盘时刻保留，后续余额查询复用原价格及取得时间，避免整晚重试缺失的分钟线；
仅保留最近 60 个键，下一交易日的收盘必须重新取得证据。申购／赎回仍须开市和新鲜估值，盘后补齐收盘不会执行排队中的资金流。
新日线响应若首次带来拆股或分红，使用同一响应中的公司行动按原有规则核对并更新账本，随后重试整次估值，
不能用读取前的股数、现金或应收款配合新收盘价冻结净值；已有的迟到拆股／修订动作核对约束仍然有效。
`status.json.valuation_error` 和状态输出说明原因。账户区块另显示估值行情最早时间，不能将快照时间当作行情时间。
数据员下载研究数据本身不等于更新账户净值；独立估值目前仅用于本地模式，Paper 仍由券商账户观测更新。

这让“盯盘”成本接近零，而择时（入场价、止损、止盈、何时复核）仍由 AI 决定。
报价优先使用带源时间的新鲜成交（推送或同一 Yahoo 响应的最新成交元数据），否则回退已完成分钟线。
分钟缓存跨过开市时的整分钟边界时重新读取，避免缓存 TTL 尚未到期、但上一条报价已超过 60 秒的误拒绝。
若提供方仍落后，过期分钟的缓存重试间隔缩短至 5 秒，同一序列的并发请求仍共用一次下载；
不会延长源时间上限或把接收时刻当成源时间。价位提醒缺行情的 Telegram 消息明确说明仅跳过本次提醒检查。
模拟成交仍等待提交后新完成的分钟线，可能延迟一到两分钟。

## 每日归因：钱从哪里来（代码计算）

盘后复盘前，`attribution.py` 按已完成收盘价算出当日归因，放进复盘上下文的 `attribution`，并保存在复盘记录和日报的
“当日归因”一节。复盘被要求以它为准，不自行估算。起点是该交易日之前最后一次账户估值（持仓、现金和短债 ETF），
权重 w_i = 持股 × 前一交易日收盘价 / 前一估值的净值，r_i 是当日收盘对收盘的收益：

| 部分 | 计算 |
|---|---|
| 市场 | w_i × β_i × r_SPY；β 只用前一交易日及以前的收盘价估计，样本不足按 1 计并列出 |
| 选股 | w_i × (r_i − β_i × r_SPY)，另按风控分组汇总 |
| 现金等价物 | 短债 ETF 的权重 × 其价格收益（分红不在价格里，会落到“未解释”） |
| 当日交易择时 | 买入：数量 × (收盘价 − 到达价)；卖出：数量 × (到达价 − 收盘价) |
| 执行滑点 | 买入：数量 × (到达价 − 成交价)；卖出：数量 × (成交价 − 到达价)；到达价取提交时观测的买入 ask／卖出 bid，缺失时择时与滑点均为未知 |
| 费用 | 负的已记录交易费用；费用未知的成交列出，不按 0 计 |

各部分都除以前一估值的净值。观测收益来自账户估值，它与各部分之和的差额单独列为“未解释”（收盘前估值、分红、拆股、
取整等），不强行配平。缺收盘价的持仓或成交列在 `unavailable`，状态为 `partial`；没有前后两次账户估值时为 `unavailable`。
同一订单既有成交回调又有券商对账记录时，只用对账记录（整笔订单），不重复计算。

### 数据保留

原则：系统决策、复盘和策略优化要用的数据一律永久保留；只清理没有任何程序再读取的数据。

| 数据 | 保留 | 原因 |
|---|---|---|
| 账本（现金、持仓、委托、成交、公司行动、初始资金） | 永久 | 账务校验每次从开户起完整重放，缺一条就对不上账 |
| 决策、审批、下单、盘前研究、盘后复盘、研究想法 | 永久 | 策略记忆、预测打分（最长 20 个交易日）、周报和影子对照要用 |
| 记分卡、因子检验、影子决策、学习评估、模型调用记录 | 永久 | 因子检验总次数是 DSR 的分母；模型费用和失败率统计 |
| 应用调用输入与返回结果（`fund_evidence_calls`／`fund_evidence_objects`） | 永久 | 新调用按编号保存提示、上下文、Schema、应用源码和已安装依赖版本；压缩去重，随 SQLite 备份 |
| 通知 | 永久 | 验收统计 STOP 和崩溃次数，也是告知过你什么的凭据 |
| 净值快照和基准价 | 永久 | 日收益、夏普、PSR/DSR、Newey-West alpha、超额收益和归因；盘中快照还用于最大观测回撤和当日复盘 |
| 迭代开始／结束等运行记录 | 永久 | 验收用每个交易日的迭代次数计算运行覆盖率 |
| 普通资讯（`fund_news`） | 30 天 | 决策只看最近 24 小时，突发检测只看几分钟；触发复核时，复核记录已经保存了标题和来源 |
| 重要资讯（申报文件、宏观发布、突发） | 180 天 | 同上，多留一段便于回查 |
| 模型调用追踪文件（`cache/agent_runtime/traces/`） | 30 天 | 只供排查问题，没有程序读回；每次调用一个，是最大的磁盘占用 |
| `events.jsonl` 月度归档 | 12 个月 | 没有程序读取；SQLite 账本里仍有全部事件 |
| 数据员的盘中行情存储 | 3 天（原有） | 次日即可从数据源重建 |
| 日志、备份 | 20 MB × 5 份、14 份（原有） | 备份另有磁盘空间保护 |

清理随每日备份自动执行（备份之后；空间不足跳过备份时也执行）。手动预览或执行：

```bash
bash scripts/fund-logs.sh prune
bash scripts/fund-logs.sh prune --apply
```

不带 `--apply` 只列出将删除的条数和大小，不做任何改动。删除的行在数据库文件里留下可复用的空间，
新数据会先用它们；文件本身不会变小。要回收磁盘需要 VACUUM，它需要约一份账本大小的临时空间并独占数据库，
本程序不会自动执行。智能体的记忆文件（`*_agent_memory_*.parquet`）和行情缓存不在清理范围内。

### 调用证据归档与只读校验

单机和免费行情也能保留当时模型实际收到的应用输入。新调用在进入原生 Agent 之前，将任务提示、各角色的
系统提示与设置、输出 Schema、逐项上下文、调用参数、现有 `prompt_version` 及调用函数代码摘要保存到当前账户的
`state.sqlite3`。同时保存进程首次归档时磁盘上的应用 Python 源码和关键依赖的已安装版本；不读取环境变量、密钥文件或完整运行配置。
返回后保存原始回答、已解析对象、提供方报告的用量和模型身份；回答是否合格、是否采用仍以原有校验／采用事件为准。
输入采用规范化 JSON（非 JSON 值沿用账本的文本转换），不是 Python 对象的二进制快照。

每个组件用 SHA-256 标识并 gzip 压缩，相同价格历史、提示或源码只存一份。每个未压缩组件上限 16 MiB；
写入失败或超限时，开始／结束事件只记异常类型与归档不可用，不增加模型调用、费用、重试或研究／交易限制。
没有返回结果的失败调用仍保留输入和原有未知用量记录。归档独立于 30 天清理的原生 trace，自动进入现有 SQLite 备份，
不依赖新服务器、数据库服务、付费数据或新的推理调用。长期磁盘用量仍会增长，应沿用现有空间监控和备份管理。

```bash
bash scripts/fund-logs.sh evidence
bash scripts/fund-logs.sh evidence <call-id>
```

也可跨平台运行 `python -m scripts.autonomous_fund.run evidence --run-dir <account-directory>`；
加 `--call-id <call-id>` 只展开所选账户中该编号的完整应用输入与返回结果，不会退回到其他账户或其他调用。
默认只读检查完整性和覆盖率，不打印提示、上下文或源码；指定编号的详细输出属于私人账户资料，应按账本同等保护。
`verified` 表示已记录调用的输入／结果哈希及事件引用一致；`partial` 列出旧输入、未完成或归档失败等缺项；
没有可校验输入为 `unavailable`。这三种诊断退出码为 0，完整性错误 `failed` 退出码为 2。
没有编号的旧 `agent` 记录另列条数，不能当成独立调用数；不从当前提示或新下载行情补造旧输入。

归档范围止于应用与原生 Agent 的交界：不包含原生记忆、SDK 合成的最终提示、后续完整工具响应或提供方内部状态。
源码是首次归档时的磁盘版本，不认证所有已加载 SDK 与磁盘文件一致。哈希可发现损坏及引用错配，不能防止恶意者同时重写
数据库与全部引用；也不代表可以精确重跑模型、行情已获独立验证或策略具有盈利优势。同机备份仍不能抵御整机磁盘丢失。

本地验证包括 20 项归档专项用例，以及合成行情、脚本模型经过原生引擎的 10 次调用：输入和返回结果均通过校验，
SQLite 备份恢复后逐调用读取一致且保留 STOP。这些是应用证据保存与恢复的功能测试，不是 Ubuntu 部署或投资效果验收。

### 本地账务校验

`bash scripts/fund-logs.sh audit` 在一个只读数据库快照内，逐笔重放初始资金、买卖、费用、拆股和分红应收款，
核对现金、股数、加权买入均价、订单累计成交金额／费用、审计事件，以及持仓报价与净值的加总。
新成交在同一事务记录所用 OHLCV、点差、滑点、手续费和参与率参数；校验失败会回滚本次成交。
提交时的市场报价单独保留源时间，委托限价只用于执行约束和追价控制，不能冒充到达报价。

读取账户、下单、估值前检查账本一致性；发现差异时不向账户工具和报告输出争议净值／成交明细。
只读研究仍可继续，AI 上下文明确标出校验状态，不能把失败的账本或缺失的费用、滑点当成已证实事实。
旧账本缺初始余额凭据、成交分钟线或到达报价时返回 `partial` 并列明缺项，不补造历史证据；
`verified` 证明已记录账务与执行假设内部一致，不证明行情供应商数据等于交易所实况。
命令退出码：`0` 完整通过，`3` 证据不足／不适用，`2` 不一致或账本不存在。命令不修账、不下单、不调用模型。

高频账户读取、下单和成交前后只扫描资金、持仓、订单、成交、费用和公司行动等权威账目，
结果标为 `scope: ledger`；每次仍重新核对，能发现其他连接修改和事务内尚未提交的差错。
历史净值快照由完整 `audit`、报告和研究审计检查，标为 `scope: ledger_and_observations`，
不再把整段净值历史放进每次下单的检查中。监控成交通知和指标最多检查最近 200 个候选快照，
逐个验算，缺少合格快照时显示待更新／不输出该指标，不把坏快照当成账户事实。
因此交易检查的耗时不再随历史净值快照数增长；仍随实际委托、成交和公司行动数量增长。

账目重放的开销与记录数成正比，只在需要它的地方运行：
- 每笔订单、成交事件只解析一次；分红应收款按证券预先整理的股数变化计算，
  不再为每次分红重新解析全部成交（以前随“分红次数 × 成交笔数”增长：5,000 笔成交时一次约 2 秒，现在约 0.25 秒）。
- 本地撮合每 5 秒轮询一次。只有到了 30 秒估值时间或账本有变化，才重放账目并写入新估值；
  读取余额只核对一次（以前两次）。
- 分钟线价格达不到限价的委托（挂单等待的大多数分钟）只记下这根分钟线已检查，不估值、不重放；
  真正可能成交的分钟线仍在成交前后完整核对。
- 休市后，同一收盘的已保存收盘估值每个进程只查找一次；缺收盘分钟线时每 30 秒重试估值，不再每 5 秒扫描全部历史净值。
- 监控只有出现新成交时才为成交通知重放账目。
- 历史净值快照逐条检查、不整体载入内存：以前一年约 20 万条快照会在每次审计时占用数百 MB 到数 GB。
  研究审计（AI 上下文中的 `ledger_audit`）在同一进程内每条快照只检查一次，之后只检查新增快照，
  结果与完整审计相同；资金事实每次都完整重放。手动 `audit`、报告和每日复盘仍检查全部快照，
  因此进程运行期间有人改动旧快照时，由这些完整审计发现。
- 报告（交易进程每 5 分钟生成一次，Telegram /status 和 `fund-logs.sh` 也会调用）和基金经理决策上下文里的
  “后续表现”不再解析、保留每条净值快照和基准记录：所有快照只读出时间、净值和收盘标记，用于排序、
  收盘规则、日曲线和观测回撤；完整内容只读取需要展示的快照（每个交易日最后一条、第一条和最新一条）。
  后续表现只用纽约时间每天最后一条快照、最早一条和对应时刻的基准。结果与原算法逐项相同；
  10 万条快照（约半年）时，一次报告从约 730 MB、6.5 秒降到约 140 MB（其中数据约 36 MB）、2.5 秒。
- 盘后复盘（每次启动、开盘前和收盘后都会检查一次）先确认该交易日是否已复盘，已复盘就直接结束；
  未复盘时只读取它用到的记录：该交易日的全部事件、前一交易日最后一次账户估值、基准与这两次估值对应的价格、
  当日盘前研究和已保存的复盘阶段，以及每个有账户／决策／成交记录的日期各一条（用来确定交易日）。
  输入与读取整个账本时逐项相同；10 万条快照时从约 630 MB、5.3 秒降到约 9 MB、2.9 秒。
- 周报只保留每天最后一次净值和每个基准每天最后一个有效价格，10 万条快照时从约 500 MB 降到约 5 MB。
  彩排只读取本次运行新写的记录，不再多次载入复制来的整个账本。
- 监控每 10 秒写一次指标文件，以前每次都完整重放账目，只为决定是否输出净值指标。现在资金事实
  （现金、成交、订单、公司行动）有可见变化时立即重新核对，否则最多每分钟核对一次；交易进程在每次下单和成交前后的核对不受影响。
- 监控每次轮询要查“哪些复盘已发日报”“哪些周已发周报”，以前每次都解析全部通知；现在通知类型有专门索引
  （`events_notification_kind`，交易进程下次启动时自动建立），一年的通知量下每次轮询从约 130 毫秒降到约 14 毫秒。
  日报只读取它列出的成交、审批、盯盘和通知记录，不再解析全部事件。
- 一条内容损坏（不是合法 JSON）的通知以前会让监控每次轮询都失败（游标随失败回滚，永远卡在这一条），
  之后的所有通知（包括 STOP 告警）都发不出去。现在这条记为 `suppressed`（`last_error` 为
  `malformed_notification_body`），不发送也不丢失，后面的通知照常发送；重启判断也跳过这类记录。
  报告、复盘、日报／周报与 JSONL 导出将这类通知显示为 `malformed_notification_body` 异常记录；
  `report.json` 的 `malformed_notifications` 给出数量，JSONL 导出保留事件序号和时间。
  原始内容仍留在 SQLite，后面的事件继续处理。只有通知允许这种投影；资金、成交和研究记录解析失败仍报错。
- 读取不含账户估值的记录（记分卡、影子决策）时不再顺带核对全部净值快照（核对只影响账户估值）；
  当日归因只读取前一交易日最后一次和当日最后一次估值的完整内容。逐条核对净值快照时每个数值只转换一次，
  10 万条快照的完整核对从约 1.9 秒降到约 1.0 秒，结果相同。
- 每条净值快照里附带的账务校验结果改为只存结论（状态、范围、计数、缺项和错误／警告代码），不再重复存整份
  重放账本（现金和每个持仓，快照本身已有）；需要完整重放时运行 `fund-logs.sh audit`。每多一只持仓，每条快照少约 60 字节。
- 读取现金、持仓、余额时的账务核对：LumiBot 每次迭代要读几十次，以前每次都从开户起重放全部成交
  （启动加一次迭代共 43 次）。现在账本相关的表和事件上有 SQLite 触发器，任何连接、任何工具对它们的
  新增、修改、删除都会让 `ledger_version` 加一；版本没变就直接用上次的核对结果，变了就重新完整重放
  （同一场景 5 次）。核对结果和以前完全相同，包括其他连接或手工改库后的下一次读取；有人删掉触发器时不再复用，
  每次都完整重放；核对失败的结果从不复用。下单和成交事务里尚未提交的写入仍在同一事务内直接核对。
- 交易进程用来去重通知的内存表以前永不清理（每条不同的通知一项），现在只保留仍可能抑制重复的项。
- 每次迭代取“待处理的重要资讯”时，以前在写事务里两次扫描全部资讯；现在有专门索引
  （一年约 25 万条资讯时从约 260 毫秒降到 0.1 毫秒）。监控投递队列也按状态建了索引。
  发送时先筛选已经到期的待发／重试记录，指定单条测试消息时也先应用选择，再最多载入两条正文；
  不再把全部积压正文载入 Python。到期判断保留时区偏移和微秒精度，未到期的发送租约不会被提前重发。
- 真实通知投递在每次认领时重新取时钟；报告构建失败和 HTTP 失败的重试间隔从失败／响应之后计算，
  网络耗时不会吃掉提供方要求的等待时间。发送前重新核对收件人、当前全局退避和投递权，并续租；
  迟到的构建失败或 HTTP 结果只可更新自己仍持有的租约，不能覆盖另一投递者的较新状态。
  并发失败保留较晚的共享退避截止时间。这些检查保护投递状态；网络结果不明确时仍不能保证远端只收到一次。
- 未来时间的通知会进入持久队列并等待自身时间到达，不再挡住后续已到期的通知或监控 STOP 告警；
  未来观测不能作为抑制当前同文通知的去重依据。无效／无时区的通知时间记为
  `malformed_notification_timestamp` 并抑制该条，保留原始事件，后续正常通知继续处理。
  去重遇到旧通知时间损坏时，也不会用它抑制新通知。资金、成交等金融证据的校验保持严格。
- 每日备份在删除旧快照前检查源账本的 SQLite 完整性和目标目录是否已存在；空间不足时最多删除本次轮换允许删除的旧快照，
  并在新快照完成前至少保留最新一份已完成快照。`--keep 1` 无法同时容纳新旧两份时跳过备份。
  复制失败会关闭连接并清理本次不完整目录；进程硬退出留下的 `.incomplete` 目录不作为可恢复快照计数。
  SQLite 连接在成功和失败后都显式关闭，避免 Windows 文件占用。

只有资金、股数、成交、费用等账本事实不一致才阻止执行并由监控停交易。
旧记录缺滑点凭据，或历史净值快照加总有误，只标为 `partial`：错误快照不再用于报告、通知和复盘，
不会阻止当前账本正确的买卖；缺失统计仍不能支持验收通过的结论。
短暂行情中断、过时或源数据无效时，订单保留，等待下一次合格行情自动重试，不因缺价写入永久 STOP。
有效期、限价、风控与完成分钟线要求继续适用；单笔委托缺行情不阻塞另一证券具备可靠价格的卖单。
新增买入仍需可靠的全组合估值，公司行动尚不能核实时也会等待，避免用拆股前价格或未知风险敞口成交。

**被收购或退市的持仓**：持有的股票被现金收购或退市后，数据源不再给它新的日线，账户无法估值，估值和新的交易会暂停
（不会猜一个价格）。每天收盘后的复盘检查所有持仓：数据源连续超过 3 个完成的 NYSE 交易日没有给出新的日线
（读取失败不算证据），就发通知 `holding_without_market_data`（每只每天一次），写明最后一根日线的日期。
模拟券商（Alpaca paper）自己处理结算；本地账本需要你查明实际结算金额后，**先停止基金**再运行：

```bash
bash scripts/run_autonomous_fund.sh settle-position --run-dir <账户目录> --symbol <代码> --cash-per-share <每股实收现金> --reason "<发生了什么>"
```

破产退市一般为 0。命令只用于本地账本，持有运行锁（基金运行时拒绝），该股票有未完成订单或未结束的下单意图时拒绝，
金额必须是 ≥ 0 的有限数。持仓数量清零，现金增加“股数 × 每股金额”，记一条 `local_actions`（`代码:日期:cash_settlement`）、
一条 `local_corporate_action` 和一条 `operator_position_settled`，并在同一事务里运行严格对账重放：重放不能复现账本时整笔回滚。
严格对账也会重放结算，金额被改动会报 `corporate_action_amount_mismatch`。结算日期晚于上一个收盘时，
那个收盘的收盘估值不再重建，等下一个收盘。换股收购（用股票支付）不支持：按收购日的现金价值结算，或人工核对。

## 周报

每个 ISO 周的最后一个交易日（按 NYSE 日历，节假日照算，例如耶稣受难日那周是周四）复盘完成后，独立监控向 Telegram
发一份周报附件（`weekly-YYYY-Www.md`，每周一份，只为最近 7 天内完成的复盘补发）。纽约 16:00 收盘后复盘通常要几分钟到半小时，
所以北京时间一般在周六早上收到：美东冬令时约 05:00 之后，夏令时约 04:00 之后。

那天没有复盘时（交易进程没运行、STOP 持续到收盘后、或复盘出错）：

- 那天有交易记录的，交易进程在下次启动或开盘前一小时补做复盘，补做后照常发周报。
- 仍没有的，下周第一个交易日开盘后，用本周最近一次复盘发周报，标题注明“本周最后一个交易日没有复盘”。
- 本周一次复盘都没有，就没有这一周的周报。

`bash scripts/fund-logs.sh status` 显示最近一份周报和它的发送状态、上周的周报为什么还没有、下一份什么时候发。
`bash scripts/fund-logs.sh weekly` 随时打印本周到目前为止的周报（用最近一次复盘生成，只打印，不发送）。

日报和周报按所选复盘的完成时刻冻结行情和费用。完成时间先于写入时间时，周报仍按记录编号纳入所选复盘本身，
包括其归因和最新备忘；不会因此纳入后续复盘、估值或调用。账户盈亏保留复盘原始输入窗口，日报另列截止前最新观测，
普通观测与带收盘凭据的估值分别标注。资金比例由账户数值计算：现金已经包含系统现金等价物，
自由现金需减去这部分；风险证券、系统现金等价物、自由现金和应收合计为净值，不叠加 AI 自述比例。

周报同时列账户超额和扣已知模型费后超额（模型费按期初净值折算）；未定价调用使后者只能作为上界。
交易费用和滑点已包含在账户收益中，不重复扣除。该周度扣费值未扣数据费用；完整系统净成本口径见基金记分卡和经济对照。
日报仅从成交记录展示当时的模拟费率、价差和滑点，不把当前配置冒充历史参数；含摩擦的模拟成交价可能超出原始分钟区间。
盯盘部分汇总各类触发数量，重复新闻复核仅列最近 20 条，保护性触发和价格提醒全部保留，完整记录仍在账本。

上述规则对 local、paper 和历史模式的可选基金报告一致适用，不依赖策略、账户或证券名称。
`tests/test_autonomous_fund_report_consistency.py` 用合成账本验证完成与写入的时间差、未来记录排除、重复现金计算、
即时读取记分卡和重试恢复；这些本地证据不代表服务器已更新或真实投资能力已通过验收。

周报、日报或其他通知生成失败时，只有这一条重试，后面的通知（包括停止告警）照常发送。
试 3 次仍失败，就改发一条中文提醒，错误和 traceback 写进服务日志（`bash scripts/fund-logs.sh errors`）。
2026-11-08 之前，生成失败的通知会一直排在队首重试，后面所有通知都发不出去。Telegram 限流或网络故障仍会暂停整个队列，避免越限越久。

## 复盘记分卡：AI 自我优化的客观反馈

为避免 AI 只凭叙述“自我感觉良好”，复盘闭环加入两张只用**已完成收盘价**计算的记分卡（`scorecard.py`）：

- **预测记分卡**：每次盘后复盘可给出最多 10 条可证伪预测（证券、`up`／`down`／`outperform`／`underperform`、
  1–20 个交易日、基准、对应的假设）。到期后自动打分，按假设汇总命中率；未到期为 `pending`，缺数据为 `unavailable`，不估算。
- **决策记分卡**：每个交易日最后一个 AI 目标组合，从决策获接受后的首个实际收盘起算 1／5／20 个交易日的收益，
  减去**按组合 beta 匹配**的 SPY 收益，得到选股超额收益（`excess_return`）。每只证券的 beta 用起算收盘及此前
  126 个交易日内两边都可观测的连续日收益估计；少于 20 个样本的证券按 beta 1 计并列在 `beta_assumed`。
  这样牛市里重仓高 beta 股票不会被记成“选股能力”。`net_excess_return` 再扣掉交易成本：
  与上一个决策相比的目标权重变化 × 每边 10 个基点（第一个决策从全现金算起）。
  旧口径（同等总敞口）保留为 `exposure_excess_return` 供对比。不含风控缩放，专门衡量 AI 的选股能力。
- **扣掉行业**：扣 beta 之后的超额再精确拆成三部分（相加等于原超额）：`within_sector_selection`（每只持仓相对
  它所属行业里各证券的等权平均，才是真正的选股）、`sector_allocation`（行业平均相对 beta × SPY，押对了行业），
  以及没有行业归属的持仓（宽基、债券、黄金 ETF）的 `unassigned_excess`。行业用风控分组里的 11 个 GICS 行业。
  重仓科技又赶上科技行情时，超额会落在 `sector_allocation`，不会被记成选股能力。
- **决策反复**（`consistency`）：同一证券的目标在 3 个交易日内朝相反方向调整（买了又减、减了又买），中间没有止损止盈，
  记一次反向调整；权重变化不到 1 个百分点不算调整。报告调整次数、反向次数和比例，以及估算多花的成本
  （每次反向约等于反向那部分的一买一卖，按每边 10 个基点）。基金经理在上下文里能看到自己的反复率；
  日报和周报也列出。比例高时需核对改变依据与持有期，不能仅凭反向次数认定每次减仓都不该做；及时纠正错误或降低风险仍可能合理。
- **决策稳定性**（`stability`，`validation.stability_checks_per_session`，默认每个交易日 1 次，0 关闭）：在没有在途订单的空闲轮次，
  用最近一次获批决策的任务提示和策略上下文复问基金经理。通过纠正才获批的决策复用纠正请求。账户状态、运行时间和工具结果仍可更新。
  结果比较证券重合度、仓位差异（权重差绝对值之和的一半）以及是否符合 1 个百分点的一致规则。复问结果只用于打分。
  `noise_ratio` 保留原字段名，表示平均复问差异与近期相邻决策平均调整之比。这个比值同时受运行状态变化和模型回答变化影响。
  记分卡只纳入标有 `input_scope=strategy_request` 的复测记录。跨日或重启后跳过未复问的决策。
  复问只在 local／paper 模式运行，每次多一次调用，并遵守 STOP、调用次数和费用预算。结果进入记分卡摘要（`decision_stability`）和日报、周报。
- **基金记分牌：扣除全部成本后的总收益**（`fund_scoreboard`，`scoreboard.py`，不增加调用）：专业基金经理按扣除全部费用后、
  相对基准的收益考核；基金每天都在付模型和数据费用，不管 AI 买不买。所以现金不是“中性、免费”的选择：现金只赚短债利息，
  费用一旦超过利息，全拿现金就是负收益，而且预期会落后于持有股票的基准。记分牌用已收盘交易日计算（按每个交易日最后的
  账户估值串起来，运营者调整授权资金的区间不计入），给出：成立以来的账户收益（已扣交易费用和滑点，含现金利息）、模型和
  数据费用（金额和占起始资金的比例）、扣除这些费用后的净收益、同期各预设基准（SPY、60% SPY + 40% SGOV 的风险匹配基准）
  的总收益和净超额、最近 5 个交易日的费用节奏折合每年占资金的比例（跑赢基准每年至少要多赚这么多）、现金等价物的年化
  收益和全拿现金扣费后的年化收益。没定价的模型调用不当作免费：净收益只扣已定价的部分、注明未定价次数，并标为上限。
  记分牌进入基金经理决策、开盘前研究和收盘复盘的上下文，并写进日报和周报。基金经理的目标改为“长期、扣除全部成本后、
  跑赢预设基准的风险调整收益”：没有交易义务，但持现代替接近基准的市场敞口是一种押注市场下跌的主动选择，要像买入一样
  给出证据；同时不得为了赚回已花的费用而冒险（换手成本也算在内）。反方审查在组合或计划大部分是现金时，也要论证
  “继续持现”的代价。费用只用来评价扣费后的结果，不是让 AI 省着用：提示词明确要求不得为了省模型费用而减少研究、工具使用或分析深度，也不得因此拉长复核间隔；花费上限只由运营者设定（`model_budget`，每日费用上限默认不设）。提示词因此改变，`prompt_version` 会变一次。
- **扣费后的基金净值和收益**（`scoreboard.accrued_costs`）：AI 调用费由运营者另付，不从券商账户扣；交易手续费和滑点
  已经在账户净值里。为了让人和 AI 都看到“扣掉所有成本后到底赚了多少”，又不破坏账户对账和风控，采用“每天计提、不实际
  划款”的口径，和专业基金每日计提费用、公布扣费后净值的做法一致：
  - 每条带账户快照的通知（开盘、决策、成交后账户更新、状态查询）在账户净值下多一行“扣除 AI 费用后的基金净值”
    ＝账户净值 − 成立以来已定价的模型费用 − 数据费用（`performance.data_costs_usd_per_month` 按有记录的交易日计提），
    并注明未定价的调用次数（不当作免费，实际更低）。
  - 每日归因另列当天的 AI 和数据费用（`fund_costs`）和扣费后当日收益（`net_return`）；它们不放进 `components`，
    因为各分量解释的是账户自身的收益，账户并不支付这些费用。
  - 周报“本周收益”下面多一行本周 AI 费用和扣除后的本周收益。
  - **实时费用反馈**（`fund_costs`）：从首日开始，研究、反方复核、基金经理决策和纠错重试各自在发起前读取费用，
    不依赖已收盘记分牌的缓存。经理能看到本轮研究和反方复核刚产生的费用；盘后经理能看到刚完成的研究费用。
    上下文保留费用截止时间、账户原始估值时间、已知模型／数据费用、未定价次数，以及账户净值减去已知费用的参考净值。
    账户估值与费用可能来自不同时刻，两者时间分别列出；未提供账户估值时不编造净值。本次尚未完成的调用费用不预估成事实。
    这是按运营者配置单价和返回 usage 算出的估算，不是供应商账单；只有输入和输出 token 数均明确时才定价，
    缺项或非法计数保留为未知，明确的零 token 则可以是零费用。原始已保存上下文不被后续费用更新改写，
    稳定性复问仍复用接受决策时的原始输入。
  - **历史数据费率**：按纽约日期去重，在该日第一条基准观测时按当时已生效的启动配置计提月费的 1/21。
    同日重启不会重复计提或重定价；调高、调低或补填费率均不改写旧日成本。已未知的历史费用继续未知，
    其他日期已知费用仍扣除；结果注明仅为净值／净收益上限。这是有基准记录日期的分摊口径，不是供应商实际账期。
  - **收益口径**：模型／数据费用没有实际从券商扣款，不能假设这部分资金已停止产生账户收益。连续、无资金调整的
    已完成区间里，记分牌净收益等于账户累计收益减去区间累计已知费用占起始账户净值的比例；例如账户始终 10,000 美元，
    两个区间各支出 100 美元，净收益是 −2%，不是按逐日模拟扣款复利得到的 −1.99%。资金调整或缺失区间仍按原有规则排除，
    区间按各自起始账户权益换算至同一比较基准；验收统计采用同一计提算法。记分牌只比较其列出的完整收盘区间，
    不覆盖首个收盘之前或最新收盘之后的费用；`fund_costs` 才是截止本次请求的累计费用。
    现金是否亏损取决于实际利息和成本，股票基准也可能下跌；不得因为费用已花而被迫买入，或因此减少研究、工具和分析。
  - 基金层面的收益（记分牌、投资验收、和基准比较）都扣这些费用；单笔决策的记分（选股是否跑赢）只扣交易成本，
    衡量的是本事，不摊固定的 AI 开支。
  - 可用资金、仓位大小、单日亏损和回撤硬锁仍按账户净值，不受这些费用影响。
  - **费用提醒**（`model_budget.cost_alert_share`，`.env` 的 `FUND_COST_ALERT_SHARE`，默认 0.02）：收盘后，累计的
    AI 和数据费用每达到起始资金的 2%、4%、6%……各通知一次（`fund_cost_alert`），附账户收益、扣费后净收益和当前
    花费节奏。只提醒，不停止交易；要限制花费用 `FUND_MAX_DAILY_COST_USD`。
- **大跌日表现**（`down_days`，不增加调用）：平均数会掩盖最要紧的日子——基金平时看起来不错，但市场大跌时可能跟着一样跌。
  记分卡用每次收盘复盘里代码算出的当日归因（基金收益、基准收益、市场部分＝贝塔×基准、选股、择时），把基准单日跌
  2% 以上的交易日单独拿出来（对照：涨 2% 以上的日子、其他日子），给出：下跌捕获（这些日子基金收益之和 ÷ 基准收益之和，
  60% 表示只跌了市场的六成，负数表示市场跌时反而赚钱）、上涨捕获、大跌日开盘时的有效贝塔比其他日子低多少（降低说明
  风险已提前减了；天数少时可能只是运气）、当天选股和择时贡献（某天未知的部分单独计数，不当作 0 相加），以及大跌日
  触发的止损/止盈总次数、可估值次数，以及按触发时买一价估算的下一交易日价值。少于 3 个大跌日时标为样本不足。
  大跌日统计覆盖全部复盘记录及对应日期的保护触发。
  它是复盘证据，不是交易规则。结果进入基金经理的记分卡摘要和日报、周报。
- **超出历史的市场预警**（`market_history_bounds`，`history_bounds.py`，不增加调用，不改任何限制或订单）：风险模型的
  预期损失和相关性用最近 `quant.es_lookback_days`（默认 252）个交易日估计，记分卡和因子检验用基金手上的历史（约两年）。
  遇到历史少见的行情时，风险估计可能失准。每个已收盘交易日，代码比较四个量与它们的
  历史值：基准近 20 日年化波动率（高于此前任何 20 日区间）、基准单日涨跌（比此前任何一天跌得或涨得更多）、基准从历史
  最高收盘的回撤（比此前任何时点更深）、可交易股票之间近 20 日平均两两相关性（高于此前任何区间；只用 20 日数据齐全的
  股票，少于 10 只时不计算；相关性接近历史高位意味着分散化失效）。每个量分别与风险模型窗口内的旧值
  （`beyond_risk_window`）和全部历史（`beyond_history`）比较，并给出历史分位；历史少于 81 个交易日时为不可用，
  不会说成正常。结果放进基金经理决策、开盘前研究和收盘复盘的上下文；超出的量发生变化时（新出现或回到范围内）
  各发一次通知（`market_out_of_history`／`market_back_within_history`）。通知列出所有越界指标，行情重试到期或质量判定改变时刷新缓存。
  长时间的危机不会每天重复。它只是提醒：
  需要更保守时由操作者手动收紧风险设置或 STOP。历史压力情景（2008、2020 等）仍照常计入风险计算。
- **提示词版本**：系统提示词、输出结构和模型名的摘要（`prompt_version`，12 位十六进制）写进启动记录和每个
  `decision_validated`；变化时记录 `prompt_version_changed`。决策记分卡按版本分组（`by_prompt_version`），
  改了提示词之后能分开比较新旧版本，而不是混在一起。
- **模型身份核对**（`model_identity.py`）：调用时用的是模型名（例如 `deepseek/deepseek-v4-pro`），名字背后具体是哪个模型
  由提供方决定，可能不换名就换了模型。基金的所有评估都默认基金经理一直是同一个：命中率、超额收益、事件判断的校准、
  决策稳定性，以及因子实验室的知识截止（截止日之后才算干净的样本外记录）。两个信号，按配置的模型名分别记录：
  - **提供方返回的版本**：LumiBot 现在记录每次回答里提供方报告的模型版本（`AgentRunResult.served_models`，
    写进每条 `agent` 事件）。第一次看到的版本是基线，之后出现从没见过的版本就算变化；轮换着用已见过的版本不算。
    回放和缓存命中不计入。很多提供方只回显请求的名字，这时这个信号看不出变化，所以还有第二个。
  - **每日固定问题**：按交易所日历在当日收盘后（包括半日市），对每个不同的模型问同一个问题。只观察模式跳过探测，
    每次调用前检查 STOP 和费用预算。用途记为 `model_probe`，独立计数 `probe_runs`。
    模型从自身知识报告型号、知识截止月份和记得的最近几件大事的月份。无效日期和晚于提问月份的回答会被忽略。
    回答有随机性，所以要多天一致才算变化：前 3 次的
    中位数是基线；最近 3 次的中位数比基线晚至少 3 个月、且 3 次都晚于基线，才算“知识截止推后”；自称型号连续 3 天
    相同、且之前从没这样说过，才算“自称型号变了”。
  发现变化时：记录 `model_identity_changed`，发一条通知；该模型的版本号（epoch）加一，并进入 `prompt_version`，
  所以记分卡、实验登记和事件判断的校准从此按新版本单独统计（记录 `prompt_version_changed`，`reason` 为
  `model_identity`）。从没发现变化时 `prompt_version` 与以前完全相同。交易照常进行，不需要操作。
  因子实验室：如果配置了某模型的知识截止（`factor_lab.model_knowledge_cutoff`），而固定问题显示的知识月份更晚，
  实验室自动改用更晚的日期（只会让干净记录更短、更保守），并通知一次；没配置截止日期的模型仍是“截止未知”，
  固定问题的自报不会被当成截止日期。每天多几次很短的调用（每个不同模型一次）。

运行中的预测、决策、择时和配对实验按 NYSE 日历确定起止日。到期前为 `pending`；已到期但证券或基准缺少端点收盘价时
为 `unavailable`。中间日期缺少行情、但起止日价格齐全时仍可计算该段收益。

**研究想法记分卡**（`scorecards.research_ideas`）衡量研究员有没有可验证的预测能力。盘前研究除摘要和证据外还给出
`ideas`（最多 8 条，多出的截掉；可以为空，表示没有足够把握的机会，提示词明确允许）：证券、方向（`up`／`down`／
`outperform`／`underperform`）、1–20 个交易日、基准（默认 SPY）、论点、优势来源（为什么价格可能还没反映）、催化剂、
证伪条件、把握（0.5–0.95，超出范围按边界记）和引用的证据序号（从 1 起，不存在的序号被去掉并列在
`dropped_evidence_refs`）。研究校验通过后，每条想法写成一条 `research_idea` 记录（`source=research`，编号
`<交易日>#<n>`，记下形成时间、模型、提示词版本和原文）。账本只追加，写入后不再修改；同一交易日的第二次盘前研究
重复同一判断（证券、方向、期限、基准都相同）不会再登记，只按第一次打分。脚本测试的回答不登记。

打分从想法形成后**第一个完整收盘价**起算到 `horizon_sessions` 个交易日后的收盘价：开盘前形成的想法从当天收盘算起，
研究员已经看到的盘前涨跌不计入。起点使用 NYSE 日历的实际收盘时间，包含半日交易日；在收盘时或之后形成的想法，
从下一次收盘开始。期限按 NYSE 日历计算，证券和基准必须有相同起止日的价格。历史形成日的收盘时间有界缓存，
避免每条想法重复构建日历。
结果包括：

- 按把握分组（0.5–0.6、0.6–0.7、0.7–0.8、0.8–0.95）的命中率、平均把握和二者之差（校准偏差），以及 Brier 分数；
- 两个朴素基准：抛硬币（命中率 50%，Brier 0.25）和“总是看涨”（绝对方向的想法都猜涨，相对的都猜跑赢）。
  与“总是看涨”的比较只看两者结论不同的想法（即看跌和跑输的判断），用符号检验；
- 剔除 beta 匹配的基准涨跌后的选股命中率（beta 只用起算日及之前的收盘价），区分“只是赌了大盘方向”和“真的选对了股”；
- 结论 `verdict`：已打分不足 30 条为 `insufficient_sample`；只有命中率同时显著高于抛硬币和“总是看涨”
  （p < 0.05）且 Brier 低于 0.25 才是 `informative`，否则 `not_informative`。期限重叠的想法相互相关，p 值偏乐观，
  只作证据，不控制任何交易。负对照测试：随机方向和随机把握的想法被判为 `informative` 的比例约 0.5%。

基金经理的上下文里有当天登记的想法（`research_ideas`，带 `idea_id`）；决策可以在可选的 `idea_refs` 里引用所依据的想法，
供以后的归因使用。想法不会自动下单：下单仍由基金经理决定并经过风控。盘前研究的 Telegram 消息列出当天的想法，
日报的记分卡部分有一行汇总。

另有**择时记分卡**（`scorecards.timing`），客观衡量 AI 自己设定的价位：每次止损／止盈离场后 1／5／20 个交易日的收盘价
相对离场价的变化（继续下跌为正贡献、反弹为负）；每次等待入场价时，若之后买入，比较买入限价与开始等待时的卖价，
若一直没买，比较之后的收盘价（上涨即错过的收益）。复盘据此校准止损和入场价的松紧，但不应因此放弃保护性止损。

**按市场状态分组与衰减检查**（只作背景，不是任何判断标准）：每个交易日按 SPY 标一个市场状态，只用当天及之前的收盘价——
收盘价在 200 日均线之上为“上涨”，否则“下跌”；20 日波动率高于此前最多 252 个交易日的中位数为“波动大”，否则“平稳”。
趋势或当前波动窗口缺少收盘价，或历史有效波动率不足 60 天的日子不标。决策记分卡（`by_regime`，每个决策按起算收盘日的状态）和研究想法
（`by_regime`，按起算日的状态）分别给出各状态下的结果，AI 可以看到它的判断是否只在某种市场里有效。
`trend_5d_net_excess`（决策 5 日净超额）和研究想法的 `trend`（命中率）把按时间排序的记录分成最近三分之一和之前三分之二，
比较平均值并给出 Welch t：t ≤ −1.65 为 `weaker_recently`（可能失效、拥挤或市场变了），t ≥ 1.65 为 `stronger_recently`，
否则 `no_clear_change`；少于 20 条不比较。若两组内部都没有波动，只报告两组均值，不给 t 值。
期限重叠使 t 偏乐观。日报和周报的记分卡部分各有一行。

市场状态分组还报告 `uncertainty`。从最早记录开始选取收益区间互不重叠的样本，研究想法先按起算日合并，
并保留该日最长的收益窗口。区间以这批样本的均值为中心；表中原有均值仍覆盖所有已打分记录。
至少 10 个不重叠样本才估算 95% 区间，决策净超额用保守的 Student t 临界值，命中率用保守的有界比例区间。
样本不足、市场状态未知或决策样本无法估计方差时标为“不可靠”。区间仍依赖样本间近似独立，只供复盘参考。

经理在理由里依据行情快照里的任何数字（1／5／20／60 日收益、20／60 日波动率、60 日 beta 和相关性、
相对 50／200 日均线和 252 日最高价的位置、20 日日均成交额），都要同时提交 `factual_claims`（每次最多 12 条）。
两种说法可以单用或合用：
- **排名**：`minimum_percentile`／`maximum_percentile`，在同一收盘日、同一可交易范围里排第几百分位（100 是最高值），
  例如 `{"symbol":"ALFA","metric":"ret_60d","minimum_percentile":80}` 表示 60 日收益至少在第 80 百分位，
  `{"symbol":"BETA","metric":"vol_20d","maximum_percentile":20}` 表示波动率在最低的 20% 里；
- **数值**：`minimum`／`maximum`，与快照同样用小数，例如 `{"symbol":"ALFA","metric":"beta_60d","minimum":1.5}`、
  `{"symbol":"ALFA","metric":"pct_from_ma200","minimum":0}`（在 200 日均线之上）。
程序只用该次模型看到的行情快照核对，说了的每个条件都成立才算正确。排名需要完整的快照和至少五个同日可比较标的，并列取平均名次。
数值核验只需要该证券的同日行情。非有限数值会触发结构化回答纠正。证据不足时记为无法核验，一个条件都没说记为 `no_bound`，
同样不计对错。判定随决策写入账本。记分卡和复盘显示正确、错误、无法核验、提交覆盖率和按指标的对错（`by_metric`），
日报和周报点出错得多的指标。错误率只以可核验断言为分母。自由文本和因果解释不在这项核验范围内。

这些记分卡进入盘后复盘、研究和决策的上下文，复盘被要求据此保留、修正或撤回假设，结果写入日报和 `report.json` 的 `latest_scorecard`。
这是客观反馈而不是自动改参数：风险参数、投资范围和权限仍只能由你修改。样本少时结论不稳定，重叠期限之间相关。

## 模拟盘日内交易计数

同一天买入又卖出同一证券算一次日内交易（每次“先买后卖”算一次；先卖掉隔夜持仓再买回不算）。
这个系统在止损当天触发、或盘中调仓时可能产生日内交易，所以：

- `bash scripts/fund-logs.sh` 的概况显示最近 5 个交易日的估算次数；
- 周报第二部分列出本周次数，运行验收报告的指标里有 `day_trades`；
- 基金经理的上下文里也有这个次数，用于了解模拟盘的交易频率。

本应用没有实盘下单通道，计数不用于判断券商限制。
[FINRA 的日内保证金新规](https://syndication.finra.org/content/understanding-new-intraday-margin-requirements)
于 2026 年 6 月 4 日生效，券商可过渡至 2027 年 10 月 20 日；实盘适用要求取决于券商。

默认 93 个代码，研究员、基金经理和数据员都覆盖整个范围，你只需要加入自己希望研究和交易的股票：

| 类别 | 代码 |
|---|---|
| 美股大盘股（56 只，覆盖 11 个行业） | AAPL、MSFT、NVDA、AVGO、AMZN、TSLA、JPM、LLY、XOM、CAT 等 |
| 大盘指数和行业 ETF | SPY、QQQ、IWM、DIA、VTI，XLK、XLF、XLV、XLE、XLP、XLI、XLY、XLC、XLU、XLB、XLRE |
| 国债、通胀保值债和黄金 | IEF、TLT、TIP、GLD |
| 因子 ETF（风格对冲和补充） | MTUM 动量、QUAL 质量、USMV 低波动、VLUE 价值 |
| 另类和对冲（非杠杆） | BTAL 市场中性（做多低 beta、做空高 beta）、DBMF 管理期货、TAIL 尾部风险（国债＋看跌期权）、UUP 美元 |
| 反向和波动率（`leveraged_etf`） | SH 反向标普、PSQ 反向纳指、DOG 反向道指、RWM 反向罗素 2000、SDS 两倍反向标普、QID 两倍反向纳指、TBF 反向长债、VIXY 波动率 |

每只个股和普通 ETF 都属于一个分组，分组有合计仓位上限（科技 30%、金融 30%、医疗 25%、必需消费 25%、工业 25%、通信 20%、
可选消费 20%、能源 15%、材料 15%、公用事业 15%、房地产 15%，另有大型成长股 35%、宽基指数 40%、国债久期 30%、
因子 ETF 30%、另类 20%）。黄金和 SGOV 只受单只上限约束。反向和波动率工具另有自己的上限，见下文。

在 `.env` 里调整，不需要改 `config.json`：

- `FUND_EXTRA_STOCKS`、`FUND_EXTRA_ETFS`：加入投资范围，逗号分隔。写成 `代码:分组`（如 `SHOP:technology`）就计入该行业上限；
  不写分组只受单只上限约束。分组名写错、把 ETF 写进股票（或反过来）、代码格式不对都会在启动时报错。
- `FUND_RESEARCH_SYMBOLS`：只供因子研究、不交易的股票。
- `FUND_EXCLUDE_SYMBOLS`：移除，也可以移除上面加入的代码。
- `FUND_GROUP_LIMITS`：调整已有分组的合计上限，例如 `technology:0.40,energy:0.10`（0 到 1 之间；分组名写错会列出可用的分组）。上限只由你设定，AI 只能在上限内决定实际配多少；反向和波动率工具的上限用下文的两个专门设置调整。

**杠杆、反向和波动率 ETF** 作为对冲或战术补充：默认加入上表中的 8 只，更多的（如 SQQQ、UVXY）只能用
`FUND_EXTRA_LEVERAGED_ETFS` 加入（类型 `leveraged_etf`，同样支持 `代码:分组`），不想用的用 `FUND_EXCLUDE_SYMBOLS` 移除。
买入反向 ETF 不借钱也不借股票，最多亏掉投入的本金，但经济效果是做空：标的下跌时它上涨，风控按它与大盘的负相关把它当作对冲。它们另有两个上限：合计不超过
`FUND_MAX_LEVERAGED_TOTAL`（默认 15%），单只不超过 `FUND_MAX_LEVERAGED_POSITION`（默认 5%），由量化风控作为分组上限执行，
同时仍受单只上限、波动率目标、尾部损失、beta 和压力测试等全部限制；风险预算按个股（更严）计算。
AI 会在上下文 `leveraged_etfs` 里看到它们和上限，并被要求说明用途和退出条件：这类产品每天重置倍数，持有越久偏离越大，
波动率产品还有期货展期损耗。代码里内置了一份常见杠杆、反向和波动率产品名单（TQQQ、SQQQ、SOXL、UVXY、TSLL 等），
名单上的代码只能按 `leveraged_etf` 加入，写进 `FUND_EXTRA_STOCKS`／`FUND_EXTRA_ETFS` 或在 `config.json` 里标成普通 ETF 都会报错；
名单不是完整的，加入的每个代码仍需你自己确认类型。
范围越大，每次 AI 调用的输入越长（行情快照、风格暴露按代码列出），数据员每轮拉取越久：日内脉搏每个代码约 5 秒，
范围大时拉取间隔自动拉长，而不是提高对 Yahoo 的请求频率。改变投资范围会改变风控指纹，重启后基金经理会重新决策一次。

**只禁止借钱和借股票**：不借钱买入（融资）、不借股票卖出（融券卖空），代码都会拦截：买入数量以账户里的真实现金为上限
（扣除费用缓冲），现金为负会停止交易；卖出数量不能超过持有数量，出现空头持仓也会停止交易。卖出、减仓、清仓、止损、止盈随时可以，
卖出不需要审批，也不占买入额度。买入反向 ETF 是普通的买入（多头持仓），不是卖空。

## 因子实验室：AI 挖掘因子，代码客观检验

因子挖掘只在盘后做：复盘的研究阶段结合以往检验结果研究可能的新规律，基金经理阶段把它写成最多 5 个因子表达式（`factor_proposals`），
代码随即检验。盘中只使用已验证因子的排名：排名来自最近一个已完成收盘，开盘前预热一次，全天复用，不占用盘中盯盘和下单的时间。

这些因子表达式由确定性代码（`factors.py`）用无前视的历史数据检验，
结果在之后的每次决策和复盘中交给 AI。闭环是：**AI 发现规律 → 写成因子 → 代码检验 → 通过的因子及其实盘表现回到 AI → AI 修正或提出新因子**。

**两个横截面，不混排**：每个因子只在一个横截面里排名（`factor_proposals[].universe`）：
`stocks` 是可交易个股加上**不可交易的研究股票池**（`factor_lab.research_universe`，默认另外 40 只大盘股，`FUND_RESEARCH_SYMBOLS` 可再加；只用来增加横截面宽度，
从不作为投资建议出现）；`etfs` 是可交易的普通 ETF（不含现金停放用的 SGOV）。个股和 ETF 混在一起排名时，
低波动之类的因子主要是在区分“ETF 比个股稳”，测到的是资产类型而不是选股能力。升级前在混合横截面上验证的因子会自动退役
（理由写明，仍计入尝试次数），需要按新横截面重新提出。注意研究股票池是今天的大盘股，有幸存者偏差。

**因子语言**（安全白名单，不执行任何 Python 代码）：价格数据 `close`、`volume`、`open`、`high`、`low`（已完成日线）；
基本面数据 `earnings`、`revenue`、`gross_profit`、`cashflow`（近四个季度合计的净利润、营收、毛利、经营现金流）、
`book`、`assets`（最新净资产、总资产）、`shares`（封面披露的普通股股数），来自 SEC EDGAR XBRL（见下）；时序函数
`ret(n)`、`vol(n)`、`delay`、`delta`、`ts_mean`、`ts_std`、`ts_max`、`ts_min`、`ts_rank`、`log`、`abs`、`sign`；
横截面函数 `rank`、`zscore`、`demean`；`+ - * /`。所有运算只看过去，窗口 1–504 个交易日。例如：
`rank(ret(126) - ret(21))`（中期动量）、`-vol(60)`（低波动）、`rank(close / ts_mean(close, 200) - 1)`、`-rank(ret(5))`（短期反转）。
基本面例子：`rank(earnings / (close * shares))`（盈利收益率）、`rank(book / (close * shares))`（账面市值比）、
`rank(gross_profit / assets)`（毛利率质量）、`rank(revenue / delay(revenue, 252) - 1)`（营收增长）。

**按披露日的基本面**（`fundamentals.py`）：SEC 的公司财务数据（company facts）每个数值都带有所在报告的受理日期 `filed`。
某个日期只能用**受理日期早于当天**的报告；后来的报告重述了某个季度，重述值也只从它自己的受理日起生效，所以历史回测没有前视。
10-Q 的利润表给出单季，现金流量表只给年初至今累计，代码按同一财年起点做差得到单季，第四季度 = 全年 − 前三季度；
必须有连续四个季度才计算近四季合计，否则为空，不外推。同一日期披露多个股票类别股数的公司（如双重股权）股数为空。
ETF 没有基本面。需要在 `.env` 设置 `FUND_SEC_USER_AGENT`（姓名＋邮箱，SEC 的要求）；不设置时基本面字段全为空，
使用它们的因子检验结果为数据不足。每家公司只缓存所需科目（`<账户目录>/cache/sec/`），最近一次报告约 80 天后才重新下载，
最多每周一次，请求间隔 0.15 秒（低于 SEC 每秒 10 次的上限）。

**检验标准**（防止“挖掘”变成过拟合）：
- 每个日期在投资范围内计算因子值与之后 `horizon_sessions` 个交易日收益的横截面 rank IC（Spearman），
  每隔 `horizon_sessions` 取一个日期，避免重叠收益虚增 t 值；
- 前 70% 为样本内，`|t|` 必须超过随**累计尝试次数**提高的 Bonferroni 门槛（试 1 个约 1.96，50 个约 3.29，200 个约 3.66）；
  同一表达式重复提出不算新尝试，但也不会重新检验；
- 后 30% 为样本外，方向必须一致且 `t ≥ holdout_min_t`（默认 1.0）；
- **滚动样本外**（与固定切分并存，两者都要通过）：取样后的日期切成 `walk_forward_windows + 1`（默认 5）段，第一段只用来训练，
  后面每一段是一个检验窗口，训练数据是它之前的全部观测，但去掉紧挨着的最后一个（隔离 `horizon_sessions` 个交易日，
  训练段的远期收益不会和检验段重叠）。窗口算“一致”要求观测至少 3 个、窗口平均 IC 和它自己训练段的平均 IC 都与总体方向同号；
  至少 `min_window_agreement`（默认 3 个，共 4 个）窗口一致才能通过，只在某一段时间有效的因子会被拒绝；
- **模型知识截止日**：`model_knowledge_cutoff`（`FUND_MODEL_KNOWLEDGE_CUTOFF_JSON`，如 `{"deepseek-chat": "YYYY-MM-DD"}`，
  由你向模型提供方查询后填写）。提出因子的模型（写复盘的研究员和基金经理）都有截止日时，取较晚的那个，
  之后日期的检验结果单独列为 `clean_out_of_sample`（模型不可能背下来的部分）；任一模型没有填写时标为 `unknown_cutoff`：
  所有历史检验都可能反映模型记住的行情，只有验证日之后的实盘记录是干净的。这一项只报告，不改变门槛；
- 前 20% 与后 20% 的多空收益差扣除交易成本后必须仍与方向一致：成本 = 4 × 五分位换手率 × `cost_bps`（默认每边 10 个基点）；
- 与同一横截面里已验证因子的排名平均相关系数 ≥ `max_redundancy`（默认 0.7）的候选记为 `redundant`（冗余），不算新发现；
- 同时报告 1／5／20 个交易日的 IC 衰减和排名自相关（排名变化越慢，换手越低），都只用样本内数据，样本外保持干净；
- 通过后跟踪**验证日之后**的 IC，这是真正的样本外记录；至少 `live_min_observations`（默认 10）个观测后若平均 IC 与方向相反，自动退役。
- **负对照**：每 `negative_control_days`（默认 7）天用股票横截面跑 `negative_control_runs`（默认 20）次随机排名因子，
  按一次尝试走完整套标准，记录通过样本内门槛的比例（应接近显著性水平）和最终通过的比例（应低于它）。
  结果在 `factor_lab.negative_control` 和 `factor_negative_control` 事件里；`too_loose` 为真说明这个横截面上运气通过得太多，
  需要人工检查，不会自动改门槛。合成数据上 200 次随机因子：样本内约 7.5%，最终通过约 0.5%。

**AI 看到什么**（`factor_lab` 上下文）：语法、检验标准、已尝试次数和下一个门槛、已验证因子（样本内／样本外／实盘 IC、
当前排名靠前和靠后的**可交易**证券）、最近被拒绝、冗余或退役的因子及原因、基本面数据状态。因子**只是证据**，不会直接下单；
AI 仍决定完整目标组合，量化风控和审批规则不变。影子 A/B 的对照组看不到因子实验室，因此 A/B 衡量的是包括因子在内的整个学习闭环。

配置在 `config.json` 的 `factor_lab` 段（`.env` 中 `FUND_FACTOR_LAB=false` 可关闭）：历史长度 504 个交易日、
每个日期至少 8 个证券、样本内至少 20 个观测、样本外至少 8 个、显著性 5%。离线检验单个表达式：

```powershell
.\scripts\run_autonomous_fund.ps1 -Mode factor-lab -DataDir data -Symbols SPY,TLT,GLD,IEF,DJP -Expression "rank(ret(60))" -Horizon 5 -MinNames 5
```

Linux 用 `--expression=...` 形式（表达式以 `-` 开头时必须如此），例如 `--expression=-vol(20)`。
**实测**：仓库自带的 2019 年 5 只 ETF 日线上，`rank(ret(20))`、`-rank(ret(5))`、`-vol(20)`、`rank(ret(60))` 全部被拒绝
（样本内 |t| 0.11–1.21，低于 1.96）。5 只证券、一年数据远不足以证明任何因子，这正是检验应有的结论；
2026-11-05 起默认个股横截面为 56 只可交易个股加 40 只研究股票，ETF 横截面为 19 只 ETF，两年日线（此前是 16 只个股加 40 只研究股票、14 只 ETF）。合成数据测试中，真实存在的动量规律在所有种子下都通过，纯噪声在所有种子下都被拒绝。

**行业内 IC**：个股横截面的检验同时报告 `sector_neutral`：先按全体排序，再减去各行业的平均排名后计算的 IC，
用的是同一批日期。接近 0 说明这个因子主要是在区分行业（押行业轮动），而不是在行业内挑股票；
AI 看到的已验证因子带 `mostly_sector_bet`（行业内方向不一致或 |t| < 1 时为 true）。这只是证据，不是通过条件：
行业轮动也可能是真实规律，但 AI 应该知道它押的是行业。

**幸存者偏差**：历史检验主要依赖当前投资范围和研究名单，遗漏退市、被收购、被剔出指数的股票可能让 IC 和多空收益偏乐观。
验证之后的记录（`live`）是时间上的样本外证据，仍受覆盖范围影响。系统用以下措施缓解：

- **因子先是“待确认”**：历史检验（样本内、留出期、walk-forward、负对照）全部通过的因子先是 `provisional`
  （日报写“历史检验通过（待样本外确认）”，实验登记表里是影子观察 `shadow`）。AI 看得到它的表达式和样本外记录，
  但不会给它偏好或回避的股票名单。验证之后的样本外记录达到 `live_min_observations` 个观察、平均 IC 方向与验证方向一致，
  才确认（记 `confirmed_at`，账本写一次 `factor_confirmed`），之后它才作为 `validated` 给出名单，登记表转为模拟盘生效。
- **按加入标普 500 的日期计入**（`factor_lab.index_membership`，默认 `true`）：今天的大盘股正是因为涨了才成为大盘股，
  在它们还小的时候就算进横截面，之后的上涨会让动量、规模类因子显得有预测力。因子实验室从公开的标普 500 成分 CSV
  （github.com/datasets 发布的维基百科列表镜像，每 30 天刷新，缓存在账户的 `cache/index_membership.json`）取每只成分股的加入日期，
  加入之前它不影响横截面排名、均值、标准差或随机对照；价格保留，供加入后的时间序列指标回看。没有日期的股票全程计入，
  AI 上下文的 `index_membership` 列出它们和历史期内才加入的股票。刷新失败时继续使用上一次有效的缓存；
  本地缓存无效时会尝试重取。若也无法下载，因子检验仍可运行，并标注未应用加入日期筛选。
  数据员还会缓存社区历史变更表。区间能与当前名单核对、日期未标为估算且发行人身份无歧义时，
  加入日计入、移出日起排除，再次加入则恢复计入；区间从 2007 年 3 月开始覆盖。
  这里只筛选已有行情的证券，缺失的退市价格不补齐，也不能确认指数以外发生的代码复用。
  合成数据测试里，一只未来才加入的股票在加入前的上涨让动量因子的 IC 超过 0.2，按日期计入后低于 0.1。
  按 2026-11 的默认配置，96 只股票在两年历史开始前就都已是成分股，所以暂时没有任何股票被排除；
  以后加入新近入选的股票或加长历史时才起作用。replay 和测试不联网，不使用这份列表。
- **每日股票池快照**（`fund_universe_snapshots`）：每天准备因子数据时，记下个股和 ETF 两个横截面的成员，
  以及它们作为成员期间数据源给出的完成日线（开高低收和成交量）。新成员从它最新一根完成日线开始记，不往前补；
  因子面板盘中复用，收盘后按新的日线截止时间重建，归档也遵循同一截止时间。
  数据源修订时，直接更新仍能取到的日线（包括开高低及成交量）；只有重叠日线支持同一调整比例时才缩放更早的价格，
  只有成交量也支持反向比例时才调整更早的成交量。
  之后离开股票池的股票（被收购、退市、移出名单，或数据源不再提供）仍按在池期间的日线留在因子检验和样本外记录里；
  它们的 SEC 基本面不查（代码可能已被别的公司使用），记为缺失。日报和周报写明快照从哪天开始。
  快照缓解幸存者偏差，仍可能缺少退市最终收益、基本面或成员历史。被日线交叉核对判定不可靠的证券不会用旧快照补回。
  快照失败只记 `universe_snapshot_error`，不影响当天的因子数据。离开股票池的股票最后几天的远期收益不计入（没有之后的价格），
  所以退市前最后一段下跌仍可能少算。

**因子拥挤度**：因子按方向分出得分最高和最低的各 20%，报告两组账面市值比中位数之差、各组过去 60 日的平均两两收益相关性，
以及可取得的 FINRA 场外卖空成交占比。估值使用已有的 SEC 时点数据，缺少有效账面价值或股数时不估算；
相关性只使用至少 40 个共同日收益的股票对。FINRA 占比先按证券用报告卖空量除以该文件的报告总成交量，再对组内有数据的证券等权平均。
数据员在纽约时间 18:00 后拉取最近发布的交易日文件；报告列出文件日期和各指标覆盖数。
FINRA 只覆盖其报告设施的已公开场外成交，不能用来推断空头持仓或全市场卖空比例。
这些指标仅用于研究和复盘，不改变因子确认或下单条件。

## 实时行情：Yahoo 推送报价

`market_data.live_stream: true`（默认）时，本地模式在后台订阅 Yahoo 的 WebSocket 推送（yfinance 自带的非官方接口，
`wss://streamer.finance.yahoo.com`），持续接收最近请求的证券的最新成交。报价规则：
- 单连接保留最近请求的 60 个符号，满额时退订最久未请求的符号并接纳新符号，不再静默忽略第 61 个及之后的请求。
  诊断中的 `capacity`、`requested` 和 `subscription_evictions` 显示容量、当前请求数及轮换次数。
  同一股类符号的点号／连字符写法共享源订阅；退订其中一个写法不会中断仍在观察的另一个写法。
- 只在 NYSE 正常交易时段使用；成交的**源时间**须晚于最近一根已完成分钟线、且不超过 `live_seconds`（默认 60 秒）；
  未来时间戳、乱序帧、休市推送都不采用。推送带买卖价且合理时使用，否则仍按披露的 10 基点价差代理。
- 按新鲜推送、最新成交元数据、已完成分钟线的顺序选择报价；`price_kind` 和 `report`／`status.json` 的 `quotes_by_kind` 记录实际来源。
- 没收到某个符号的推送时，先检查同一次分钟线响应携带的 `regularMarketPrice`／`regularMarketTime`。
  两者必须同时有效，源时间须在当前常规时段、不在未来、不超过 `live_seconds`，且晚于完整分钟线；否则继续回退完整分钟线。
  这种报价标为 `chart_last_trade_with_spread_proxy`，计数为 `chart_quote`；不使用正在形成的分钟线收盘价，不补造源时间或分钟成交量。
- 分钟线下载失败或退避时仍会订阅新请求的符号；若已收到合格的新鲜常规时段推送，可独立提供报价，不补造分钟成交量。
  分钟线故障仍保留在诊断中，撮合继续独立要求真实、完整的新分钟线。
- 同一响应中的最新成交价／源时间对会在 K 线完整性检查前独立保留；即使没有完成分钟线、全部 K 线无效或随后进入退避，
  合格的新鲜 chart 成交仍可作为报价。推送继续优先，chart 证据按符号隔离，至多保留 60 个最近符号，
  旧响应和无效更新不能覆盖较新的合格成交。每次读取重新检查源年龄与常规交易时段，不重新计时，
  不提供不存在的成交量，也不能代替撮合所需的完整 K 线。
- 日线／分钟线中的非有限、非正价格、负成交量或 OHLC 包络错误只剔除整根坏 K 线，保留原始时间上的缺口，
  不插值、不前向填充，也不把缺少的成交量改为零；其余有效 K 线继续可用。
  全部完成 K 线都无效时仍拒绝该证券，拆股／分红字段无效时仍阻止其账务处理。
  `discarded_rows` 和 `last_rejected_bar` 保留坏行数量、符号、周期、时间及字段。
  网络请求跨分钟时，用返回后的时钟判断 K 线是否完成。
- `status.json` 的 `market_data.quotes_by_symbol` 保留最近请求的至多 60 个符号，分别显示实际选中报价的
  `price_kind`、`source_as_of`、`checked_at`、`age_seconds`，以及推送／chart 各自的源时间。
  这些年龄是 `checked_at` 时的结果，不是读取状态文件时重新计算的年龄；未收到推送时 `stream_as_of` 为 `null`。
  总订阅数与有推送符号数不同，不能仅凭这两个总数判断具体哪个符号缺行情。
- 提醒拒绝观测时，`price_observation_rejected` 保留源时间、检查时间、实际年龄、上限和拒绝原因；
  诊断与原通知共用去重窗口，不因每次变化的时间而刷屏。`bash scripts/fund-logs.sh errors` 包含这些 INFO 级行情故障。
  如果所有真实来源都过期，提醒仍等待新行情，不能保证备用源一定能提供新价。
- `market_data.source_failures` 保留至多 60 个仍未恢复的历史序列故障，包含符号、周期、失败尝试时间、
  原因、连续失败次数和当前剩余退避秒数。后续 `cooling down` 不覆盖该次失败的原因；同一序列成功后才清除该项，
  其他证券成功不会清除它。提供方 SDK 异常只保留类型，不复制可能带私人信息的响应正文。
- 断线自动重连（指数退避），错误次数和最后错误写入诊断，不会把旧价格当成新价格。
- 本地模拟**成交**仍按提交后新完成的一分钟 K 线保守撮合，不因推送而变乐观。

配合 `execution.iteration_seconds`（默认配置 30 秒，可设 15–300），止损、止盈、提醒的反应时间从 1–2 分钟缩短到半分钟左右。
`check` 会尝试接收 SPY／QQQ 推送并报告是否连通。

本地模拟盘开盘首分钟只取得上一交易日的持仓报价时，会报告 `opening_valuation_pending`。后台估值在 5 秒轮询中尝试更新，
组合复核在下一次策略迭代重新读取报价。首次拒绝会记录 `price_observation_rejected`，包含标的、来源、源时间和年龄。
首分钟之后持续缺价时按普通估值失败报告。

收盘时最后一分钟和尚未补齐的当日日线均不可用时属于 `closing_valuation_pending`，后台继续重试，同时复盘可以使用已保留的观测；
不会把盘中净值改标为收盘净值。其他收盘账户核对／估值失败仍为 `report_error`，保留具体风控原因，
并在 `operation_error` 记录安全的模块、函数和行号，不序列化提供方响应、异常局部变量或私人路径。
本地模拟应用的后台余额刷新失败后隔 15 秒再尝试，避免原生缓存现金属性每秒触发同一失败堆栈；
失败或等待重试都返回刷新失败，不推进“最后成功刷新”时间。
显式余额刷新、`get_cash()` 和 AI／交易账户快照继续立即尝试读取；行情源自身的退避仍然有效。
已有缓存仅供原生状态展示，不能替代这些严格读取的结果。
账户快照的 `as_of` 与事件时间使用数据读取完成后的观察时刻，不再取请求开始时间；
读取过程中才到达的行情不能提前进入历史报告。交易时段发布本地快照前再次校验持仓行情，
后续读取已使其过期时等待新行情；收盘净值仍保留真实 session close 和另外记录的观察时间。
基准行情独立逐证券读取、校验真实源时间并在发布前复核，缺少某一基准不会丢弃其他有效基准或纯现金账户快照。
持仓中已有的基准直接复用同一有效估值，减少重复读取并保持估值一致；
`benchmark_observations` 保留采用的价格与源时间。历史／脚本模式仍使用原生历史价格语义。
这些改动修复新观测，不重写以前快照的时间，也不推算当时未保存的收讫时间。
模拟买入复核现有持仓时，风险计价使用保留的真实源时间，并要求买卖价为有限、正数且不交叉；
持仓风险金额使用卖价与已观测价格中较高者。后续证券读取和账本检查后，再次校验原始账户估值与持仓报价的年龄，
失效时等待新行情，不消耗该根 K 线或修改现金、股数。卖出继续使用自身的有效执行 K 线，
不会为其他持仓的风险计价额外请求行情。
以上规则适用于全部本地模拟符号、推送开启／关闭及全账户／资金分仓配置，没有证券专用例外。
坏行情不得成交、旧／未来观测不得触发提醒、无效公司行为不得改账、复盘不得伪造收盘价均有合成回归对照；
本地回归证明代码路径，服务器加载与实际行情恢复仍需以新进程的状态和日志核对。

局限：这是非官方接口，没有服务等级承诺，Yahoo 条款限制个人用途，可能随时变更或被限流；
数据来自部分交易所的最新成交而不是全市场合并报价（SIP），成交量不完整，股票通常没有买卖盘。
用于个人研究和模拟足够；真钱交易应改用券商行情（Alpaca 免费 IEX 实时、Schwab 开户后的免费推送）或付费 SIP 数据。

## 实时资讯：AI 综合考虑的信息流

`news.enabled: true` 时，后台线程（不占用交易线程，不调用模型）每 `poll_seconds`（默认 300 秒，休市时放慢 4 倍）轮询：

| 来源 | 内容 | 触发提前复核 |
|---|---|---|
| Yahoo 个股新闻（yfinance） | 整个投资范围的最新标题 | 持仓证券在 `burst_minutes`（60 分钟）内新增 ≥ `burst_threshold`（3）条 |
| Google News RSS | 运营者 `queries`（默认：美联储利率决议、CPI、非农）和 AI 在决策中给出的 `news_watch` 搜索词 | 出现新的匹配标题 |
| 美联储新闻稿 RSS | 利率决议、讲话、监管公告 | 每一条新发布 |
| SEC EDGAR 8-K | 持仓公司的重大事项公告（需设置 `FUND_SEC_USER_AGENT` 联系人） | 每一份新公告 |
| `rss_feeds` | 运营者自行添加的 https RSS／Atom 源 | 只进入上下文 |

每条资讯去重保存来源发布时间和首次观测时间。启动后每个来源的第一批只作为基线，不会把积压的旧闻当成新事件；
超过 24 小时的旧闻和未来时间戳不触发。研究员、基金经理和盘前研究都会收到最近 24 小时与持仓、目标证券相关的资讯
以及全部宏观／搜索命中（最多 `max_items_per_context` 条），并标注为**未经核实的第三方文本**，要求重大判断回到原始公告核对。
重大资讯通过 `watch_triggers` 告诉 AI 为什么被提前唤醒，仍受最短复核间隔、失败退避和每日模型预算约束。
AI 只能提供搜索词，不能提供网址；资讯监控不下单。来源失败各自退避，不影响交易。
历史回测不启用实时资讯，研究员仍用带发布时间校验的研究工具。

## 反方审查与组合构建 A/B

**模型回答的格式**：回答里的文字超过字段长度上限时截断并标注 `…[truncated]`，条目过多时只保留前面的，不再因为多写几句就整份作废
（2026-11-03 一次反方审查的摘要超出 1500 字被整份丢弃）。实盘模式下证据时间写成区间（`A ~ B`）时取结束时间，写不出可读时间的
用校验时刻并在 `estimate_reason` 注明；历史回放仍然严格：时间必须可读，区间按结束时间判断是否晚于模拟时刻。

证据的日期估计说明统一使用 `estimate_reason`。输入兼容说明字段 `estimated_note`：只提供别名时按
`estimate_reason` 保存；同时提供时，空说明或相同说明合并为一个字段，保留非空说明；两个非空说明不一致时拒收。
这不会忽略其他未知字段，也不会把非字符串转成文字；必填字段和历史证据的时间、估计依据校验保持有效。
输入原文仍由原生 trace 保存，规范化后的证据只保留 `estimate_reason`，无需重新调用研究员。
反方审查兼容额外的 `missing_evidence_placeholder: null` 空占位字段；非空占位字段和其他未知字段仍拒收，
真实的 `missing_evidence` 列表不会被占位字段替换或丢弃。
三个角色都明确要求返回完整的 schema JSON 对象，解释文字放在对象内；经理的全部决策理由放在一个
`rationale` 字符串中，不另加续写字段。未知字段仍拒收，不通过丢弃字段来接受一个不合规答案。
经理格式失败及盘后研究格式失败沿用已有的一次预算内纠正；格式告警本身不代表该轮最终失败，
需结合 `decision_format_retry`、`decision_validated`、`decision_backoff` 或 `postmarket_research_retry` 等后续事件核对。

`Invalid structured agent answer` 通知现在包含失败角色、已提供的阶段、字段位置和错误代码，例如
`researcher/postmarket_review; schema_validation: evidence[0].observed_at (string_type)`。
告警最多显示五处错误，未知字段名显示为 `<extra>`，不会把模型输入值、研究正文或提供方错误内容复制到通知中。
账户账本的 `agent.answer_diagnostic` 保留错误分类、数量和同一份安全位置；原始 `parse_error` 与研究全文仍留在账本／trace 中供核查。
超时等运行失败单独标为 `runtime_error: TimeoutError`，空回答为 `missing_answer`，无法提取 JSON 为 `invalid_json`。
这些诊断在本地使用同一解析器和 schema 完成，不发起新的模型请求，也不会把失败结果激活为策略备忘。
`fund-logs.sh errors` 同时保留校验错误下一行的字段位置、缩进详情及说明链接，其他进程的心跳不会切断它们；
Python 自定义异常即使名称不以 `Error`／`Exception` 结尾，或没有错误消息，也保留 traceback 的最后原因行及异常链。
这类终行只在同一进程已经开始的 traceback 内识别，不用来扩大普通日志或校验错误记录的范围。
正常的大型研究输出仍不进入异常摘要。

原生 `notify_user(title, message, severity, enabled)` 使用 LumiBot 的通知管理器，并将本账户的消息排入
`fund_outbox` 持久化队列；原生 `Strategy.notify` 的接口、回测禁发和 `enabled=false` 行为保持有效，
其他已配置通知提供方继续收到原生分发。队列确认的 `payload.status=queued` 仅表示已落盘，
Telegram 送达仍由独立监控确认。AI 通知固定记为 `agent_notice` 并标注供参考，不能伪装成审批请求或健康故障；
接收人来自该账户已有的监控配置。内部业务告警单独使用 `_notify_fund`，不再覆盖原生通知接口。

三个角色的研究提示均说明 DuckDB 的实际表结构检查、CTE 只在本条语句内有效，以及用多个 CTE 分开计算
滞后收益、滚动统计和聚合。上下文字段名不能代替实际表列名。近似研究统计里的小数乘法／幂运算，应在运算前
把操作数转为 `DOUBLE`；只在乘积外转换类型，无法避免中间的 `DECIMAL` 溢出。需要精确小数时，先选择能容纳
中间结果的精度和小数位数，不能只把位宽增至 38 却保留会相乘超限的小数位。不得修改底层账本或舍入来源证据来掩盖错误。
查询错误仍返回给模型，由它修正并核对成功结果；这些提示不保证模型永不写错 SQL，也不自动改写模型的查询。
前瞻收益须先在对齐的交易日网格上计算，再筛选信号条件；不能先筛信号再把“下一次信号”当作下一交易日。
每个期限和条件分别列总行数与非空收益样本数，均值、胜率使用同一组有效起止价；尾部未成熟数据保持 NULL，不能算零收益或失败。
提示提供 `COUNT(excess_return)` 与忽略 NULL 的胜率 SQL 范例，并要求说明重叠窗口、独立样本不足和多次试验限制。
宏观结论按同源同日收益率判断倒挂，发布日历按每个事件的官方来源核对，不把数据台未采集等同于官方未发布。
提示更新通过正常 `prompt_version` 区分，不重写旧研究、预测和评分；这些检查指引没有新增模型调用或交易门槛。

**反方审查**（`critic` 段，`FUND_CRITIC`）：基金经理决策前可调用一个只读的 AI 角色（默认用研究员的模型，
可用 `FUND_CRITIC_MODEL` 指定），专门给出研究的最强反面论证：反面证据、已被定价或拥挤的逻辑、估值、事件和流动性风险、
观点之间的相关性、陈旧或无日期的证据。输出按证券列出的疑虑和缺失的证据（`critique`），基金经理必须在理由里回应重要疑虑。
盘中评议使用已保存的预研及其可用性信息，不先重跑研究员；历史回放继续评议该轮已验证日期的研究。
它不做决定、不下单。模型预算不够两次调用（反方＋基金经理）时跳过，调用失败只记录 `critic_unavailable`，都不会挡住决策。
反方同时比较“维持上轮已接受计划”和“改变／退出”，使用相同的前瞻期限并计入调整的增量摩擦；反对当前组合不是必须给出另一个组合。
经理仍独立决策，反转近期目标时解释新的证据或现在识别出的原判断错误，并核对原持有期、失效条件及未来交易成本。
不要求一定等到止损价或出现新消息才纠错，也不强制最低持有期。共同发生的模型／数据开销不能算成某个选择独有的收益，
年度费用覆盖不足本身不能决定加仓还是减仓。已支付手续费已经体现在净值中，属于沉没成本；未来买卖的费用、价差和滑点仍需比较。
盘中两方现在也接收截至账户快照的最近 6 条确认成交及费用，累计券商回报替代分笔观测，未知费用保留未知。
时效纠正重读账户时同步刷新成交截止范围，避免账户已经更新却仍只看到最初那批成交。
同一交易日内研究、持仓、唤醒原因（`watch_triggers`）、上轮计划、近期成交和提示版本都没变时复用上一次的审查（`critic_reused`）；
任何一项变化都重新审查。复用保留原时间和源调用编号，不把旧审查标成刚生成。提示文字更新通过正常 `prompt_version` 区分新旧记录。
影子 A/B 的两组看到同一份反方审查。

**组合构建 A/B**（`construction` 段，`FUND_CONSTRUCTION_MODE`）：专业基金通常把“选什么”和“各买多少”分开。
每个通过校验的决策都同时记录两种构建方式（`construction_variant`）：
- `ai`：AI 给的权重；
- `risk_budget`：同样的证券和总仓位，按 AI 权重分配**风险贡献**（波动低的证券分到更多权重，波动高的更少），
  用协方差的坐标下降法求解，负相关也成立；没有历史的证券保持 AI 权重。
两种方式用同一套已完成收盘价打分，比较从决策后首个收盘到下一交易日收盘、相对 beta 匹配基准的超额收益。
同一个起算收盘日最多计一对，不需要额外的模型调用。
`auto`（默认）先用 `ai`，至少 `min_pairs`（20）个交易日、配对 t ≥ `switch_t_stat`（2）时切换到风险预算并发 Telegram 通知，
之后证据反转再切回；也可以固定为 `ai` 或 `risk_budget`。无论哪种方式，量化风控的全部上限都照常生效。
决策记分卡（`decisions`）只衡量 AI 的选股，构建方式的比较在 `scorecards.construction`。

## 量化风控原则

借鉴量化基金常用的“预测与组合构建分离”：AI 负责观点和相对配置，`scripts/autonomous_fund/quant.py`
负责把目标投影到风险约束内。全部计算只用调用方提供的**已完成交易日**收盘价（不含当日或未来 K 线），
没有模型、券商或网络依赖。每一步都只缩小权重，所以结果同时满足所有约束；函数末尾还独立复核一次。

| 约束 | 方法 | 默认值（`quant_risk`） |
|---|---|---|
| 波动率估计 | 最近 63 个交易日简单收益的 EWMA 方差（RiskMetrics λ=0.94），年化 | 下限 10% |
| 相关性估计 | 相关性比波动率需要多得多的数据：用最近 252 个交易日、衰减更慢的 EWMA（`correlation_lambda` 0.97，等效样本约 65 天），再向平均相关系数收缩 `correlation_shrinkage`（常相关目标，收缩后仍半正定）。λ=0.94 的等效样本只有约 31 天，用来估 27×27 的相关矩阵噪声太大，几周的异常走势就会让组合波动估计大幅摆动 | 252 天、λ=0.97、收缩 25%；平盘序列与其他证券的相关系数按 1 处理且不参与收缩 |
| 单名风险上限 | 权重 ≤ min(10%, 风险预算 ÷ 年化波动)；个股用 `max_name_risk`，普通 ETF 用 `max_etf_name_risk` | 个股 0.025：波动 25% 的股票上限 10%，波动 50% 的上限 5%；ETF 0.05（依据下文 2019 年真实数据回放校准） |
| 组合 beta | 各持仓权重 × 相对 SPY 的事前 beta（来自上面的协方差）之和 ≤ `max_portfolio_beta`；超过时只按比例缩减 beta 为正、推高这项暴露的证券，负 beta 的不动 | 1.0（`FUND_MAX_PORTFOLIO_BETA`） |
| 风格暴露 | 动量（12-1 个月收益）、波动（63 日实现波动）、规模（60 日日均成交额的对数，代表规模，只算股票）三种风格在交易范围内做截面标准分（截尾 ±3），组合暴露 = 权重 × 标准分之和，绝对值 ≤ `max_style_exposure`；超过时按比例缩减推高该方向的证券。AI 在 `risk.exposures` 里看到当前暴露、上限和每只证券的分数 | 0.75（`FUND_MAX_STYLE_EXPOSURE`）；只基于本系统约 30 个标的，不是全市场风险模型 |
| 行业／主题组 | 运营者定义、可重叠的组，组内权重和 ≤ 组上限 | 科技 30%、通信 20%、可选消费 20%、金融 30%、医疗 25%、能源 15%、必需消费 25%、大型成长股 35%、宽基指数 40% |
| 回撤分档预算 | 回撤 ≤ 4% 满额；4%–8% 线性降到 25%；≥8% 锁定增仓 | 总敞口预算 = 70% × 系数，超出部分自动卖出 |
| 组合波动率目标 | 事前年化波动 √(wᵀΣw) 超过目标时整体等比例缩小 | 12% |
| 尾部风险 | 1 日 97.5% ES = max(252 日历史模拟 ES, 正态 ES)，超过上限时整体缩小 | 2% 净值；历史样本少于 120 天时只用正态 ES |
| 历史情景压力测试 | 把当前目标权重放进已结束的历史危机窗口，按买入持有计算整段亏损（不计止损和回撤保护，偏保守）；最差情景超过上限时整体缩小。某证券在窗口内没有完整历史（如当时尚未上市）时，用基准跌幅 × max(1, beta) 代替，完全没有历史的用 60% 波动对应的倍数，并列在 `scenario_proxied`；基准本身缺历史的情景跳过并列在 `scenarios_unavailable`。窗口只在结束之后才使用，所以历史回测不会“预知”之后的危机。每只证券的长历史只下载一次，存入账本表 `fund_scenario_returns`（下载失败或返回空不记录，次日重试；“窗口内没有历史”的结论 30 天后复查一次） | `max_scenario_loss` 35%；`stress_scenarios`：2008-09-01～2009-03-09（金融危机）、2020-02-19～2020-03-23（新冠暴跌）、2022-01-03～2022-10-12（加息熊市），可在 `quant_risk.stress_scenarios` 改写，最多 10 个 |
| 数据缺失 | 历史不足 20 个交易日的证券不能加仓，只能持有或减持，并按 60% 波动、完全相关计入组合风险 | 不填充、不插值 |
| 单日亏损闸门 | 相对上一交易日最后观测净值亏损 ≥ 2% 时，当日停止买入，次日自动恢复 | 卖出不受影响 |
| 市场压力 | SPY 上一交易日或盘中跌幅 ≥ 3%，或 SPY EWMA 年化波动 ≥ 35%；基准历史缺失按压力处理 | 压力下的买入需要审批 |

构建结果、绑定的约束（情景压力为 `scenario_stress`）、事前波动、ES 和各情景亏损写入 `risk_overlay` 事件，报告的 `latest_risk_overlay` 可查看。
基金经理的风险上下文里有 `stress_scenarios`：各情景窗口、基准跌幅和各证券在窗口内的涨跌，便于直接给出不超限的组合。
基金经理在每次决策前收到风险上下文：各证券波动估计、单名上限、分组、当前回撤和预算、单日亏损、
今日已用额度和市场压力状态，以便直接给出可行的组合，减少被缩小或被拒绝的情况。
这些估计基于历史数据，不能预测跳空、停牌或从未出现过的相关性变化；ES 和波动目标约束的是事前估计，
不是亏损上限保证。修改 `quant_risk` 后重启生效，摘要变化会让旧目标失效。

## 事件风险与宏观环境

**财报前降仓**（`events` 段，`scripts/autonomous_fund/events.py`）：止损挡不住隔夜跳空，而财报是最常见的原因。
个股在财报日当天或下一个交易日（`earnings_window_days`，默认 1 个 NYSE 交易日）之前，权重上限降到 `earnings_max_position`
（默认 5%），超出部分按普通减仓自动卖出；财报日过后上限恢复，AI 可以再买回。ETF 不受影响。
窗口按实际交易日历计数，跳过周末和休市日，半日交易日仍算一个交易日；设为 0 时只覆盖当天，不会在周末自动扩展到下周。
日历来源：设置了 `FINNHUB_API_KEY` 时用 Finnhub，否则用 Yahoo 日历（非官方，每次最多等 10 秒）；每只股票每天只查一次，在开盘前研究时取好，存入账本表 `fund_earnings`。
拿不到日期时不猜测：该股票维持正常上限，并列在风险信息的 `event_risk.unknown`。只在 local／paper 模式生效，
因为历史回测需要“当时已知的日历”，而免费接口不提供。绑定的约束记为 `earnings:<代码>`。

**宏观环境**（`macro` 段，`scripts/autonomous_fund/macro.py`）：每个交易日从 FRED 取 3 月／2 年／10 年美债收益率、
10y−2y 利差、高收益债利差（ICE BofA）和 VIX，给出最新值、20 个观测的变化、一年分位数，以及收益率曲线倒挂、
信用压力（高收益债利差 ≥ 6 个百分点或 20 个观测内上升 ≥ 1 个百分点）、波动偏高（VIX ≥ 25）三个标记和现金停放的国债收益率。
这些是市场数据，FRED 不修订，所以只保留早于当天的观测在历史回测中也没有前视。有 `FRED_API_KEY` 用官方 API，
否则用公开 CSV。它只是给 AI 的参考信息，不是交易规则；某个序列取不到时只标为不可用。
CSV、API 和缓存中的观测都检查日期及有限数值；NaN、无穷大和无效单元格不会参与分位数与环境标记，零及负利率仍可使用。
全部观测无效时记为不可用，数据员不会把这次刷新标成成功。运行进程已获取有效观测时，日缓存写盘失败不会丢弃它们，
当天继续使用内存数据，也不会为缓存故障重复请求；进程重启后仍可能需要重新获取。
旧缓存内容无效时按缺失处理：有准备预算就重新获取，没有预算则标为延后，不会因坏缓存一直隐藏正常的数据源。

## 现金管理：闲置现金自动买短期国债 ETF

总敞口上限 70% 意味着至少 30% 的资金是现金，AI 选择空仓时更多。专业基金不会让这部分钱零收益地闲着。
`cash_sweep` 段（`.env` 的 `FUND_CASH_SWEEP`）把闲置现金停在运营者认可的一只现金等价 ETF 上（默认 `SGOV`，
0–3 个月美国国债），实现于 `scripts/autonomous_fund/cash.py`：

- 投资范围里把它标为 `"cash_equivalent"`（最多一只）。它**不是 AI 的投资目标**：AI 不能把它写进目标组合，
  账户快照里它的市值直接计入 `account.cash`（另列在 `cash_equivalents`）。所以总敞口、单日风险增量额度、
  审批、每日买入额度、回撤和单日亏损的计算都与停放前完全一样。
- AI 的目标组合配置完成后，真实现金超出 1%（`keep_cash`）的部分若超过净值的 2%（`band`），自动买入 SGOV。
- AI 当天有过买卖时，现金等到下一个交易日再停放（`min_idle_sessions`，默认 1；设 0 则立即停放）。本地模拟盘按每笔 0.1% 手续费、再按分钟最高价加滑点和点差成交，SGOV 一进一出约 0.4%，相当于五六周的短债利息；当天可能再用的现金不值得来回付这笔钱。真实券商免佣金、SGOV 点差约 0.01%，等一天只少约一天的利息。
- AI 要买入证券而真实现金不够时，先卖出刚好够用的 SGOV（加上 1% 现金缓冲），成交、新快照确认后，
  买入再走一遍原有的全部风控和审批检查。
- 停放买卖是普通限价单，走同一条提交路径（STOP、独立监控、交易时段、同一时间只有一个未结订单、每日提交上限）。
- 本地撮合也按已配置的现金等价物分类检查：停放买单不套用普通投资的单名／总敞口上限，回撤暂停不禁止现金停放；
  普通证券买单的风险敞口不计现金等价物持仓。实际现金、保留资金、费用和 `keep_cash` 缓冲仍逐次检查，
  包括部分成交及重启恢复；把普通证券订单标成 `cash_sweep` 不能绕过限制。
- 现金停放是系统的现金管理，不属于某次 AI 决策：停放买单**不会**因为它之后的 AI 决策过期而撤单。（背景：2026-11-05 至 11-09 的本地账户里，约 50 笔 SGOV 停放单从未成交，11-06 还用光了当天的买入提交额度。原因是当时本地撮合在成交时对停放买单套用了普通投资的单名 10%／总敞口 70% 上限，第一根可成交的分钟线就撤单，且撤单事件没有原因字段；已在本版本修复，见上一条。下面的规则是额外的防护。）现在停放买单仍遵守普通挂单等待时限（过久未成交会撤单重报价，不一直挡住后续复核）；有新的 AI 目标生效时让路撤单（`cash_parking_superseded`）。被撤后不必等下一次 AI 决策：空闲时（没有生效中的 AI 配置）会重新停放。每个交易日最多 3 笔停放买单（`SWEEP_BUYS_PER_DAY`），绝不挤占 AI 自己的买入提交额度。不能停放的原因每天每种只记一次（`cash_sweep_unavailable`）。基金经理决策和开盘前研究的上下文都带有 `cash_management`（停放代码、缓冲、等待规则），知道 SGOV 由系统处理、算作现金。
  `local_risk_canceled` 记录具体 `reason`（如 `position_limit`、`exposure_limit`、`cash_buffer`、`insufficient_cash`），
  旧事件没有原因字段时不能仅凭 `canceled` 状态推断原因。
- 分仓撮合与账户快照使用同一套持仓归属规则：账户外持仓不计入授权资金的净值、投资敞口或现金缓冲基数，
  不得借此放大单名额度，也不能挤占正常分仓买单的额度。冻结的运营者持仓即使与投资名单同名，也不能被待成交买卖单动用；
  这类取消记为 `external_holding`，当前名单外的其他订单记为 `ineligible_asset`。
- 局限：每次买入前多一笔卖出，占用卖出额度；盘中卖出（包括止损）后的现金按上面的规则等到下一个交易日才停放；
  SGOV 本身有极小的价格波动和每月分红，模拟盘的分红按本地撮合规则入账。设 `FUND_CASH_SWEEP=false` 可关闭，
  `FUND_EXCLUDE_SYMBOLS=SGOV` 也会关闭它。

出厂投资范围同时加入了 `IEF`（7–10 年美债）、`TLT`（20 年以上美债）和 `GLD`（黄金），让组合在股市下跌时有分散的选择，
而不是只能减仓；`treasury_duration` 组限制两只美债合计不超过 30%（在默认单只 10% 的上限下不会触发）。

## 全自动／半自动与例外审批

在 `.env` 选择，默认全自动：

```dotenv
FUND_AUTOMATION_MODE=full
FUND_APPROVAL_MODEL=deepseek/deepseek-flash
```

`full`：经理自主投决，超出自动额度或市场压力下的买入交给**独立风控 AI** 复核；`semi`：这些例外仍由人工审批。
两种模式的自动额度、量化硬上限、STOP、独立监控、资金和凭证权限均不改变；全自动不代表每个请求都会获批。
`FUND_APPROVAL_MODEL` 单独选择风控模型，默认 `deepseek/deepseek-flash`；可以自行改成其他支持的 `提供方/模型ID`，不随基金经理模型切换。
它拥有独立的指令和本次请求上下文。该变量覆盖 `config.json` 的 `automation.model`；变量留空沿用配置，配置字段缺失或为 `null` 才回退到经理模型。
使用其他提供方须配置对应的 API key；启用每日费用上限时，还须配置该模型的 token 费率。
它能使用只读研究工具核验证据，不能下单、改目标、放宽额度、划转资金、改凭证或清除 STOP。其调用和费用计入现有预算。
环境修改需重启加载，`bash scripts/fund-logs.sh status` 显示实际启动时加载的模式；旧进程未记录模式时不会假装已经全自动。
模式改变会通过策略摘要使旧目标与审批失效，经理重新评估。历史实验仍不假设有人或模型同意例外。

原则：**硬上限由代码执行，审批不能放宽；降风险永不等待；只有例外买入需要所选审批者。**

- **卖出／减仓**（本账户只做多，卖出一定降低敞口）：始终自动执行，包括清仓和回撤降仓。
- **自动买入额度**（`approval` 段）：以纽约交易日为单位，总敞口相对开盘可提高 `auto_daily_exposure_increase`
  （默认 25%），且当日观测到的买入现金流不超过净值的 `auto_daily_buy_turnover`（默认 40%）。
  额度内的买入直接执行；额度不足时只执行能放进额度的部分。
  所以“有待审请求，同时发生买入”不一定是绕过：待审的是超出额度部分，自动部分可以先执行。
  买入现金流包含手续费；下单名义预算先预留配置的费用缓冲，本地至少使用模拟券商已知费率，避免名义金额刚好达标而含费支出越界。
- **需要审批的例外**：超出上述额度的买入，或任何处于市场压力状态下的买入。
  此时生成**一份覆盖整个调仓计划**的审批请求，而不是逐笔审批。
- **硬性额度**：即使批准，当日敞口增幅也不超过 `max_daily_exposure_increase`（默认 50%），
  买入现金流不超过 `max_daily_buy_turnover`（默认 100%），并且仍受全部量化约束和硬上限限制。

举例：全部现金建仓到 70% 时，第一天自动建到约 25% 敞口，第二天、第三天继续自动建仓，无需任何人工；
如希望更快，所选审批者批准一次可在当天建到 50% 的硬性额度内。全自动自动完成例外复核，半自动才会请你处理。

AI 只回答批准／拒绝及理由，必须原样绑定本次请求编号和摘要；不能修改范围。超时、格式错误、请求错配或证据不足都不会自动放行。
失败至少等 5 分钟，默认每请求最多 3 次尝试；尝试和运行租约保存在账本中，重启不清零。达到上限后请经理重新评估。
最后一次尝试仍持有有效运行租约时，重启后的进程继续等待；它明确失败或租约到期后才按重试耗尽请求重新评估。
AI 批准后本轮不直接下单，下一轮刷新账户、报价和全部硬风控；AI 拒绝则停止该目标继续买入并请经理重新评估。
Telegram 分别显示“AI 复核中／批准／拒绝”，批准通知明确不是成交；半自动保留现有人工回复审批流程。
待审批通知在入队、领取发送任务和构建完消息后复核请求状态、摘要、账户、策略及有效期。
已经批准、拒绝、替换或过期的请求不会再补发“待审批”；其原始记录、批准／拒绝结果通知仍保留。
过滤原因记在通知投递记录的 `last_error=approval_*`，不修改交易或审批状态。

审批请求列出：触发原因、拟买入证券及各自的权重上限和限价上界（参考限价 ±`price_collar`，默认 2%）、
批准后最高敞口、当日买入现金流上限、构建后组合的波动和 ES、市场压力详情、AI 的完整理由，
有效期不超过 `valid_minutes`（默认 60 分钟）、目标有效期或本交易日收盘。
同一计划内价格在领口内变化、重复轮询都复用原请求；出现新证券、更高权重、新触发原因或价格超出领口才生成新请求。
原请求的现金流上限仍足以覆盖当日已支出及当前剩余整股买入（含费用预留）时，净值小幅变化不会仅因理论硬额度变化而换号。
复用不修改原请求的金额、摘要或有效期；实际需要超过原现金流授权时仍重新审批。
一份批准可覆盖该计划内的多笔买入，每次使用都在预留同一事务内复核范围并记录 `approval_used`。
触发原因覆盖硬额度内可到达的整份剩余计划，避免后续一腿越过第二个自动阈值而对同一范围重复审批。
替换目标、改变风险策略或过期都会使旧批准失效。
新订单把独立计算的自动额度、审批编号和放行来源保存到 `fund_order_authority` 与提交事件；
`decisions YYYY-MM-DD --event N` 显示自动／AI／人工／系统现金管理来源，以及该计划关联过的审批请求。
旧记录缺少凭证时明确缺项，不把经理理由当作审批事实。授权在发送前、本地接受和成交事务中复核；
撤销／过期会停止后续模拟成交，已成交部分保留。Paper 已在途订单仍以券商撤单和成交回报为准。

查看后再复制准确的请求 ID 和 digest；命令只记录批准，交易进程在下一迭代重新风控后才提交：

```powershell
.\scripts\run_autonomous_fund.ps1 -Mode approvals -RunDir artifacts/fund-local
Get-Content artifacts/fund-local/approvals.json -Encoding UTF8
.\scripts\run_autonomous_fund.ps1 -Mode approve -RunDir artifacts/fund-local -ApprovalId <request-id> -ApprovalDigest <reviewed-digest>
.\scripts\run_autonomous_fund.ps1 -Mode reject -RunDir artifacts/fund-local -ApprovalId <request-id> -ApprovalDigest <reviewed-digest>
```

不批准则超额部分不下单，额度内的部分不受影响。拒绝会停止该目标，等下一次正常复核；已经提交的订单须通过撤单流程处理。
STOP 激活时不能批准开启交易，但可以撤销已有批准，未成交部分进入撤单流程。历史实验不假设人工或模型同意，超额买入仍会挂起。
审批命令可以在运行进程持锁期间使用，不需要模型或券商 Key。

**手机审批**：独立监控进程把审批请求发到 Telegram，你直接**回复这条消息「同意」或「拒绝」**即可；
也可发送「同意 代码」／「拒绝 代码」（提醒里的 6 位审批代码），只有一个待审请求时直接发「同意」也行。
机器人会回复处理结果；交易进程在下一次迭代重新通过全部风控后才执行。安全约束：
只接受 `FUND_TELEGRAM_CHAT_ID` 这个会话；私聊默认由聊天本人审批，群组必须用 `FUND_TELEGRAM_APPROVER_IDS` 列出审批人；
早于请求创建时间的消息、STOP 期间、过期或已被替换的请求一律拒绝；批准与 CLI 完全相同地绑定摘要和范围，不放宽任何硬上限；
每条指令记入账本（`telegram_command`，授权人 `telegram:<用户 ID>`）。发送「状态」可查看监控、待审批数、分仓净值和周报状态。
控制了你的 Telegram 账号就等于控制了审批，请开启 Telegram 两步验证；设 `FUND_TELEGRAM_APPROVALS=off` 可退回只通知。
希望所有买入都人工确认的运营者可把 `auto_daily_exposure_increase` 设为 `"0"`。

## 离线验证：用真实历史数据回放风控

`validate-risk` 把固定的 AI 目标权重逐日送入同一套量化风控，在真实收盘价上回放，比较“未风控持有”与“风控后”：

```bash
python -m scripts.autonomous_fund.run validate-risk --run-dir artifacts/validation --data-dir data --targets SPY=0.1,TLT=0.1,GLD=0.1
```

回放无前视：第 t 天收盘时只用到 t 天及以前的收盘价决定权重，赚取 t→t+1 的收益；缺数据的日子跳过，不补数；
按换手收取 10 基点成本；结果写入 `validation_risk.json`（含逐日敞口、约束和事前波动）。`--data-dir` 下每个证券一个 CSV，
支持 Yahoo 导出（Date/Close）或分钟线（time/close，自动取每日最后收盘）。

用仓库自带的真实数据（`data/`：2019 年 SPY/TLT/GLD/IEF/DJP 日线；`data/XYZ_1Min.csv`：美国指数期货 2020-01 至 2020-04 分钟线，含新冠暴跌）得到（2026-11-02 改用新的相关性估计后重跑，三组结果不变：前两组只有一个证券，不涉及相关性；2019 年没有约束触发。离线回放不含情景压力测试）：

| 场景 | 未风控 | 风控后 |
|---|---|---|
| 2020 暴跌，70% 单一指数，只开波动率目标／ES／回撤分档 | 收益 −8.5%，最大回撤 25.0%，年化波动 45.4% | 收益 −6.2%，回撤 12.2%，年化波动 13.4%（目标 12%，暴跌初期 EWMA 有滞后） |
| 2020 暴跌，同上，全部默认（含单名风险预算） | 同上 | 收益 −3.1%，回撤 6.3%，年化波动 7.4% |
| 2019 平稳，5 只 ETF 各 10%（出厂配置） | 收益 5.34%，回撤 1.25% | 收益 5.23%，回撤 1.26%，没有任何约束触发，成本仅为再平衡费用 |
| 2019 平稳，SPY 25%/TLT 15%/GLD 15%/IEF 10%/DJP 5%，按个股预算 | 收益 9.56% | 收益 7.57%，回撤反而略高：单名预算把 SPY 压低了 181 天 |
| 同上，按 ETF 预算（现在的默认） | 收益 9.56% | 收益 9.39%，回撤与波动相同 |

结论：波动率目标和回撤分档在真实暴跌中把回撤减半以上；平稳市场几乎没有成本。回放还发现单名风险预算对宽基 ETF 过严，
因此新增 `max_etf_name_risk`（默认 5%），个股仍为 2.5%。这些都是机制验证，不含 AI 的选股、盘中止损或日内跳空，
2019 一年和 2020 一个季度的样本也不能代表所有市场环境。这些数字由 `tests/test_autonomous_fund_validation.py` 固定为回归测试。

## 影子 A/B：验证 AI 的自我优化是否有效

每天的复盘备忘和记分卡会改变 AI 之后的决策，但“改了”不等于“改好了”。`validation` 段开启影子 A/B：

- 每个交易日的第一次决策后，基金经理基于**同一份研究**再做一次对照决策（`shadows_per_session`，默认 1 次）：
  一组带复盘备忘与记分卡（memo 组），一组不带（baseline 组）。只有当前“冠军”组的决策会交易，另一组只记录（`shadow_decision`）。
  两组看到的市场、研究、风控和约束完全相同，也都看不到自己属于哪一组；对照组失败不会影响交易或触发退避。
- 每次盘后复盘之后，用已完成收盘价给两组决策打分：从两组结果都已入账后的首个收盘起持有一个交易日，计算相对 beta 匹配的 SPY 的超额收益。
  每个起算收盘日最多计一对，按日求差（memo − baseline），计算均值、t 统计量和胜率（`learning_evaluation`）。
- 至少 `min_pairs`（默认 20）个交易日、且 |t| ≥ `switch_t_stat`（默认 2）时才切换冠军：memo 组显著更差就改由 baseline 组交易并通知你；
  之后若 memo 组显著更好再切回。样本不足或不显著时维持现状。
- 成本：每个交易日多一次基金经理调用，计入每日模型预算；预算不足时跳过对照组，不影响交易。

局限：日度配对差可能有自相关，20 个样本的 t 检验只是谨慎的门槛，不是严格的因果证明；
对照组仍然是同一个模型，只是去掉了学到的经验，所以它检验的是“复盘学习这一环”是否有价值，而不是模型本身的选股能力。

## 退化监测与回滚：生效的东西变差了怎么办

阈值事先定好（`degradation.py`），每次盘后复盘后检查一次。**短期亏损或盈利本身不会触发任何动作。**

| 对象 | 原有规则（不变） | 新增的退化规则 | 触发后 |
|---|---|---|---|
| 学习对照（看备忘 vs 不看） | 全部记录的配对 t 达到 ±2 才切换 | 最近 20 个交易日的配对 t 达到 2 且不利于正在交易的一组 | 换回另一组交易（上一个生效版本），Telegram 写明“退化回滚” |
| 组合构建（AI 权重 vs 风险预算，`auto` 模式） | 同上 | 同上 | 同上；手动指定的模式不会被切换 |
| 已验证因子 | 样本外 IC 转为反向就退役 | 无（已有） | 登记表记录退役 |
| 换手 | 无 | 最近 5 个交易日的日均换手高于之前至少 40 个交易日的 95% 分位 | 基金经理的最短复核间隔加倍，少做调整；止损、止盈和其他保护性卖出不受影响。日均换手回到之前的中位数后恢复 |

切换只影响之后的决策和调仓；进行中的订单仍按原有的执行规则走完或撤单，不会重复下单。
仓位、beta 和风格暴露的上限在每次调仓时由风控强制执行，持仓漂移在下次调仓时纠正，所以不另设退化规则。
每次切换和换手保护的开关都记在账本（`learning_evaluation`、`construction_switched`、`degradation`）和实验登记表里。

## 交易价值判断：这笔买入值不值它的成本

基金经理的决策上下文里有 `trade_value`（`trade_value.py`）：一次买卖来回的成本，等于手续费加滑点再加报价买卖价差，
本地模拟盘按 `fee_rate` 和 `slippage_bps` 计算，Alpaca Paper 按 0 手续费、5 个基点滑点估计。

**研究想法被证明有预测能力之前，这只是给基金经理看的信息，不拦截任何交易。** 想法记分卡的结论变成 `informative` 之后
（至少 30 条已打分、命中率显著高于抛硬币和“总是看涨”、Brier 分数低于 0.25），调仓时对每一笔加仓检查：

- 这个证券今天有研究想法时，用想法的把握度所在分组的实际命中率 p（这一组至少 10 条已打分，否则用全部想法的命中率），
  乘以已打分想法在各自期限内的平均涨跌幅，得到预期优势 =（2p − 1）× 平均幅度；看跌或跑输的想法取负号；
- 预期优势不超过来回成本（2 ×（半个买卖价差 + 手续费 + 滑点））时，这笔加仓不执行，持仓保持在当前权重，账本记 `trade_value_held`；
- 减仓、卖出和保护性卖出永远不受限制；今天没有研究想法的证券无从估计优势，不做判断。

**买不起一股的证券**：系统只买整股。一个证券最多能占的仓位是单只上限和它所在每个分组上限中最小的那个
（例如杠杆、反向 ETF 每只 5%）。盘前研究和基金经理的上下文里有 `affordability`：

- `unaffordable`：一股的缓冲买入限价就超过这个上限，任何目标都买不进。告诉 AI 不要计划买入；已持有的照常持有或卖出，研究也照常；
- `coarse`：买得起，但上限内最多只能放下 4 股或更少。目标权重会向下取整到整股，所以低于一股权重的目标一股也买不成，
  两档之间的目标只买到下面那一档，列出一股的权重和最多几股，让 AI 给出能成交的目标。

名单不是固定的：每次盘前研究和每次决策都按当时的账户净值重新判断。价格用最近一个已完成交易日的收盘价；
一股的权重离上限不到 10% 的证券（买得起与买不起的分界附近），在本地模拟盘和 Alpaca Paper 里改用当前报价再算一次，
所以盘中跌到买得起、或涨到买不起，下一次决策就会反映（`basis` 写明用的是收盘价还是实时报价；报价读不到时沿用收盘价）。
实时报价使用执行侧的卖一价（ask）；可买股数复用下单的 Decimal 计算，计入当前 `limit_buffer` 和向上取整到美分的限价。
例如净值 10,000、单只上限 10%、ask 为 999.50、限价缓冲 0.1% 时，买入限价为 1,000.50，提示为买不起一股。
展示的一股价格与权重保留原始报价，目标权重还须覆盖限价缓冲。收盘价回退结果只是参考，现金、组合敞口及成交资格仍由下单前检查确认。
历史回放只用收盘价，结果可以重现。下单本身一直按实时报价和整股计算，永远不会超过上限。
买不起的名单变化时，Telegram 通知你（每个纽约交易日最多一次，避免在分界附近来回跳时反复打扰）；
全部恢复时会说“现在都至少买得起一股了”。要交易买不起的证券，需要提高授权资金或单只／分组上限。

## 运行验收报告

本地或 Paper 运行一段时间后，用 `acceptance` 从账本生成两份互相独立的验收报告（数据都在 `acceptance.json`）：

- **运行验收**（`acceptance.md`）：系统是否可靠地运行，标准见下表；
- **投资能力验收**（`investment_acceptance.md`）：扣除费用后有没有超额收益，标准见本节后面的“投资能力验收”。

运行验收通过不代表投资能力验收通过，反过来也一样。命令：

```bash
python -m scripts.autonomous_fund.run acceptance --run-dir artifacts/fund-local
```

| 标准（`validation.acceptance`） | 默认阈值 | 含义 |
|---|---|---|
| `min_sessions` | 20 | 有账户观测的已结束交易日数 |
| `min_iteration_ratio` | 0.9 | 各交易日实际完成的迭代数 ÷ 应完成数的中位数（反映掉线、卡住） |
| `max_watchdog_stops` | 3 | 独立监控或服务监督写 STOP 的次数 |
| `max_unresolved_intents` | 0 | 仍未结束的委托预留（含无法确认的提交） |
| `max_fill_details_unavailable` | 0 | 券商只给累计成交、缺明细的次数 |
| `max_model_failure_rate` | 0.2 | 模型调用失败比例 |
| `min_review_ratio` | 0.9 | 完成盘后复盘的交易日比例 |
| `max_mean_slippage_bps` | 25 | 成交价相对首次提交限价的平均不利滑点（基点） |
| `max_bot_crashes` | 0 | 绕过所有保护导致进程退出的崩溃（`bot_crash`）；记账错误和自动恢复次数只作为参考数据列出 |

报告还列出人工干预次数（审批、复位、补单、出入金、Telegram 指令）、保护性卖单、改价撤单、追价封锁、回撤与单日亏损闸门、
最新的影子 A/B 结论等。它只证明运行层面的可靠性，不证明盈利；本地虚拟账户也不能代替券商 Paper 的证据。

**业绩证据：是能力还是运气**（`performance.py`，报告的 `performance_evidence`）：只用账本里每个交易日最后一次净值和
同时记录的 SPY 价格（跨越出入金调整的那一天不计收益，缺数据不补）：
- 概率夏普比 PSR：考虑样本长度、偏度和峰度后，真实夏普比大于 0 的概率；
- 去试错夏普比 DSR：同上，但门槛换成“试过 N 种配置时单靠运气能得到的最好夏普比”，N 是所有试过的配置之和，在
  `configurations_breakdown` 里分别列出：交易过的提示词版本数 × 风控配置数，加上测试过的因子表达式数（包括未通过的），
  加上组合构建对照（运行过就加 1）和学习对照组（影子 A/B 运行过就加 1），不会少于原来的算法；
- 最短记录期 MinTRL：按目前的夏普比，要多少个交易日才能有 95% 的把握说它大于 0；
- 相对 SPY 的回归：beta、年化 alpha 和 alpha 的 t 值，以及用 **Newey-West**（Bartlett 核，滞后
  `floor(4·(n/100)^(2/9))`）稳健标准误算出的 alpha t 值，收益有自相关时它更小；
- 年化收益和波动、最大回撤、Sortino（只用下行波动）、**按自相关修正的夏普**（Lo 2002：用到 Newey-West 滞后阶数为止的自相关，
  更高阶记为 0；正自相关会降低夏普），每项都注明交易日数。

**事先定义的基准**（`config.json` 的 `performance.benchmarks`）：默认 `spy`（100% SPY）和 `risk_matched`
（60% SPY + 40% SGOV，每个交易日再平衡）。每个基准的 id 是名称加定义的哈希（如 `risk_matched-1a2b3c4d`），
写在启动记录里；改了定义就是新 id，旧定义的结果继续列在报告里（标为“旧定义”），不会被新定义追溯替换，
不能事后挑最容易战胜的基准。基准收益用账本里每个交易日最后的价格记录计算，再加上为基准证券记录的分红和拆股
（`benchmark_action`；本地模式每个交易日从 Yahoo 查一次最近 40 天的公司行为），所以是总收益：SGOV 的收益几乎全是月度分红，
只看价格会让基准过于容易战胜。数据源不提供公司行为时（如 Alpaca paper），报告写明“分红未计入”。
已记录的公司行为按日期计算分红时的持股数，分红现金不会因之后的拆股而放大或缩小，也不假定现金自动再投资。
例如原来一股 100，先分红 2，再一拆二，期末每股 49，则股份价值 98 加现金 2，总收益为 0。
同日先处理拆股，再按拆股后的每股口径处理分红；录入顺序不影响结果。起点当日的行为不重复计入，终点当日的计入。
每个基准给出年化超额收益、跟踪误差、信息比率和 alpha（普通与 Newey-West t 值）。

**两种净收益口径**：

- 账户净收益：账户净值的变化，已经包含成交费用和相对成交价的滑点；
- 系统净收益：再扣掉区间内的模型费用（每次调用记录的 `cost_usd`）和数据订阅费（`performance.data_costs_usd_per_month`，
  `FUND_DATA_COSTS_USD_PER_MONTH`，默认 0，按每月 21 个交易日分摊）。任何一个区间有未定价的模型调用，或数据费用设为未知（null），
  系统净收益就显示“未知”，不当作 0。
  调用中断、没有返回 token 用量或用量为空时，缺失的 `cost_usd` 仍是未知；只有明确记录的零费用、脚本测试调用及本地答案缓存可计为零。

**分阶段资金就绪度**（`capital_stage`）：只有在运行验收通过、至少 60 个交易日且不少于 MinTRL、PSR ≥ 0.95、DSR ≥ 0.90、
alpha t ≥ 1.65（单边 95%，普通 t 值和 Newey-West t 值取较小者）、且没有触发回撤上限时，才给出 `eligible_stage_1`（最多投入计划资金的 10%）；否则为 `paper_only`
并列出每一条不满足的原因。25% 和 50% 两个阶段需要实盘记录满足同样的检验。**这只是报告**：本应用没有实盘模式，
任何真金白银的一步都需要你明确授权和单独审核的执行路径。

**投资能力验收**（`investment_acceptance`，V2 4.4）：结论只有三种：`insufficient_evidence`（样本不足，尚不能判断）、
`edge_not_shown`（尚未证明有扣费后的超额收益）、`preliminary_edge`（初步显示扣费后的超额收益）。没有“已证明”这一档：
模拟盘成交偏理想、样本仍短，通过也不保证未来盈利。

| 标准 | 必需 | 要求 |
|---|---|---|
| 交易日数 | 是 | 至少 60 个交易日，否则结论为样本不足 |
| 相对 SPY 的 alpha | 是 | 扣掉 beta 后的 alpha t 值 ≥ 1.65（普通 t 与 Newey-West t 取较小者） |
| 相对风险匹配基准 | 是 | 年化超额 > 0，且 alpha t ≥ 1.65（默认 60% SPY + 40% SGOV） |
| 扣模型和数据费后 | 是 | 系统净收益仍跑赢风险匹配基准；有未定价的调用时为“未知”，不通过 |
| 交易成本翻倍后 | 是 | 已实现交易成本加倍后，相对风险匹配基准的年化超额仍 > 0；成交、费用或到达价证据不全时为“未知”，不通过 |
| 去试错夏普（DSR） | 是 | ≥ 0.90，试错数包括所有提示词、风控配置、因子、对照实验 |
| 稳定性 | 是 | 记录分成前后两半，两半的 beta 调整后日均收益都为正：只在一段时间有效不算稳定 |
| 学习对照 | 参考 | 看备忘组减对照组的配对 t ≥ 2（第四关）；未达到时写“未证实改善” |
| 研究想法 | 参考 | 打分结论为 informative |

**成本敏感性**：模拟盘的成交偏理想，刚好跑赢成本的超额可能并不存在。已实现交易成本按每笔订单计算：手续费加上
成交价偏离到达价的**绝对值**乘以股数（有利的偏离也算成本；同一订单的对账记录代替逐笔回报）。
只计入风险匹配基准与账户都有数据的净值区间内记录的交易，并按每段期初净值折算成年化比例。
报告“成本敏感性”一节列出成本 1 倍、2 倍、3 倍时相对风险匹配基准的年化超额，2 倍时仍为正才通过。
投资验收只在相邻两个已结束的 NYSE 交易日都有账户估值时计算单日收益，缺估值跳过的区间数会列在报告里。
决策记分卡的每个期限也给出 `mean_net_excess_return_2x_costs` 和 `_3x_costs`（按估算成本的 2 倍、3 倍）。

报告同时列出业绩证据、两种净收益、事先定义的基准、分阶段资金就绪度，以及全部记录的 AI 调用价值。

## 研究网络与数据边界

研究员的原生网页工具会拒绝解析到私有、回环或保留地址的网站（防 SSRF）。OpenClash 等代理的 Fake-IP 模式会让所有域名解析到
`198.18.0.0/15`，这类研究请求因此全部失败。`check` 命令现在会报告 `research_network`：
逐个解析 SEC、Yahoo、Reuters、美联储等研究站点，标出 `fake_ip_dns` 或 `private_answer` 并给出处理建议。

可在 `config.json` 设置 `"research_network": {"resolver": "doh"}`：网页工具改用 DNS-over-HTTPS（默认 `https://1.1.1.1/dns-query`）
获取公开地址，代理仍按规则转发连接；SSRF 检查保持不变，解析到私有地址仍会被拒绝。更稳妥的做法仍是让服务器不走 Fake-IP。

研究用 DuckDB 仍禁止访问账本、配置和密钥，但现在可以读取研究工具自己的下载目录（`cache/browser`、`cache/research`），
下载的 CSV／Parquet 可以直接用 SQL 分析。

## 模型调用预算与失败退避

`model_budget` 段约束推理成本，避免“失败 → 下一分钟重跑”的付费循环：

基金经理每次通过校验的复核都会记为一次有效决策；维持已有目标也计入，但不等于新增交易。
研究员、反方审查、影子对照和盘后复盘也会消耗 Agent 调用预算，不能把总调用次数当成有效投资决策次数。
调仓通知只在每天首次复核、证券增删、权重变化至少 1 个百分点或交易价位变化时发送，
所以多次复核只有一次通知可能是正常行为。按日期核对可用 `bash scripts/fund-logs.sh decisions YYYY-MM-DD`。
日常时间线只显示理由开头。若开头都是账户核对，可在命令末尾加 `--event 123`（把 123 换成该日时间线中的事件编号），
展开这一条决策的完整模型原文，例如 `bash scripts/fund-logs.sh decisions YYYY-MM-DD --event 123`。
只从当前配置账户、指定纽约日期选择该事件；编号不匹配会报错，不会改查其他日期或账户。该命令不修改账本、不会调用模型或发送通知。
新决策同时保存 `decision_basis`，按实际接受的计划编号关联本次输入的上轮计划、反方原文与其源调用／时间、近期成交。
`--event` 一并展示这些内容，标注反方属于模型判断；审查可能复用，保留原始来源。旧记录未保存这些关联时明确说明缺项，
不会靠相邻时间猜配反方意见。诊断写入失败仅报告 `decision_basis_unavailable`，不阻止已通过校验的计划继续执行。
事件判断的“是否漏判”和经理的“是否改组合”分别显示：判断需要复核时，`miss=false` 仅表示没有漏判，不能据此说经理没改组合。
静默跳过仍遵守原触发条件，下一次检查会落在最短复核间隔与最长静默期限中较早的时间，
不会因最后一次静默检查把基金经理再次推迟到最长静默期限之后。没有新增模型、次数上限或投资限制。

- 本地／券商模拟盘中，只有基金经理调用或决策验证失败（超时、结构化回答无效、决策过期或超限）后，
  按 `failure_backoff_minutes`（默认 5、15、60 分钟，之后保持 60 分钟）延后下一次复核，成功后清零；
  连续失败次数、失败角色与下次时间持久化，重启不会绕过经理退避。
  研究员的盘前异常只记录／通知，不阻止盘中经理评估。升级时根据匹配的失败事件迁移旧版仅研究员失败的共享退避，
  不清空 STOP、预算、订单、审批或已接受目标；归属不明的旧退避保持不变。
  历史回放保留先研究、验证日期证据、再经理决策的流程及其失败退避，不能把历史研究缺失当成已验证证据。
- 每个纽约交易日最多 `max_agent_runs_per_day`（默认 60）次 Agent 运行，其中 `reserved_review_runs`（默认 4）
  留给盘前研究与盘后复盘。日内额度用完后不再发起新决策，已接受的目标继续执行，次日自动恢复，
  并发送一次 `model_budget_exhausted` 通知。
  盘中一次基础评估只需预留一次经理调用；盘前、盘后及可选评议／影子评估继续计入实际调用预算。
- AI 指定的 `next_review_at` 不早于 `min_review_minutes`（默认 15 分钟）；目标执行窗口也按此下限计算。
- **模型费用核算**：每次模型调用记录时，按 `FUND_MODEL_PRICES_JSON` 的价格（`input`、`output`、缓存命中的 `cached_input`，
  不填缓存价时按普通输入计，偏保守）算出费用，和 token 一起记在日志里。`fund-logs.sh` 和每日报告显示：今天、近 30 天、
  日均和按此速度一年的费用，以及**一年费用占净值的比例**——AI 每年至少要跑赢基准这么多才能打平模型费用。
  状态与周报把未定价原因分为用量缺失、用量不全、用量格式异常、缺少费率。提供方没有返回 usage，或失败／超时未获得完整用量时，
  仍计入未定价调用，不能靠补单价或填零假装已核算。新调用保存原因，旧调用按原始用量证据解释，不改写历史费用。
  调用次数、token、未定价次数和费用使用同一个 30 天窗口，窗口外及未来调用不计入；
  周报单独限制在本周、选中复盘的截止时间内，所以全历史 SQL 的数量可能不同。
  最近没有调用时不会把旧记录误报为缺少单价。`FUND_MAX_DAILY_COST_USD` 设定每个交易日的费用上限：到达后当天不再发起新决策、反方审查和盘前研究
  （已有目标、止损止盈照常执行，盘后复盘照常运行），并通知一次；设置上限时必须为每个在用的模型填好单价，否则启动时报错。
- **跳过无变化的定时复核**（`skip_quiet_reviews`，默认 `true`，`FUND_SKIP_QUIET_REVIEWS`）：到了 AI 自己定的复核时间，
  只有同时满足以下条件才不调用模型（记录 `review_skipped`，`min_review_minutes` 后再检查）：没有待处理的盯盘唤醒
  （提醒、大幅波动、市场压力、新闻命中）；没有暂停加仓；上次模型决策在同一纽约交易日、距今不到 `max_quiet_minutes`
  （默认 120 分钟，`FUND_MAX_QUIET_MINUTES`，取值 `min_review_minutes`..1440）；该决策的调仓已完成（`allocation_complete`），
  且持仓与完成时完全一致（现金管理 ETF 视为现金）；已保存的盘前研究仍是它看到的那一份。任何一条不满足就照常调用基金经理。
  已设置的止损、止盈和价格提醒在跳过期间照常生效；提示词告诉基金经理这一规则，让它用提醒和 `news_watch` 安排需要更早唤醒的情况。
- **盘中事件判断**（`triage` 段，`FUND_TRIAGE`／`FUND_TRIAGE_MODEL`，2026-11 起）：把盯盘、事件判断、投资决策分给三方：
  每分钟的价格、止损止盈、挂单和风控由程序负责，不调用 AI；普通新闻和价格异动先由快速模型（默认研究员模型 Flash）判断；
  买卖和调仓只由基金经理（Pro）决定。
  起因是 2026-11-05 至 11-09 的账本：5 天里 1031 次新闻触发让基金经理每到 15 分钟下限就被叫醒（每个交易日 15～21 次），
  “无变化跳过”一次也没生效；11-09 的 19 次基金经理决策没有一次改变组合，盘中决策约占模型费用的 93%。
  - **只筛软触发**：等待处理的唤醒全部是 `news` 或 `price_move` 时才先问快速模型；市场压力、AI 自己设的价格提醒、
    止损止盈成交后等其他原因照旧直接叫基金经理。今天还没有模型决策、或距上次决策已到 `max_quiet_minutes`（默认 2 小时）时
    也不筛，直接叫基金经理。快速模型调用失败、格式不对或费用预算用完时，同样照旧叫基金经理。
  - **快速模型看什么、答什么**：最近的触发（新闻标题、来源、时间、相关证券；价格异动的参考价和现价）、持仓、
    基金经理当前的目标、理由和关注词；没有工具，不联网。它只回答要不要现在叫基金经理（`escalate`）、重要程度、
    相关证券和理由，不选交易。它有自己的调用计数（`triage_runs`），不占基金经理的每日调用次数，费用计入每日费用上限。
  - **默认直接生效**（`mode: auto`，`start: enforce`）：快速模型说“不需要”就不叫基金经理，清掉这批触发，回到基金经理自己定的
    复核时间（到点时仍按“无变化跳过”规则判断）；之后 `min_review_minutes` 内新来的新闻攒成一批再判断。说“需要”就叫基金经理，
    并把理由放进它的上下文（`event_triage`）。
  - **抽查和自动退回**：每 `audit_every`（默认 5）次“不需要”仍照常叫一次基金经理，而且基金经理看不到快速模型的判断（盲测）；
    那次基金经理改了组合（增删证券或权重变动至少 1 个百分点）就记一次漏判。抽查满 10 次后，漏判率超过 `max_miss_rate`
    （默认 15%）就自动退回影子运行，并通知一次（`triage_rolled_back`）。
  - **影子运行**：基金经理每次都照常被叫、看不到判断，每次“不需要”都打分。最近 `window`（默认 40）次“不需要”里，
    漏判率的单侧 95% 上限（Clopper-Pearson）不超过 15%（40 次里最多漏判 2 次）时自动重新生效，并通知一次（`triage_enforced`）。
    想先影子验证再生效，把 `start` 设为 `shadow`。`mode: shadow` 只打分不生效，`enforce` 一直生效（仍抽查、不退回），`off` 关闭。
    相同配置与模型下，`auto` 已到达的状态在重启后保留。
    筛选模型、提示词／schema、经理决策版本或筛选政策变化时创建新 `triage_profile`，按当前 `mode`／`start` 重新开始，
    不沿用旧模型的漏判样本或资格。`triage_profile_changed` 保留前后来源及旧样本；当天调用与费用预算不重置。
    老版本缺少来源绑定时归档旧样本；`auto` 保留已知的生效／退回状态，不因迁移而把退回状态自动重新开启。
  - 账本记录 `event_triage`（每次判断和动作：shadow／dismissed／audit／escalated）、`triage_scored`（基金经理是否改了组合、
    是否漏判、当时的统计）和 `triage_unavailable`；`fund-logs.sh` 概况显示当前状态、最近漏判和今天的判断次数。
  - 新闻合批和恢复原计划时都会受 `max_quiet_minutes` 截止时间约束；快速模型调用期间若已到期，记录 `deadline` 并直接复核，
    保留这批触发供经理判断。风险暂停、未来或损坏的调度时间不经过软事件筛选；状态统计沿用实际打分窗口，不固定取 40 次。
    STOP 在筛选或上下文准备期间到达时，不再发起后续经理调用。
    `event_triage` 和 `triage_scored` 记录 `profile_id`；属于其他来源的迟到结果不进入当前样本。
    快速模型的提示词不进入 `prompt_version`（它不决定买卖），学习对照不受影响。
- **行情快照**（`market_snapshot`）：每个交易日由代码从已完成日线计算一次可交易标的的 1/5/20/60 日收益、20/60 日年化波动、
  相对压力基准（默认 SPY）的 60 日 beta 和相关性、相对 50/200 日均线的位置、距 252 日最高收盘的回撤和 20 日日均成交额，
  放进盘前研究和盘中决策的上下文，研究员和基金经理不必再用工具重复计算。只用已完成的交易日（历史回放同样不看未来），
  缺数据为 `null`，从不填补；预算用完时尚未读取的标的列在 `deferred`，下一轮补齐。
- **数据员**（`data_desk` 段，`FUND_DATA_DESK`，常驻服务 `lumibot-fund-desk`）：一个不调用模型、不下单的进程持续拉取整理
  资讯（开盘时每 5 分钟）、盘中行情（每 `FUND_DESK_INTRADAY_SECONDS`，默认 5 分钟）、FRED（工作时段每小时）、财报日历
  （每 6 小时）、盘前行情（交易日 04:00 到开盘）、全球市场（股指期货、VIX、美债、美元、外汇、原油、黄金、亚太和欧洲指数）、
  经济日历（需要 `FRED_API_KEY`）、日线（美东 06:00 以后）、行情快照和 SEC 财报，存到 `<账户目录>/cache/daily/<交易日>/`
  和账本的资讯表。它让着交易进程使用 Yahoo（交易进程的请求出错时暂停），过期的数据标为过期，跳空 25% 以上的标为可疑；
  资讯合并重复报道并按与持仓的相关度排序。交易进程先读这些，缺的或
  过期的才自己联网补；盘前研究和盘中决策的输入里有 `data_desk`（各数据的新鲜度、盘中行情、上次决策以来新增的资讯条数），
  三个 AI 角色在实盘模式下都有 `desk_latest` 工具，可在思考过程中随时读到那一刻最新的数据（历史回放没有这个工具，不会看到未来）。
  数据员停了交易照常，交易进程自己拉数据。见 [Ubuntu 部署](AUTONOMOUS_FUND_UBUNTU.md#数据员常驻的数据整理服务)。

`desk_latest(section="intraday")` 的 `coverage` 提供可用标的数、应覆盖数、缺少的大盘基准，以及涨跌家数的样本数和应覆盖数。
盘中决策上下文使用相同的逐标的源时间校验。报价超过 15 分钟、时间无效或超前时，标为过期。过期和可疑报价不计入涨跌家数或领涨领跌。
涨跌家数的范围是有有效涨跌幅的可交易标的，基准和交易范围外的告警、持仓单独报告。暂缺已收完的分钟线时，可限速补查关键标的一次。
补查合并已有数据时保留各标的源时间。数据台刷新失败时会披露原因，已有数据仍可按其源时间判断是否可用。

日线交叉核对通知会为待确认的公司行动列出日期和类型，并说明哪个来源缺少同日记录，或每股计价口径仍待确认。逐项明细最多显示 20 条，
其余记录可在对应纽约交易日的 `corporate_action_quality.json` 查看。
Alpaca 返回分红但币种未提供或与美元口径不同时，保留这条记录并提示币种待核对。同日有其他美元分红时，仍需确认所有金额的币种才能比较合计。
明确以美元计价的外国发行方分红可参与核对。

共享日缓存每次写入使用独立的临时文件，完整写入后再原子替换目标文件。同一进程的两个线程同时刷新同一条数据时，
不会再因共用 PID 临时文件而发生覆盖或改名失败。写入或发布失败保留上一份完整缓存，并清理本次写入自己的临时文件；
成功刷新仍改变缓存版本，让读者重新载入数据。

**每次调用值不值**（`call_value.py`）：每次模型调用记一个 `call_id` 和用途：决策复核、影子对照、反方审查、盘前研究、
盘后复盘（历史回放里还有研究）。调用的结果真正被用上时，再记一条同 id 的 `agent_outcome`：
- 决策通过校验，并记下是否改变了目标组合（增删证券，或权重变动至少 1 个百分点，与调仓通知同一规则）；
- 盘前研究保存，并记下登记了几条可验证的投资想法；
- 复盘保存，并记下给出几条可证伪预测、策略备忘有没有变；
- 影子决策可以打分；反方审查被基金经理看到。
- 事件判断实际用于升级、跳过或抽查调度，影子判断用于对照；模型身份核对结果保存到观测状态。
  若事件判断返回时强制复核期限已到，判断不再用于拦截经理调用，记录为未采用及其原因。

旧版缺少 outcome、或 outcome 写入失败，不能仅凭没有记录就认定调用被丢弃。报告区分已记录采用、明确失败与采用结果未记录；
不会按相近时间给旧调用补造采用关系。需要格式或引用纠正时，第一次无效调用仍计入未采用。
周报第二部分按用途列出：调用次数、被采用次数、改变组合的比例、每次被采用的调用和每次改变组合的费用、没被采用的调用花的钱，
以及因为没有新情况而跳过的复核和复用的反方审查。有未定价调用或采用记录不完整时，费用比例显示“未知”，不按 0 计；
旧字段 `unused_cost_usd` 保留兼容，含义是没有已记录采用结果的已知费用，不能直接解释为浪费。
不用输出字数评价研究质量。之前没有 id 的调用不进入按用途的采用统计，但其已知费用和未定价数量进入整体覆盖率，
周报及投资验收报告同时列出账本调用记录总数、有编号数、无编号旧记录数和各自已知费用。
这统计的是应用调用记录，不是提供方内部的模型请求数或账单。

按用途的已知费用去向分为已采用、失败、明确未采用、采用未知；未定价记录按同样类别另列，
不会因为有一笔费用未知就隐藏其他已知支出。明确未采用需要实际的 `valid=false` 结果，
缺少 outcome 仅标为采用未知；缓存回答和脚本模型成本为零，显式零费用与未知区分。
调用归因中的历史费用为负数、布尔值、非有限数值或不可读金额时保持未知，不生成虚假的已知支出或费用比例。
原有按用途字段及费用比例保留兼容；新增覆盖率不能为无编号调用补造用途或采用结果。
目标组合发生变化不等于收益贡献，跳过复核或复用审查的次数也不能直接换算成节省金额。

## 停止、恢复与异常通知

```powershell
.\scripts\run_autonomous_fund.ps1 -Mode stop -RunDir artifacts/fund-paper
.\scripts\run_autonomous_fund.ps1 -Mode resume -RunDir artifacts/fund-paper
```

`stop` 创建 STOP 文件（不带目录时包括所有正在运行的账户，并打印停止了哪些目录）；运行进程下一次迭代停止新单并尝试取消本应用已知未完成订单。
每种停止原因（谁、为什么）在 6 小时内通知一次（`stop_active`），服务反复重启或原因来回切换不会刷屏。
不要把创建文件当成券商已确认撤单。模型或网络调用进行中可能延迟处理；紧急时同时去券商界面核验并撤单。
Ctrl+C 可以停止进程，但不能保证撤回已经被券商接受的订单。
本地模拟盘的休市等待可被原生关闭钩子唤醒，Ctrl+C 后会退出等待并释放进程锁；
正在进行的模型或数据请求仍可能需要结束后才能退出。`-Once` 结束也会关闭撮合连接，后续撮合需重启同一账本。
若提示 `already in use`／`runner.lock could not be acquired`，说明另一个实例仍持有操作系统锁。
先结束原来的进程并等待退出，再使用原目录重启；不要删除锁文件、账本或更换目录来绕过互斥。
升级前已在休市长时间等待的旧进程不会自动获得修复，必要时由操作员核验命令行、项目路径与运行目录后，仅结束那个实例。
`resume` 只移除人工停止，不清除回撤锁或不确定订单。
回撤在 4%–8% 之间时由量化风控自动降低敞口预算并在回升后自动恢复，不需要人工；只有 8% 硬锁需要人工复位。
本地模式将上述命令中的目录替换为 `artifacts/fund-local`；轮询器也在休市时处理本地 STOP 和到期撤单。
回撤暂停需要操作员停掉进程后显式执行 `reset-drawdown`；新高水位从下一次净值开始，操作会留痕。

**没有有效决策的告警**：独立监控只在常规交易时段检查。开盘 90 分钟后今天还没有 `decision_validated`，或最近一次决策后，从它自己的 `next_review_at` 起超过 3 小时仍没有新的决策，就发一次 `decision_drought` 通知（每个纽约交易日最多一次），附今天的 `decision_backoff` 次数。以下不算：STOP 期间（解除后重新计 90 分钟）、当天的模型次数或费用预算用完、只观察运行、休市。安静复核跳过（`review_skipped`）不受影响：基金经理仍然至少每 `max_quiet_minutes` 被调用一次。

**可选数据准备不会卡住交易迭代**：独立监控在开盘期间如果 180 秒内既没有迭代开始／结束、也没有模型调用事件，就判定
“迭代卡住”并写 STOP。因子研究的历史数据（含研究股票池）、SEC 财报、财报日历、FRED 宏观数据和历史危机窗口的长历史都是
可选数据：在 local／paper 的每轮交易迭代里最多占用 `PREPARATION_BUDGET_SECONDS`（45 秒），没下载完的下一轮接着做，
已下载的不会重复下载（日线按天缓存在内存，SEC 摘录缓存在磁盘）。空闲迭代和 STOP 期间也会利用剩余时间继续准备，
恢复交易时数据已经就绪。准备期间因子实验室显示 `warming`（只给出已验证因子，不给排名，排名不完整的横截面会扭曲 IC）；
财报日历未查到的股票列在 `event_risk.deferred`，这段时间不降仓；FRED 未取到的序列标为 `deferred`；
危机窗口未取到历史的证券按基准跌幅 × max(1, beta) 悲观代替，基准本身总是先取。风控必需的数据（可交易证券的日线）仍然同步获取。
开盘前研究和收盘后复盘不受这个时间限制，会一次准备完整；历史回测也不受限制，结果不依赖机器快慢。
这是 2026-11-02 服务器事故的修复：午间更新重启后，第一次决策同步下载了这些数据，超过 180 秒，被判定卡住；
每次重启内存缓存清空又重复一遍，直到 24 小时内 3 次自动恢复用完（见 `docs/investigations/2026-11-03_FUND_ITERATION_STALL.md`）。

**进程稳定性**：LumiBot 在实时模式下，只要有异常逃出生命周期钩子（每轮迭代、开盘前、收盘后），就会调用
`on_bot_crash` 并结束整个策略。本应用的处理：

- 每轮迭代的业务逻辑（读账户、盯盘、调用模型、下单）出错，只记录 `blocked` 通知，下一轮照常运行；
- 账本导出、报告重建、迭代记录等**可重建的记账步骤**失败（数据库暂时被锁、磁盘写入失败、报告数据异常），
  记录 `bookkeeping_error` 通知并在下一轮重试，不会结束进程。如果账本真的无法写入，所有订单预留也会被拒绝，
  继续运行不会增加风险，而进程退出反而会停止盯止损；
- 盘前研究、盘后复盘、因子检验、学习评估各自出错都只发通知，不影响交易进程；
- 新闻轮询、Yahoo 实时推送在后台线程中逐轮捕获错误并自动重连；Paper 模式的心跳线程单次写入失败不会退出；
- 监控进程逐条处理 Telegram 回复：某条回复处理出错只记录 `telegram_command` 错误，不会让监控退出或反复读同一条；
- 模型调用很长（研究加决策超过 3 分钟）但仍在推进的迭代，不会被误判为“迭代卡死”；
- STOP 期间仍会核对券商的订单状态，已撤销或已成交的订单会被标记结束，自动恢复因此不会一直被挡住；撤单请求同样限频；
- 若仍有异常让进程崩溃，`on_bot_crash` 先写入 `bot_crash` 通知，独立监控进程据此（以及心跳超时）通过 Telegram 告警；
- 历史回测中这些错误仍直接抛出，以免测试掩盖真正的 bug。

**进程退出后的自动重启与自动恢复**：

- Ubuntu：三个 systemd 服务（交易、监控、数据员）退出后 30 秒自动重启；
- Windows 或没有 systemd 的机器：用 `serve` 代替直接运行，它同时管理交易、监控和数据员三个进程，任一退出 30 秒后重启：

  ```powershell
  .\scripts\run_autonomous_fund.ps1 -Mode serve
  ```

  与服务器一样要求在 `.env` 配好 Telegram。开机自动启动可在“任务计划程序”中创建登录时运行的任务，
  例如 `schtasks /Create /TN "LumiBot Fund" /SC ONLOGON /TR "powershell -NoProfile -ExecutionPolicy Bypass -File <repo>\scripts\run_autonomous_fund.ps1 -Mode serve"`；
  长期运行请关闭电脑睡眠（`powercfg /change standby-timeout-ac 0`），睡眠期间进程冻结，心跳超时会触发 STOP。
  Windows 下的 `serve` 只在模拟测试中验证过，尚未在真实 Windows 机器上运行。

每次（重新）启动都会先写入 STOP，避免无人监控的成交。**STOP 文件记录原因**，分三级，后写入的不能降级：

| 级别 | 来源 | 自动解除 |
|---|---|---|
| 人工 | `stop` 命令；**手动关闭**服务（`systemctl stop`／`restart`、在 `serve` 窗口按 Ctrl+C）；首次安装、**全新账户的第一次启动**（包括切换 `FUND_MODE`／`FUND_RUN_DIR` 后）、恢复的备份、旧版本留下的空 STOP | 永不，必须 `resume` |
| 监控 | 看门狗或服务监督发现故障 | 仅进程级故障（心跳超时、进程退出或卡死、监控暂时不可用）；磁盘不足、版本不符、撮合错误、未配置通知不解除，且之后出现的进程级故障不能覆盖这些需要人工处理的原因 |
| 服务 | **异常关闭**：进程自己退出（崩溃）、被系统杀死、断电或死机后重新启动、操作系统关机或重启 | 是 |

STOP 的类别、原因或已提供的时间字段损坏，以及非 UTF-8 内容，都按人工停止处理，不会让读取流程崩溃，
也不会被服务重启降级为可自动解除的停止。核对后仍可用正常的 `resume` 命令解除。

自动恢复由独立监控进程执行（`config.json` 的 `service` 段，`.env` 中 `FUND_AUTO_RESUME=false` 可关闭），必须同时满足：
交易进程连续健康至少 `auto_resume_after_seconds`（默认 180 秒，故障后从恢复时重新计时）；没有状态不明或未结束的订单预留
（交易进程在 STOP 期间会撤销本应用的未完成订单）；24 小时内自动恢复不超过 `max_auto_resumes_per_day` 次（默认 3）。
恢复、被挡住（`auto_resume_blocked`）或次数用完（`auto_resume_exhausted`）都会通过 Telegram 通知。
心跳必须未超时且不在观测时间之后；未来时间戳记为 `heartbeat_unavailable`，不能累计为自动恢复所需的连续健康时间。
真实轮询在读取心跳后采样 UTC 时钟，避免运行进程在轮询期间正常刷新心跳时被误判；心跳恢复正常后重新累计健康期。
手动关闭和异常关闭的区分：服务收到停止信号时，若操作系统正在关机或重启（systemd 报告 `stopping`）视为异常，开机后自动恢复；
其他停止信号（你执行 `systemctl stop`／`restart` 或按 Ctrl+C）视为手动关闭，下次启动保持 STOP，核对后 `resume`，
修改 `.env` 后重启服务同样需要 `resume`。无法判断时按手动处理。直接关闭窗口或在任务管理器中结束进程，程序来不及记录，按异常处理。

`notify(kind, details)` 是通知扩展接口，默认输出控制台及持久化本地通知 outbox。
同一状况（同类型、同内容）在 30 分钟内只记录一次，STOP 提示为 6 小时，避免每分钟写入相同告警；
`report.json` 的 `blocked_iterations` 因此统计的是被记录的阻断通知数，而不是阻断的分钟数。
`notifications.json` 与 SQLite 通知事件是权威 outbox。可用独立进程接入 Telegram；
先在自己的 Telegram 客户端通过 BotFather 创建机器人并向其发送 `/start`，准备明确的 Chat ID。
密钥只放本地；第二个 PowerShell 窗口安全输入：

```powershell
$fundTelegramToken = Read-Host 'Telegram Bot Token' -AsSecureString
$env:FUND_TELEGRAM_BOT_TOKEN = [System.Net.NetworkCredential]::new('', $fundTelegramToken).Password
Remove-Variable fundTelegramToken
$env:FUND_TELEGRAM_CHAT_ID = Read-Host 'Telegram Chat ID'
.\scripts\run_autonomous_fund.ps1 -Mode notify-test -RunDir artifacts/fund-local
.\scripts\run_autonomous_fund.ps1 -Mode monitor -RunDir artifacts/fund-local
```

Telegram 持久化发送状态、重试和限流等待；相同告警在 30 分钟内抑制重复，未变化时保持安静。
`notify-test` 只向所选账户的通知收件人发送一条测试消息，不修改 STOP、不执行订单；
显示 `sent` 表示 Telegram API 已确认，仍须在自己的客户端确认收到。健康恢复后的新一轮故障会再次通知，
不会被重复告警抑制；限流等待对新旧消息全局生效。
发送确认丢失仍可能造成重复通知，事件序号用于辨认；不能保证恰好一次送达。
没有 Telegram 配置时可用 `-Mode monitor -ConsoleOnly`，只有本地保护，不代表手机已收到。
监控第一次启动忽略超过一小时的旧告警；请同时查看现有审批、回撤和订单状态。

独立监控默认检测 180 秒心跳失效、开盘后迭代停滞、900 秒模型调用未结束，以及旧执行器版本。
发现异常就写 STOP 并通知，旧状态未恢复时持续重申 STOP，不能只靠人工删除文件继续交易。
恢复后也不自动解除 STOP；核验订单后由操作员显式 `resume`。
本地模式使用撮合心跳；Alpaca Paper 使用独立运行心跳，原生迭代／模型开始结束事件提供额外进度证据。
监控必须在另一进程运行；本机断电、系统整体挂起、断网或 Telegram 故障仍会影响送达。
写 STOP 不等于券商确认撤单，紧急时仍须核对券商订单。未运行监控时，主程序保留本地告警，但没有独立保护。

## 自动盘后复盘与策略反馈

正常运行的进程在原生 `after_market_closes` 钩子中自动复盘：

1. 先核对订单并尝试记录账户；缺少收盘报价或账户接口失败时，保留真实最后观测时间并告警。
2. Flash 研究员读取当日已有研究、目标持仓、订单、成交、现金和持仓变化，结合只读市场研究整理证据。
3. V4 Pro 基金经理评估选股、择时与执行，输出中文复盘、保留教训、撤回假设、数据缺项和下一交易日策略备忘。
4. 成功完成的备忘按版本持久化；下一轮盘前研究、正常时段研究和基金经理决策都收到 `strategy_memory`。
   后续复盘重新检查前一版本假设，决定保留、修正或撤回；没有证据时允许不调整。

复盘上下文在原有 120 条／120,000 字符预算内优先保留被接受的完整计划、订单、成交、审批及资金变动，
再填入较新的常规观测；原事件内容与时间不变，`omitted_events` 和 `omitted_event_kinds` 披露省略量，完整账本仍可只读查询。
复盘将研究实际读取的记分卡随完成记录原子保存，监控无需等待随后写入的索引事件；经理重试仍使用该次已保存研究的记分卡。
旧记录没有内嵌记分卡时，优先只读恢复同日、同输入时间、同研究模型及同回答的已保存研究快照，随后兼容同日旧格式。
不改写账本；匹配不到的证据不补造，显式不可用与没有保存结果分别显示，不推断为没有样本。

复盘提示要求把单日观察与已验证规律分开：新设或修改的规则需预先说明样本外期限、比较基准、扣费口径和失效条件；
固定几个案例、次日表现或重叠预测不能证明优势。断言核验只覆盖已提交的快照数值断言，不验证整段因果解释或所有复盘正文。

选股与择时调整均包含假设、依据、证据引用、验证条件和失效条件。基金经理从本轮的
`allowed_evidence_refs` 清单逐字复制引用，优先使用 `evidence_catalog` 中的短编号：
复盘事件用 `event:<sequence>`，已保存研究的第 n 条证据用 `research:n`，
本次快照中实际提供的字段用 `context:<字段名>`（例如 `context:factor_lab`）。
原始来源名称仍可精确引用，来源原文和时间不会因编号而改写。清单不包含未提供的字段或不存在的事件。
编号只属于该轮快照，不能把旧备忘中的同名编号当成本轮新证据；引用旧备忘可用 `context:strategy_memory`。
编号索引随复盘和策略备忘保存，方便追溯到原始研究及保存的输入。
这是 AI 在后续决策中利用可追溯经验，不是重新训练模型或自动改写 Python，也不保证每天收益改善。
完整目标组合仍须由正常时段的新决策产生，再通过全部独立风控和新鲜行情校验。
盘后结果 schema 不接受 `targets` 或额外权限／风控字段；研究员与基金经理始终只有只读工具。
收益、回撤、每天订单数、投资范围、实盘入口都不由复盘修改。

按 NYSE 交易日识别休市、提前收盘和纽约日期。每个有本账户观测的已结束交易日最多完成一次复盘。
正常结束、重启启动和下一次盘前钩子都会检查遗漏的最近一个已结束交易日；
不会虚构账户启动前的交易历史，也不会在周末凭空生成交易日。离线跨过多日时只补最近有记录的一天，
没有自动补齐所有历史日期或全天候后台任务。需要保持交易进程运行，关闭进程期间不调用模型。

Flash 成功结果先提交 SQLite；Pro 失败后，下次上述检查复用该阶段，保留原始时间、模型和 Mock 来源。
盘后研究调用明确要求完整 `Research` JSON：非空 `summary`、至少一条 `evidence` 及其必填来源／时间字段。
使用 `deepseek/deepseek-flash` 或 `deepseek/deepseek-v4-pro` 的结构化 Agent 调用还会把实际 schema
传给 DeepSeek Responses API 的 `text.format`，包括研究员、反方、盘中经理和盘后经理各自的结构。
研究工具、推理原文、工具调用 ID／结果和缓存／输出用量保持在调用链中；`DEEPSEEK_API_KEY` 仍为必需，
已有 `DEEPSEEK_API_BASE` 覆盖必须支持 `/responses`，不会借用 OpenAI 的凭证或地址，也不会静默降级。
未完成或失败响应即使带有看似完整的 JSON 也不作为最终回答；提供方报告的用量仍保留。
接口结构约束不能保证请求一定完成或研究事实正确，必填字段、真实证据时间和引用仍由本地校验。
部署后可单独运行 `scripts/check_deepseek_schema.py`：默认 `--offline` 只做模拟；
显式 `--real-models` 才调用真实 Flash／Pro，并可用 `--env-file "<your-secret-file>"` 选择密钥文件。
脚本统一用当前 `Research` schema 检查 `summary`／`evidence`、合成只读工具往返和已报告用量，
默认最多八次提供方请求（模型回答前可再次读取工具，最多三轮，记录为 `tool_rounds`；
第四次要求工具判为 `too_many_tool_rounds`），不自动重试、不连接券商；结果保存在 `artifacts/verification/deepseek-schema-smoke/`。
`--schemas all` 再检查基金经理决策（`Decision`，含 `Research` 没有的 `exclusiveMinimum`）、反方审查（`Critique`）、
盘后复盘（`PostmarketReview`，引用必须来自给定清单）和约束探针（故意要求空 `summary`、空 `evidence`、权重 1.5、入场价 0：
返回了这些值说明 DeepSeek 没有强制该约束，记为 `not_enforced` 并判为失败；入场价可为空，
模型用 null 代替 0 记为 `held_null`；实际返回值记录在 `constraint_observed`），两个模型最多 18 次请求。
它不代替完整账户策略复现，也不能证明正在运行的服务已经重载新代码；详见 `docs/AGENT_STRUCTURED_OUTPUT.md`。
真实接口若在第一次请求就返回 HTTP 400，表示请求被拒绝，不能据此声称原生 Schema 已实测可用。
更新后的诊断会提供 `provider_problem`：区分格式不可用、Schema 关键字／必填项规则被拒绝、
定义不被接受，以及 Schema 与工具／推理模式的组合不兼容；未知原因仍保留为 `provider_request_rejected`。
同时保留已知提供方错误码、公开参数名和只含公开 API／Schema 词汇的 `diagnostic_terms`，
不复制错误正文、输入值、密钥、私有地址或请求 ID。分类仅用于定位，不触发重试、自动删字段或输出模式降级。
首次真实检查中两个模型均返回了 HTTP 400；后续 Flash 的诊断已定位到严格对象规则：`required` 必须包含所有 `properties`。
原 Pydantic schema 的 `ideas` 等带默认值字段及部分嵌套字段未列入 `required`，因此请求被拒绝。
Flash 和 Pro 共用的发送层现在递归生成严格 wire schema，明确要求模型输出这些字段；字段类型、约束、默认值、
原 schema 和本地验证保留，程序不补造模型答案，也不把非空字段改成可空。未声明 `additionalProperties` 的属性对象
在请求副本中设为 `false`，已显式声明的设置保留。脚本同时验证原 schema 和 wire schema，并分别记录摘要指纹。
需在同步核心适配器及诊断脚本后重跑真实调用；本地替身通过不能代表提供方已经接受修正后的请求。
如果研究员返回的 JSON 不符合 schema 或无法提取 JSON，每次复盘尝试最多额外纠正一次，提供原始回答、
安全的字段错误位置及同一份输入快照，要求模型根据真实证据返回完整结果；程序不自动补摘要、证据或日期。
两次回答和用量均保留在 `agent` 记录，`postmarket_research_retry` 记录纠正原因。
纠正受 STOP、当天调用次数及费用预算限制，并为后续基金经理调用留出次数；成功后仍校验证据时间，
实盘无日期来源继续可用。传输／运行失败、空回答和历史证据晚于回放时点不触发这种格式纠正。
纠正后仍不合格则保留告警，不保存为成功研究或新备忘。

**盘中决策的格式纠正**（2026-11 起）：基金经理的每次决策请求本来就带着 Decision schema：
`deepseek/deepseek-flash` 和 `deepseek/deepseek-v4-pro` 走 DeepSeek 原生严格 JSON schema（`strict: true`）；
其他模型只能把 schema 写进提示词。但提供方并不总是严格执行，偶尔仍会返回不合格的回答。
2026-11 的 `schema_validation: $ (model_type)`（`$` 指整个回答，`model_type` 指它不是一个 JSON 对象）就是这样：
回答是一段文字，LumiBot 的解析器从文字里取到 `[1]` 这样的方括号，当成了列表。2026-11-10 起解析器只取和 schema
同类型的值（决策要对象就只取 `{...}`），文字里的方括号不再被误认；文字里没有 JSON 对象时报 `invalid_json`。
以前这一轮决策直接作废，按 5、15、60 分钟退避重试。
现在第一次格式不合格时，再发一次真实调用（用途记为 `decision_correction`）：提供出错位置和错误类型（不含任何输入数值）
和它自己上次的回答（最多 6000 字，标明是不可信的旧输出），要求重新返回完整的决策 JSON 对象。
`decision_format_retry` 记录纠正原因，两次回答和用量都留在 `agent` 记录里。
纠正受 STOP、当天调用次数（为复盘保留的次数除外）和费用预算限制；提供方故障、超时和空回答不纠正，交给 LumiBot 自己的重试。
纠正后仍不合格，才像以前一样作废并退避，通知末尾注明 `(also after one format correction)`。
本地／Paper 的回答结构合格但时间过旧、在未来或已经过期时，同样可使用这一次纠正机会，重新读取账户、风险和数据员上下文，
要求经理依据当前证据重新评估并返回完整决策。格式与时间问题共用一次机会，绝不会因两类错误连续追加第三次调用。
`decision_time_rejected` 和 `decision_time_retry` 记录原因、原始 `as_of`／`expires_at`、请求时间、校验时间与年龄；
纠正回答仍不合格时注明 `(also after one timing correction)`，按原有规则退避。
Python 不改写旧答案或来源时间，不放宽五分钟接受期限；历史回放的时间错误不触发此纠正，其他风险超限仍直接拒绝。
重新读取上下文之后还会检查 STOP、调用次数和费用预算，所有执行前的账户与行情校验继续生效。

盘后研究员和经理会收到 `cash_management` 政策快照（可引用 `context:cash_management`），区分 AI 目标名单和系统现金停放。
现金管理证券被排除在 `eligible_universe` 外是设计行为，不足以证明订单越界；取消原因应引用实际事件，缺少原因时标为未知。
复盘重试沿用已保存研究的原始政策，不把当前配置补写成旧快照的证据；旧快照没有该字段时不补造。
诊断里新增 `answer_shape`：回答最外层是 object、array、string、number、boolean、null、fenced（Markdown 代码块）
还是 prose（文字），以后出现同类问题能直接看出模型返回了什么，不记录回答内容。
启动时账本记录 `structured_output_protocol`：每个角色的模型是否走强制 schema；只是提示词约束的角色会在日志里提示一次。
完成的复盘不会因重复回调、重启或重新导出而再次调用模型。模型失败会写入 `postmarket_review_error` 通知，
旧备忘保持有效，未完成的复盘不激活。外部调用成功、落盘前崩溃的极短窗口仍可能重复付费，不能声称模型请求恰好一次。
如果只有引用校验失败，每次尝试最多让同一基金经理额外修正一次：提供原复盘、失败位置及同一份证据清单，
不重新运行已成功的研究员，也不把模型转述自动认作新证据。修正调用照常计入模型次数、用量与费用，
STOP、当天调用次数上限或费用预算已用完时不发起修正。
修正后仍未通过校验，通知和运行日志会标出复盘日期及失败位置，例如 `selection_adjustments[0].evidence_refs[1]`
表示第一条选股调整的第二个引用。原始引用可在本次基金经理调用的 `trace=` 文件中查看。
这里的“outside the supplied review”表示引用不在本轮提供的证据清单内，不是证券超出投资范围或仓位超限。
核对时须比较该次基金经理实际输出的引用和已保存研究快照里的允许清单；仅凭错误位置无法判断是改写来源名称、
引用了未提供的事件，还是其他引用问题。无效复盘不保存为新的策略备忘，上一份有效备忘继续使用。
STOP 和只读观察模式不触发新复盘。回撤暂停只限制新增风险，不妨碍只读复盘。

回测的日志、复盘完成时间和收盘时间都按策略时钟过滤，未来完成的备忘不能传给过去的决策。
原生 Pandas 日线快路径不调用收盘钩子，因此在下一个日期行、当日决策之前补上一已结束交易日的复盘，
不会把时钟提前到未来收盘。用户结束时间前尚未结束的最后一日不补造盘后结果。
原生回测结束清理若越过用户结束时间，不额外复盘。日线按纽约日期和 NYSE 实际收盘时间判断是否完成，
包括夏令时和提前收盘日：收盘前排除当日 bar，收盘后可使用数据源已经提供的当日收盘价。
行情源、预取文件和策略内存中的盘前数据不能代替盘后价格；跨过收盘后按新截止日期刷新，
持久化价格同时记录该日期，重启可复用已完成的收盘价，盘中读取仍只得到更早的交易日。
来源未提供当天收盘价时仍披露缺项，不用最新报价冒充收盘价。
local／paper 模式的日线异常或空响应只缓存 60 秒，之后允许重试，并让依赖缺失历史生成的风控估计、风格、
因子、快照和记分卡重新计算；成功的其他证券日线仍可复用。重试继续服从数据源已有的退避，
历史回放不使用墙上时钟决定重试，保证相同输入下的结果可复现。数据恢复前，缺失历史的原有风控限制仍然生效。
记分卡在可见的研究想法、决策、复盘或执行事件增加时，以及跨过收盘或纽约日期时重新计算；
无关心跳不会使缓存失效，模拟时钟之后的事件不进入缓存或统计。
研究可核对已完成分钟线；缺少收盘净值、新闻、费用或完整样本必须披露，不能伪造。
观察盈亏包含未实现部分，可能只是日内最后观测，并非保证的收盘净值或已实现收益。
基准只有观测时间吻合才计算，未对齐则为 null。
每轮上下文最多带入 120 条、120,000 字符的相关事件，并披露省略数量；完整记录仍保存在 SQLite。
策略备忘有长度上限，并附最近三次复盘摘要，防止运行越久上下文无限增长。

## 新旧目标的经济对照（只读）

运行 `bash scripts/fund-logs.sh economics`，或
`python -m scripts.autonomous_fund.run economics --run-dir <account-directory>`。
它只读取所选账户的账本、已有日线缓存和股票池快照，不调用模型、不下载数据、不改审批和交易。
周报会在报告截止时间下显示同一项评估，范围为全部可用历史，不能与当周收益直接相加。

- **换方案是否比维持旧目标好**：新旧目标从决策被接受后的第一个交易所收盘同时起算，观察之后 1／5／20 个交易日。
  先按目标权重变化的每侧 10bp 扣情景交易摩擦；另列准确关联到本次决策的经理、纠错和新反方调用费用。
  复用反方不重复收费；研究、事件判断、审批和其他运营费用不归入这项局部费用，仍在基金净成本计分板计算。
  旧记录缺少原目标、调用 ID、用量或当时净值时，相应值保留未知，不倒推或按零费用填充。
  全部可评分方案的平均增益（可能含重叠）与费用完整子集使用不同样本，不能用两个均值相减解释费用影响。
  `cost_matched` 在费用完整的同一组观测上同时报告扣费前均值、调用链费用占净值的平均比例和扣费后均值；
  `cost_matched_non_overlapping` 先排除费用不完整记录，再按接受时间顺序保留区间不重叠的观测，并报告相同三项。
  选择不依赖后续收益好坏；相邻区间可共享一个收盘端点但不共享收益区间，区间不重叠也不保证统计独立。
  没有费用完整样本时显示数量 0、均值未知，不把全部方案的收益冒充同组扣费前收益。
- **期初风险对照**：从区间起点的真实收盘持仓和估值估计贝塔，锁定到下一收盘；剩余部分使用当时记录的现金代理，
  明确未配置代理时使用零收益美元现金。估计只使用起点已完成的日线，不看区间结束后的风险。
  未知贝塔不按 1 补齐，超出无杠杆对照范围或缺行情时不强行给结果。扣全部模型和数据费后的差额要求费用完整。
  固定基准继续保留，不能挑表现较差的对照替代它们。
  这是贝塔匹配，不表示波动率或 ES 完全相同。报告仅复合两端都有有效收盘估值的相邻交易日，另列缺口数，
  不把这项匹配区间收益当作连续全期收益。

这里比较的是**目标价格方案**，不还原实际成交、触发当日的日内盈亏、整股、限价、止损或风控缩量；方案不含分红和现金收益。
期初对照则使用账本基准价格与已记录的公司行动，但不保证为交易所正式收盘价。
基准价格优先取该估值回执随附、源时间有效的观测；旧记录仅使用估值时点之前的当日正常交易时段记录，
保留逐证券的有效结果。盘后新价格不能覆盖收盘价格；次日才取得的收盘回执按它原本的估值日期归属，查询时间仍限制何时可以看到它。
基金经理看到的历史净成本计分板同样只连接相邻交易日，缺少中间估值时不跨过去拼收益，并在报告中披露区间缺口。
缓存日线中单独的空值、非有限数值、布尔值、非正价格或坏日期按行隔离，其余有效行保留，缺口不补；
`economics` 会显示被隔离的行数及不可读文件数。
研究历史可能被数据商事后修订，不能当作经认证的历史数据版本。报告列出非重叠样本数；样本重叠及非随机选中的决策
均不能证明模型的因果贡献。现有决策记分卡的贝塔也改为使用决策被接受时已完成的日线，提前收盘按交易所日历处理。

调用覆盖率和同组扣费比较是所有本应用账户的只读诊断，对 local、paper、历史模式使用相同规则，
不依赖策略、账户或证券名称，也不更改调用预算、调度、行情、撮合或风控。合成账本回归
`tests/test_autonomous_fund_cost_attribution.py` 覆盖旧记录、失败／拒绝／采用未知、缓存／脚本／零费用、
费用完整与缺失、重叠区间及截止时间。测试证明本地实现的输出；部署后的服务版本与实际报告仍需单独核对。

## 复盘调整的后续评估与对照回放

`strategy_evaluations.json` 自动跟踪每版备忘之后的实际账户观测，分别显示 5／20 个观测交易日的结果。
没有足够交易日就显示 `insufficient_observations`；不填充休市或缺失数据，不把日内最后观测包装成收盘净值。
该结果与后续研究、决策和复盘共享。组合同时受到后续多次决策影响，不能把这份跟踪当成某版备忘的因果效果。

可显式进行一次原生对照实验：两次回放使用相同冻结 CSV 行情、资金、费用、投资范围、风控和模型设置；
基线不带备忘，候选仅带选定的冻结备忘，期间不激活新的滚动备忘。

```powershell
.\scripts\run_autonomous_fund.ps1 -Mode qualify -RunDir artifacts/fund-qualification -DataDir <frozen-history-directory> -MemoryFile <earlier-postmarket-review.json> -Start <later-start-date> -End <end-date>
```

CSV 须覆盖完整投资范围及 SPY／QQQ，遵循下面的历史数据格式。备忘的完成时间和所评交易日收盘必须不晚于起点，
输入 CSV 在两次回放前后核对 SHA-256，发生变化就拒绝输出可比结论。每天的历史数据仍由原生引擎按模拟时钟提供。
`-Scripted` 可无付费模型调用检查流程，不能验证投资判断；不带此选项会产生真实模型调用费用。
审批规则同样生效，实验不会假设人工批准重大交易，也不会向运行中的模拟账户发单。

输出 `qualification.json` 和 `baseline/`、`candidate/` 的独立成交／净值／用量记录。
少于 20 个日采样标为 `insufficient_sample`；样本足够时仅报告该窗口收益／回撤是否改善。
单次对照含模型随机性、样本选择和训练知识污染风险，不证明未来盈利；不会自动推广候选或改变运行权限。
更严格的多窗口、独立保留样本和统计检验仍需独立研究，不能把这个功能当成已认证的策略优化器。

## Schwab 实盘准备

本应用**仍然没有实盘下单入口**，`TRADING_BROKER=schwab` 或任何 `.env` 设置都不会启用它。目前提供的是实盘前的零风险准备：

**1. 账户选择**：强烈建议在 Schwab 为 AI 单独开一个账户（同一登录下可有多个账户，用 `SCHWAB_ACCOUNT_NUMBER` 指定），
放入授权资金即可，`FUND_ALLOW_EXTERNAL_HOLDINGS=false`。这样 AI 的成交、税务批次和你的持仓完全分开。

**2. 与你的持仓共用一个账户**（可行但次优）：设 `FUND_ALLOW_EXTERNAL_HOLDINGS=true`。
- 首次启动时，账户里的**全部**持仓（股票、ETF、货币基金等）都记为你的外部持仓并冻结数量，按券商市值估值，不计入 AI 分仓；
  分仓 = 现金 − 保留现金，AI 之后自己买入的才是分仓持仓。
- 你已持有、且在 AI 投资范围内的代码（例如你持有 AAPL）会**自动从 AI 可交易范围中剔除**：否则 AI 卖出时，
  券商可能按先进先出等批次规则卖掉你的长期持仓，带来税务后果，也无法区分归属。你在这些代码上的挂单不会阻挡 AI。
- 你手动买卖了外部持仓，系统会暂停交易，核对后用 `adjust-reserve --rebaseline-external`（出入金同时用 `--amount`）重新确认。
- 券商持仓读取失败或只返回部分结果时直接拒绝，不会把“读失败”当成“没有持仓”而重复买入。

**3. 只读体检 `schwab-check`**：在 `.env` 填好 `SCHWAB_ACCOUNT_NUMBER`（以及自己的 `SCHWAB_APP_KEY`/`SCHWAB_APP_SECRET`/
`SCHWAB_BACKEND_CALLBACK_URL`，或使用 LumiBot 默认应用）后运行：

```powershell
.\scripts\run_autonomous_fund.ps1 -Mode schwab-check -RunDir artifacts/schwab-check
```

它使用 LumiBot 原生 Schwab 适配器完成 OAuth 和账户读取，并在该实例上**禁用所有下单、撤单、改单方法**。输出 `schwab_check.json`：
账户类型（现金／保证金）、现金、已交割可用现金、未交割现金、清算价值、每个持仓及是否在 AI 范围、挂单、
预计保留现金与 AI 起始分仓、将被剔除的共享代码，以及需要处理的问题（现金少于授权资金、保证金负债、现金账户已交割现金不足、
已有持仓但未允许外部持仓、存在挂单）和提示（未设 `SCHWAB_APP_SECRET` 时约 7 天需重新登录；未设 `SCHWAB_APP_KEY` 时 OAuth
回调经过 LumiBot 默认应用的 `api.botspot.trade`，如需完全自控请注册自己的 Schwab 开发者应用）。

**4. 拟议的实盘入口（需要你单独明确授权后才会实现）**：
- 前置条件：本地或 Alpaca Paper 连续运行通过 `acceptance`（默认 20 个交易日），`schwab-check` 无问题；
- 独立的 `schwab-live` 模式，必须同时满足：`.env` 中显式确认（如 `FUND_LIVE_CONFIRM=I-UNDERSTAND-REAL-MONEY`）、
  账户号与上次体检一致、监控与 Telegram 健康、授权资金不超过你设定的上限；
- 现金账户只用已交割资金买入（T+1），保证金账户也绝不借款或卖空；
- 初期所有买入都需要审批（`FUND_AUTO_DAILY_EXPOSURE_INCREASE=0`），稳定后再放开自动额度；
- 每笔订单与券商回报逐笔对账，任何不一致即 STOP；首周只允许很小的授权资金；
- AI 仍然没有修改配置、权限或启动实盘的能力。

Schwab 原生适配器的通用说明见 `docsrc/brokers.schwab.rst`（OAuth、token 续期、订单状态）。
不要把框架通用文档中的 paper/live 描述当成 Schwab 提供独立 Paper 交易环境的保证。
